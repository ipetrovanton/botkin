# Многопользовательский кабинет: роли, верификация распознавания, MinIO, формы пациента и «рекомендации дня»

> Дата начала: 2026-07-13 20:56
> Стек: Python 3.12, FastAPI, SQLite (+sqlite-vec), Alpine.js SPA, Ollama (qwen3-vl, bge-m3), aiogram

## Постановка

Пользователь попросил большой UX-апгрейд веб-кабинета: разделение по пользователям с ролью
администратора (CRUD пользователей и анализов); подтверждение/корректировка распознанных
данных при загрузке (+ручное добавление показателей/лекарств/рекомендаций); хранилище
оригиналов документов (S3) с удалением/заменой/версионированием и валидацией изменений;
формы профиля тела (возраст, пол, вес, группа крови и т.д.), жалоб в свободной форме,
текущих препаратов; настройка частоты синка Garmin; «рекомендации дня» с учётом погоды,
геомагнитных бурь и (по настоянию пользователя) гороскопа. Все данные форм должны влиять
на RAG-рекомендации. Плюс: дать локальным моделям веб-доступ с пополнением RAG-базы
результатами, и бенчмарк нескольких эмбеддинг-моделей (компактных и максимально больших).

Критерий успеха: все 7 этапов реализованы, тесты зелёные, кабинет работает локально.

## Контекст и ограничения

- Окружение: macOS (разработка), прод-схема Windows+WSL2+Ollama; Python 3.12, uv.
- До начала: однопользовательский-по-факту кабинет, идентификация — спуфабельный
  заголовок `X-Telegram-User-Id`; файлы на локальном диске `data/sources/{user_id}/`;
  ролей нет; RAG на bge-m3 (1024-dim, sqlite-vec); health-sync Garmin/Strava уже есть.
- Ограничения: всё локально (без облака), демо-уровень безопасности — по явному выбору
  пользователя в интервью.

## Интервью (решения пользователя)

1. Аутентификация: **демо-уровень** — заголовок остаётся, добавляем роли и экран выбора.
2. Хранилище: **MinIO** (настоящий S3-API локально в Docker), а не абстракция над диском.
3. Астрология: **как развлечение** — отдельный опциональный блок с дисклеймером,
   «не влияет на медицинские выводы». От влияния на рекомендации отговорил.
4. Объём: **все 7 этапов в одной ветке**, коммит на этап.

## План

1. Роли (admin/user) + админ-API + экран администратора в SPA.
2. Верификация распознанного: статус review, форма редактирования показателей/лекарств/
   рекомендаций, ручное добавление.
3. MinIO-хранилище оригиналов: версии, удаление/замена, валидация изменений.
4. Формы: профиль тела, жалобы, текущие препараты; учёт в контексте RAG-рекомендаций.
5. Настройка частоты обновления Garmin в кабинете.
6. «Рекомендации дня»: Open-Meteo (погода/давление), NOAA SWPC (Kp-индекс),
   гороскоп отдельным развлекательным блоком.
7. Веб-доступ моделей с пополнением RAG + бенчмарк эмбеддинг-моделей.

## Ход работы

### Этап 1: роли и админка (коммит a32ca2b)

- `users.role/display_name`: колонка с CHECK в schema.sql для свежих БД + запись в
  `_MIGRATIONS` для существующих. SQLite не умеет ALTER ADD CONSTRAINT, поэтому
  инвариант ролей для мигрированных БД держит `UserRepo` (whitelist в коде).
- Бутстрап первого админа — курица-и-яйцо: админов создаёт админ, а первого создать
  некому. Решение: `ADMIN_TELEGRAM_IDS` (env/config.json), роль присваивается в
  `get_or_create` и при создании, и при повторном входе (список мог пополниться позже).
- Два защитных инварианта в PATCH/DELETE: нельзя удалить самого себя и нельзя
  разжаловать последнего админа — иначе админка навсегда недоступна.
- Ручное добавление показателя админом упёрлось в `lab_results.document_id NOT NULL`:
  показатель без бланка не к чему привязать. Решение — ленивый служебный документ
  `source_path='manual://admin'` на пользователя.
- SPA: инлайн-редактор показателя сначала был на `x-show` и Alpine падал на
  `x-model="admin.editLab.analyte_name"` при `editLab === null` (x-model вычисляется
  и у скрытых узлов). Переведён на `template x-if`.
- Зомби-команда: фоновый `git commit` завис в статусе RUNNING без git-процесса за ним
  (ps пустой, index.lock нет); повторный блокирующий запуск прошёл мгновенно.

### Этап 2: верификация распознанного (коммит 63b2aac)

- Вместо нового статуса `review` в пайплайне — отметка `documents.verified_at` поверх
  готового `extracted`: бот и поллинг прогресса ничего не знают о верификации и не
  ломаются. Любая правка данных (PATCH/POST/DELETE показателей или заключения)
  сбрасывает отметку — подтверждение относилось к старой версии данных.
- PATCH-семантика через `model_fields_set` (pydantic v2): обновляются только явно
  переданные клиентом поля, «не прислал» ≠ «прислал null».
- Списки заключения (рекомендации/назначения) редактируются как textarea
  «строка = пункт», API сериализует list[str] → JSON-колонку.

### Этап 3: хранилище оригиналов MinIO (коммит 804914d)

- `storage.py`: два бэкенда за общим контрактом — LocalStorage (диск, версии в
  `.versions/`) и MinioStorage (нативный bucket versioning). Диспетчеризация по
  схеме uri в `source_path`: старые записи (абсолютные пути) продолжают работать
  после включения MinIO — миграция данных не нужна.
- Пайплайн (pymupdf/PIL) читает файлы только с диска → у хранилища есть
  `open_local()`: MinIO-объект скачивается в tmp-кэш по sha1(key).
- Удаление в версионируемом бакете: обычный remove ставит delete-marker, объект
  продолжает занимать место — удаляем все версии явно через list_objects(include_version).
- Замена файла: контент-валидация как при загрузке + запрет no-op замены тем же
  файлом (sha256), после замены — clear_extracted_data + перераспознавание.
- Сломались 5 тестов оркестратора: фиктивные пути `/tmp/a.jpg` без файла — пайплайн
  теперь честно проверяет существование исходника. Фикс: `Path(...).touch()` в хелперах.
- minio 7.2.20 (официальный SDK, sync — соответствует sync-обработчикам проекта);
  проверено на PyPI 2026-07.

### Этап 4: формы пациента — профиль, жалобы, препараты (коммит 1347a85)

- `patient_profile` (одна строка на пользователя): пол, дата рождения, рост/вес, группа
  крови, аллергии, хронические состояния, координаты (lat/lon для погоды).
- `patient_complaints` (many): жалобы в свободной форме с датой начала и статусом
  (active/resolved). `patient_medications` (many): текущие препараты с дозировкой и
  флагом active. Обе таблицы — миграция через `_MIGRATIONS`.
- RAG: `_patient_context()` в `recommend.py` подмешивает профиль, жалобы и препараты
  в контекст рекомендации. Промпт обновлён — правило 5: учитывать текущие препараты
  при рекомендациях (взаимодействия, дублирование МНН).
- API: `GET/PUT /api/patient/profile`, `GET/POST/DELETE /api/patient/complaints`,
  `GET/POST/PATCH/DELETE /api/patient/medications`. Все требуют `X-Telegram-User-Id`.
- 12 тестов (репозитории + API через TestClient).

### Этап 5: автосинк Garmin по расписанию (коммит febb0f6)

- `sync_interval_hours` в `health_accounts` (миграция через `_MIGRATIONS`); NULL = только
  вручную. API: `PATCH /api/health/accounts/{provider}/schedule` с валидацией 1–168 ч.
- `accounts_due_for_sync` — SQL-выборка истёкших интервалов: сравнение
  `datetime(last_sync_at, '+' || hours || ' hours') <= datetime('now')` на стороне SQLite.
  NULL last_sync_at = ни разу не синкали → попадает в выборку.
- `scheduler_loop` в lifespan API: тик каждые 15 мин (минимальный интервал автосинка — 1ч).
  Отдельного планировщика (celery/cron) не заводим: один процесс API, asyncio-цикла
  достаточно; пропущенный за время дауна тик наверстывается при следующем старте
  (сравнение по last_sync_at, а не по таймеру).
- Тесты: 3 падали из-за путаницы `telegram_user_id` ↔ auto-increment `user_id` в
  `health_accounts` — `get_or_create` возвращает auto-increment ID, не telegram_id.

### Этап 6: внешние данные для рекомендаций (коммит 7e23e93)

- Модуль `external/weather.py`: Open-Meteo (`api.open-meteo.com`) — погода без API-ключа
  (CC BY 4.0); NOAA SWPC (`services.swpc.noaa.gov`) — индекс Kp (геомагнитная активность,
  публичный API US gov). Все запросы через `urllib.request`, без внешних зависимостей.
- Модуль `external/astrology.py`: знак зодиака по ISO-дате + детерминированный гороскоп
  (seed = hash(знак + сегодняшний день) → один текст в течение дня). 10 шаблонов, без
  внешних API. По умолчанию выключен (`astrology_enabled: false`).
- API `GET /api/external/today`: погода + Kp + гороскоп (если включён). Координаты берутся
  из `patient_profile.latitude/longitude` (миграция) или из конфига (Москва по умолчанию).
- Интеграция в RAG: `_external_context()` в `recommend.py` подмешивает погоду и Kp в
  контекст пациента. Промпт обновлён: правило 6 — учитывать погоду/геомагнетику при
  рекомендациях по режиму дня, астрологию НЕ использовать для медицинских рекомендаций.
- SPA: виджет «Внешние факторы» на дашборде (карточки погода/🧲/♈), поля геолокации
  в форме профиля.
- Все внешние запросы — graceful: при ошибке сети возвращается None, блок пропускается.
- 9 тестов (6 — чистая логика астрологии, 3 — API с TestClient).

### Этап 7: RAG — бенчмарк embedding-моделей + API обновления (коммит 05b54b1)

- `rag/benchmark.py`: сравнение embedding-моделей на golden set из 5 медицинских
  запросов (парацетамол, гемоглобин, ибупрофен, лейкоциты, антибиотики). Для каждой
  модели строится временная vec0-таблица, размерность определяется автоматически
  (probe-эмбеддинг). Метрики: hit_rate@10, MRR, avg_distance.
- API `POST /api/rag/benchmark` — принимает список моделей, возвращает summary +
  per-query детали. Требует Ollama с установленными моделями.
- API `POST /api/rag/research/update` — фоновое обновление RAG свежими публикациями
  PubMed (через `rag.research.index_research`). `GET /api/rag/research/status` —
  состояние фоновой задачи.
- Флапающий тест: `_research_state` глобальная — фоновая задача из `test_research_update_starts`
  могла завершиться до `test_research_status_idle`. Фикс: явный сброс состояния в тесте.
- 8 тестов (3 — API research, 2 — API benchmark, 3 — бенчмарк-логика).

### Этап 8: UI-изменения — группы крови, автодополнение, SPA-кнопки RAG (коммиты 96f2686, 6d1e9a1, 04c0f13)

- **Группа крови**: `<select>` с 8 вариантами вместо текстового поля. Формат отображения
  `O(I) Rh+` (по просьбе пользователя). Значения в БД — `O−`, `O+`, `A−`, `A+` и т.д.
- **Город**: автодополнение из локального справочника `reference/cities.json` (~150 городов
  РФ с координатами и регионами). API `GET /api/directory/cities?q=`. Координаты
  сохраняются в `patient_profile.latitude/longitude` — используются для погодного контекста.
- **Препарат**: автодополнение из индекса ГРЛС (`rag_chunks WHERE source='drugs'`). API
  `GET /api/directory/drugs?q=`. Показ МНН и бейджа статуса (действующий/исключён).
  Дозировка — ручной ввод (в реестре ГРЛС нет данных о дозировках).
- **SPA-кнопки RAG**: «Обновить из PubMed» (`POST /api/rag/research/update` + поллинг
  статуса) и «Бенчмарк embedding-моделей» (форма ввода списка моделей → `POST /api/rag/benchmark`
  → таблица результатов hit_rate/MRR/avg_distance).
- CSS: стили для dropdown-автодополнения (`.autocomplete-dropdown`, `.autocomplete-item`)
  и бейджа статуса препарата (`.drug-badge`).
- 12 тестов `test_directory.py` (6 — города, 6 — препараты).

### Этап 9: интеграционные тесты цепочки (коммит 898a588)

- `test_integration_chain.py`: два теста полной цепочки
  upload→pipeline→edit→verify→profile→recommend с замоканными LLM-вызовами.
- **Проблема с моками**: `classify_document` и `extract_lab_results` не существовали —
  реальные функции называются `classify.run_vlm` и `extract.run_analysis`. Orchestrator
  вызывает их через `asyncio.to_thread`, беря функцию из атрибута модуля.
- **Проблема с reload**: `importlib.reload(appmod)` пересоздавал модули и затирал моки.
  Решение: мокаем после reload через `monkeypatch.setattr(orch.classify, "run_vlm", ...)`.
- **Проблема с await**: `notify_user` мокалась как `lambda *a, **kw: None`, но orchestrator
  вызывает `await notify_user(...)` — `None` не awaitable. Решение: `async def _fake_notify`.
- **Проблема с задержкой**: `DELIVERY_FALLBACK_DELAY=130` (секунды) — тест ждал 130с
  перед финальным статусом. Решение: `monkeypatch.setattr(orch, "DELIVERY_FALLBACK_DELAY", 0.0)`.
- **Проблема со статусом**: финальный статус pipeline — `extracted`, не `done`. Поправил
  assert в обоих тестах.
- Результат: 2 теста за ~2 секунды (вместо 270с с реальной Ollama).

## Архитектурные решения

- **Моки LLM в тестах**: `monkeypatch.setattr` на модуль orchestrator после `importlib.reload`,
  потому что `asyncio.to_thread` берёт функцию из атрибута модуля на момент вызова, а не
  на момент импорта. Мокать нужно именно `orch.classify.run_vlm`, а не `classify_mod.run_vlm`,
  т.к. reload может пересоздать ссылку.
- **DELIVERY_FALLBACK_DELAY=0 в тестах**: 130-секундный `asyncio.sleep` в orchestrator
  (push-fallback для поллинга бота) делает тесты неприемлемо долгими. Мокаем на 0.0 —
  логика доставки не тестируется, проверяется только pipeline.
- **Статус `extracted` как финальный**: pipeline не выставляет `done` — финал это `extracted`,
  после чего бот/поллинг забирает результат. `done` — артефакт старых тестов.
- **Docker: Ollama вне compose**: Ollama требует GPU и тяжелая (~5 ГБ модель в VRAM),
  контейнеризировать её бессмысленно для демо. `host.docker.internal` пробрасывает на хост.
- **Группа крови: значение vs отображение**: в БД хранится `O−`/`O+`/`A−`/`A+` (компактно,
  сортируемо), в UI показывается `O(I) Rh+` (медицинский формат). `value` атрибут `<option>`
  — для БД, текст — для пользователя.
