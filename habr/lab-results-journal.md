# Журнал реализации: распознавание лабораторных анализов

> Фактура для статьи на Хабре и доклада на конференции. Пишется по ходу работы:
> решения, находки, грабли, обоснования порогов. Не причёсано — сырьё для нарратива.

## Контекст задачи

Бот распознаёт медицинские документы (фото/PDF) через локальную VLM (qwen3-vl + Ollama,
instructor для structured output). Лабораторные анализы **терялись** в pipeline —
трёхслойный баг: извлечение (падение валидации), классификация, рендер карточки.

**Цель блока:** анализы надёжно проходят pipeline и выводятся в Telegram; распознанные
названия нормализуются по справочнику **ФСЛИ** (Федеральный справочник лабораторных
исследований, OID 1.2.643.5.1.13.13.11.1080, портал НСИ Минздрава) — каноничное имя +
LOINC + код НМУ; единицы измерения сверяются с эталонными.

**Метод:** строгий TDD (red-green-refactor), 11 задач. Архитектура повторяет уже
проверенный блок B (нормализация препаратов по ГРЛС): офлайн-скрипт `xlsx → registry.jsonl`,
ленивый синглтон-нормализатор на `rapidfuzz`, декларативная миграция БД.

## Task 5: скрипт сборки реестра ФСЛИ (xlsx → jsonl)

**TDD-цикл:**
- RED: `tests/test_build_analyte_reference.py` (5 тестов на чистых функциях
  `row_to_record` / `normalize_key` / `STATUS_MAP`) → `ModuleNotFoundError` (модуля нет). ✓
- GREEN: `scripts/build_analyte_reference.py` — 5/5 passed.
- REFACTOR: добавил guard `if ws is None` (как в `build_drug_reference.py`); ruff чисто.

**Структура источника ФСЛИ (xlsx):** один лист «Справочник», шапка в строке 2 (1-based),
данные с 3-й. ~18 значимых колонок; берём LOINC, FULLNAME, ENGLISHNAME, SHORTNAME,
SYNONYMS (разделитель `;`), UNIT, GROUP, TESTSTATUS, NMU.

**Дизайн-решения (фактура для статьи):**
- **Параллель с блоком препаратов.** Скрипт сознательно повторяет структуру
  `build_drug_reference.py` (ГРЛС): те же `normalize_key`, `_meta` первой строкой jsonl,
  `write_registry`, `argparse` + `# pragma: no cover` на `main`. Единый паттерн «офлайн-сборка
  справочника из госвыгрузки → jsonl» переиспользуется между регистрами Минздрава.
  Разница: ГРЛС — ZIP из 8 листов-статусов, ФСЛИ — один xlsx-лист.
- **`normalize_key`: ё→е + lower + схлопывание пробелов.** OCR и сами бланки путают «ё/е»;
  ключ дедупликации и матчинга должен быть к этому устойчив. Тест-кейс `«  Гёмоглобин  Общий »`
  → `«гемоглобин общий»` фиксирует все три преобразования разом.
- **LOINC «0» → null.** В выгрузке отсутствие кода LOINC закодировано строкой "0", а не пустотой.
  Если не вычистить — в БД попадёт мусорный код «0», ломающий связку с LOINC. Отдельный тест.
- **Дедупликация по нормализованному имени.** Первый победитель остаётся (`seen`-множество).
- **`STATUS_MAP`: Актуальный/Новый/Устаревший → active/new/deprecated.** Статус теста несём
  до рантайма, чтобы потом подсвечивать устаревшие позиции в карточке.

Коммит: `feat(reference): скрипт сборки справочника анализов из ФСЛИ (xlsx → jsonl)`.

## Task 6: генерация registry.jsonl — две засады в реальном файле

Первый прогон скрипта на живом `Справочник лабораторных тестов.xlsx` дал **«Записано 0 тестов»**
(ожидалось ~20727). Диагностика вскрыла два расхождения плана с реальностью — обе попадут в статью
как иллюстрация «офлайн-данные госреестров полны сюрпризов, читай файл, не доверяй спеке».

**Засада 1 — битые `dimensions` + `read_only=True`.**
В `read_only` режиме openpyxl берёт размеры листа из сохранённых метаданных, а выгрузка ФСЛИ
записала туда `A1:A1` (хотя реально `A1:R20729`). Итог: `iter_rows` отдаёт ровно одну ячейку
`'ID'` и обрывается → ноль данных, без ошибки. Тихий провал, как и `extra="forbid"` ранее.
Перепроверка с `read_only=False` показала реальные 20729×18.
Фикс: `ws.reset_dimensions = True` (заставляет openpyxl вычислять границы по мере чтения,
сохраняя потоковый режим и не вытягивая 20k строк в память).

**Засада 2 — двойная шапка.** План предполагал шапку в строке 2. Реально:
- строка 1 — **машинные** имена колонок: `ID, LOINC, FULLNAME, ENGLISHNAME, SHORTNAME, SYNONYMS, …`
- строка 2 — **человекочитаемые** описания: «Уникальный идентификатор», «Код LOINC», «Полное наименование», …
- строка 3+ — данные (первая запись: АЧТВ, LOINC 14979-9, НМУ A12.05.039, ед. «с»).

`row_to_record` матчит по машинным ключам (`FULLNAME`, `LOINC`), значит шапка — строка **1**,
а строку 2 (описания) надо явно пропустить — иначе она прошла бы как валидная запись с именем
«Полное наименование». `_HEADER_ROW=1`, `_DATA_START_ROW=3`.

**TDD-замечание:** баг `read_only`/dimensions специфичен для конкретного битого файла и не
воспроизводится синтетическим xlsx (openpyxl при сохранении пишет корректные dims). Поэтому
логику парсинга (шапка=стр.1, пропуск стр.2, данные=стр.3+) покрываю unit-тестом на временном
xlsx, а фикс dimensions верифицирую реальным прогоном (число записей > 0).

**Развязка засады 1.** Первая попытка фикса — `ws.reset_dimensions = True` в read-only режиме —
**не сработала** (прогон снова дал 0; прямая проверка: `iter_rows` всё ещё отдаёт 1 строку).
В потоковом read-only парсере openpyxl `reset_dimensions` не переопределяет границы из битого
`<dimension>`. Рабочее решение — `read_only=False` (полная загрузка вычисляет реальный
`A1:R20729`). Для разового офлайн-скрипта держать ~20k строк в памяти приемлемо. Урок для статьи:
«ленивый стриминг экономит память, но доверяет метаданным файла — а госвыгрузка им врёт».

**Результат сборки:** 20720 уникальных тестов (из 20727 строк; 7 — дубли по нормализованному имени).
Спот-чек качества:
- Гемоглобин → LOINC `718-7`, НМУ `A09.05.003`, ед. «г/л» ✓
- АЧТВ → LOINC `14979-9`, НМУ `A12.05.039`, ед. «с» ✓
- Статусы: **20579 active / 93 deprecated / 48 new**.
- **Заполненность полей: LOINC — 31%, НМУ — 37%, единица — 78%.**

**Находка для калибровки и статьи:** LOINC проставлен лишь у ~трети позиций ФСЛИ, НМУ — чуть
больше трети. То есть «обогащение анализа кодом LOINC» сработает не всегда — в карточке это надо
показывать как опциональное поле, а не обещать всегда. Единица измерения есть у 78% — на неё
можно опираться для сверки (блок проверки единиц, Task 9). Синонимов много и они разноязычные
(`["Активированное частичное…", "APPT", "aPTT, aPTT PPP, PTT"]`) — хорошая база для фаззи-матчинга.

## Task 7: пороги нормализатора в config

Тривиальный TDD-цикл. Добавлены `ANALYTE_MAX_EDIT_RATIO=0.35` и `ANALYTE_RATIO_FLOOR=75`.
**Замечание:** пороги для анализов строже, чем для препаратов (`0.40`/`70`). Обоснование —
названия анализов короче и их в справочнике больше похожих («билирубин общий / прямой / непрямой»),

показатели. Финальные значения подлежат калибровке на реальных бланках (Task 11).

## Task 8: AnalyteNormalizer — фаззи-коррекция по ФСЛИ

**TDD:** 9 тестов (8 на синтетике + 1 на упакованном реестре 20720 записей) → все зелёные.

**Дизайн-решения (фактура):**
- **Scorer = абсолютная дистанция Дамерау-Левенштейна** (как в блоке препаратов). Выбран потому,
  что OCR-ошибки — это расстояние 1–3 (з→э, и→н), и distance-scorer ставит верный ответ первым,
  тогда как WRatio/JaroWinkler на большом словаре дают ложные совпадения. `cap = max(1, floor(len ×
  0.35))` — короткие имена строже. Плюс пол по `fuzz.ratio ≥ 75`.
- **Разворот записи в множество поисковых ключей.** Каждый тест индексируется по полному имени,
  краткой форме, английскому имени и всем синонимам → одна каноничная запись. Так «CRP», «СРБ» и
  «С-реактивный белок» все ведут к одной записи. Первый победитель за ключ остаётся (детерминизм).
- **Короткие ключи (≤3 символов) — ТОЛЬКО точное совпадение.** Ключевое решение: на аббревиатурах
  «HGB», «СРБ», «АЛТ» фаззи с дистанцией 1 склеивал бы разные показатели (3 буквы, расстояние 1 =
  каждая вторая аббревиатура «похожа»). Поэтому для коротких запросов — строгий lookup по словарю,
  иначе `unverified`. Тест `test_short_abbreviation_requires_exact`: «HGB»→Гемоглобин, «XYZ»→unverified.
- **Принцип безопасности (как у препаратов): не подменять при сомнении.** Если ни порог по
  расстоянию, ни ratio-floor не пройдены — имя НЕ заменяется, оригинал сохраняется в `raw`,
  `status='unverified'`. Защищает редкие/новые показатели от ложного «исправления» в чужой анализ.
- **`status` теста несётся в `match_status`** (active/new/deprecated) — чтобы карточка могла
  пометить устаревшую позицию ФСЛИ.

## Task 9: интеграция в pipeline + сверка единиц

**TDD:** тест `test_persist_lab_normalizes_and_checks_unit` (опечатка «Глюкоэа» + неверная
единица «г/л») → RED (нет синглтона) → GREEN.

**Решения:**
- Ленивый синглтон `get_analyte_normalizer()` — точная калька `get_drug_normalizer()`. Реестр
  20720 записей читается из jsonl один раз за процесс.
- **Исходное имя не перезаписывается.** В `analyte_name` остаётся то, что прочла VLM («Глюкоэа»),
  каноника пишется в отдельную `analyte_canonical` («Глюкоза»). Принцип: распознанное и
  нормализованное — разные колонки, чтобы можно было аудировать ошибки матчинга и откатить.
- **Сверка единиц через `canonical_unit`.** Обе единицы (распознанная и эталонная из ФСЛИ)

- **Побочно починены `ref_operator`/`ref_text`:** старый `_persist_lab` их не писал в БД (хотя
  колонки и поля модели уже были) — потерянная связь из ранних задач. Теперь INSERT их сохраняет.

## Post-Task 11: смена источника сборки xlsx → JSON

Пользователь принёс ту же выгрузку ФСЛИ в JSON (`{"records": [...]}`, 20727 записей, ключи —
машинные имена колонок). Решение: **рантайм не трогаем** — `AnalyteNormalizer` в проде читает
не входную выгрузку, а собранный `registry.jsonl` (компактный, по строке на запись, ленивая
загрузка). JSON меняет только офлайн-шаг сборки.

**Что дал переход (по TDD: RED на синонимах и JSON-чтении → GREEN):**
- **Убраны засады xlsx.** Чтение через `json.loads` вместо `openpyxl` — больше нет битого
  `<dimension>` (требовавшего `read_only=False`) и двойной шапки (строка описаний). Плоский
  JSON разбирается стандартной библиотекой, детерминированно. Тема для статьи: *«тот же
  госреестр в JSON оказался надёжнее xlsx — формат выгрузки как источник хрупкости»*.
- **Починен баг разделителей синонимов.** ФСЛИ смешивает `;` и `,` в одном поле
  (`"...; APPT; aPTT, aPTT PPP, PTT"` — 771 запись). Старый split только по `;` склеивал
  хвост в один мусорный «синоним». Перешли на `re.split(r"[;,]")`: **2438 записей получили
  больше форм, +4561 синоним всего** (11177 → 15738) — это прямой прирост покрытия фаззи-матчинга.
- **Результат сборки идентичен по составу:** те же 20720 нормализованных ключей 1:1, изменения
  только в синонимах. Зависимость `openpyxl` оставлена — её ещё использует `build_drug_reference.py`
  (выгрузка ГРЛС приходит .xlsx внутри zip).

**Грабля-омоним:** антигены системы Резус `E` и `e` — два разных антигена, но `lower()` в ключе
дедупа схлопывает их в один; реестр сохраняет лишь одного «победителя» (зависит от порядка строк
в выгрузке). Дефект дедупа давний, не от смены источника, но всплыл при diff'е. Урок: регистр-
зависимые сущности в медицине существуют, агрессивная нормализация ключа может терять данные.

Итог: `uv run pytest -q` → **146 passed**, ruff чисто.

## Калибровка на живой Ollama: настоящий корень «пустого извлечения»

Прогон `sample_020.pdf` (Инвитро, 2 стр.) на живой qwen3-vl:8b показал: документ
классифицируется верно (analysis, title/clinic извлечены), но `lab_results` пуст,
`raw_extraction="[]"`. Карточка рендерит шапку и «—».

**Сначала добавили наблюдаемость** (без неё — гадание):
- Логирование в API-процессе вообще не было настроено (`basicConfig` жил только в боте),
  а pipeline крутится именно в API → `[*_EXTRACT]` в консоль не выводились. Вынесли
  `setup_logging()` (LOG_LEVEL) в общий модуль, подключили в обоих entrypoint.
- Залогировали границы: число страниц PDF и размеры рендера; число изображений и объём
  base64, уходящих в VLM; число распознанных строк; при нуле — **сырой ответ модели**
  до парсинга (`[EMPTY_EXTRACT]`).

**Что показал лог (опровергнув две гипотезы по дороге):**
- Не препроцессинг: PDF→2 изображения 1555×2200, ~1.2 МБ base64 — норма.
- Не переполнение контекста: `Prompt: 4096 t` при `num_ctx=16384` — с запасом.
- Сырой ответ — **валидный JSON со всем ОАК**, но в СВОЕЙ схеме:
  `{patient_id, ..., tests:[{test_name, results:[{parameter, value, unit, reference_range, comment}]}]}`.

**Корень — тихий рассинхрон схем.** instructor ждал `LabResults{results:[LabResult]}`
(плоско, поля `analyte_name`/`value_num`/`ref_low`). На верхнем уровне ответа ключа
`results` нет → pydantic берёт дефолт `results=[]`, лишние поля игнорируются (`extra=ignore`,
снятый в Task 3 ради устойчивости — здесь он же замаскировал проблему!) → валидация
проходит без ошибки, retry не срабатывает. Классический тихий отказ: «успех» + ноль данных.

**Фикс — адаптер под вывод модели** (вместо борьбы промптом с 8B-моделью, которая уже
проигнорировала инструкции): pydantic-схема `RawAnalysis` под фактическую вложенную
структуру + маппер `rows_from_raw` в плоский `LabResult`. Парсинг значения и нормы
перенесён из промпта в КОД (надёжнее модели): `parse_lab_value` («44.6*»→44.6, текст→
value_text), `parse_reference_range` («35 - 45»→low/high, «< 1.0»→оператор, «≤/≥»→</>,
текст→ref_text). instructor-схема теперь совпадает с естественным выводом модели — рассинхрон
снят в корне; промпт переписан под ту же структуру. Маппер проверен на реальном сыром
ответе из лога: 6/6 строк ОАК с верными значениями, единицами, нормами и флагами.

Тема для статьи: **«`extra=ignore` спасает от падений извлечения и одновременно прячет
рассинхрон схемы — наблюдаемость (сырой ответ модели в логе) важнее, чем кажется»**; и
**«с локальной 8B-VLM дешевле принять её естественный JSON и распарсить в коде, чем
заставлять следовать вашей схеме»**.

Итог: `uv run pytest -q` → **164 passed**, ruff чисто. Финальный E2E через Ollama — за
пользователем (среда разработки без GPU), логика маппинга доказана на фактическом ответе модели.

## Итерация 2: модель недетерминирована в схеме — и теряет страницы

Прогон с адаптером под именованные поля снова дал `[]`. Сырой ответ показал, почему:
**qwen3-vl:8b каждый прогон раскладывает данные по РАЗНЫМ ключам**. Прогон №1 —
английские (`tests/results/parameter/value/unit/reference_range`); прогон №2 — русские
(`Результат`/`Исследование`/`Единицы`/`Референс`) и верхний ключ — пустая строка `""`.
Данные по содержанию верные каждый раз, но имена ключей выдуманы заново. Перечислить их
все в схеме/алиасах невозможно.

**Вывод:** парсить надо по СОДЕРЖИМОМУ значений, не по именам ключей. Гибрид:
1) структурный разбор по именованным полям (быстрый путь, покрывает «послушные» ответы);
2) fallback — `harvester`: рекурсивно ищем в любом JSON массивы строк-показателей и
классифицируем поля по виду значения (число / диапазон «35 - 45» / оператор «< 1.0» /
единица) с подсказкой по алиасам ключей. Имена ключей не важны. Проверено на ОБОИХ
реальных ответах (англ. и рус.) — один и тот же результат.

**Вторая проблема, всплывшая на реальном PDF:** `sample_020.pdf` — два отдельных бланка
(стр.1 — С-реактивный белок, стр.2 — клинический анализ крови). При двух изображениях в
одном запросе модель вернула данные ТОЛЬКО со стр.2 — первая страница «потерялась». При
этом `Prompt: 4096 t` при `num_ctx=16384` — контекст НЕ переполнен; увеличивать его
бессмысленно (и медленнее). Решение — **гибридная многостраничность**: один общий вызов;
если распознанных исследований меньше, чем страниц, — добор каждой страницы отдельным
вызовом и объединение с дедупом. Платим лишними вызовами только когда модель реально
потеряла страницу.

**Заголовок документа.** «С-реактивный белок» как название всего документа — плохо.
Обобщаем по преобладающему биоматериалу (`specimen` ФСЛИ, заполнен на 100%):
Кровь/Сыворотка/Плазма → «Анализ крови», Моча → «Анализ мочи». Fallback — название
исследования из бланка → «Лабораторные анализы».

Темы для статьи: **«structured output на локальной 8B — не контракт, а лотерея имён
ключей; парсьте инвариант (содержимое значений), а не синтаксис»**; **«VLM при нескольких
изображениях молча теряет страницы — детектируй по покрытию и добирай»**; **«полнота
контекста ≠ его размер: Prompt 4096/16384 опроверг гипотезу переполнения за секунду —
если есть лог»**.

Итог итерации 2: **180 passed**, ruff чисто. Осталась калибровка скорости (`extract_long_side`)
на живой Ollama — за пользователем.

## Итерация 3: pipeline отработал, а UI завис — отладка многопроцессной доставки

Первый живой E2E через Telegram дал неожиданное: pipeline распознал документ полностью,
а бот навсегда завис на «🧩 Нурмализую данные». Классический случай, где «успех» в одном
процессе не равен «результат у пользователя».

### Сложность: бот зависает на «Нормализую данные», результат не приходит

- **Симптом:** прогресс-бар в Telegram застывает на стадии «🧩 Нормализую данные ●» и
  не превращается в карточку. При этом логи API-процесса показывают полный успех:

  ```
  [SUCCESS_EXTRACT] ... Распознано строк: 0          # общий вызов — пусто
  [MULTIPAGE] ... добор постранично
  [SUCCESS_EXTRACT] ...#стр2 ... Elapsed: 79.47s      # одна страница — 79 секунд!
  [EXTRACT_QUALITY] строк: 27 | с единицей: 27
  [NORMALIZE_QUALITY] сопоставлено ФСЛИ: 16/27
  Doc 18: заголовок обобщён → 'Анализ крови'
  Doc 18 processed                                     # статус extracted записан в БД
  ```

- **Гипотезы (три, конкурирующие):**
  - **D1** — исключение в фоновой задаче бота `asyncio.create_task(run_progress_flow(...))`:
    задача без `await` и без `done`-callback глотает любое исключение молча → поллинг
    обрывается, сообщение застывает на последнем рендере.
  - **D2** — гонка доставки: бот ловит `extracted`, но `claim_delivery()` возвращает
    `False` (push-fallback pipeline забрал доставку первым). Ветка `if claimed:` БЕЗ
    `else` → сообщение не обновляется, результат уходит отдельным «/show»-уведомлением.
    Зависит от `DELIVERY_FALLBACK_DELAY` (env, дефолт 130 с).
  - **D3** — таймаут поллинга бота (120 с) ≈ время обработки (~108 с в этом прогоне,
    раздутое 79-секундным добором стр.2). Чуть медленнее — `poll_until_done` вернёт `None`.

- **Что пробовал (по методу — сначала исключить, потом чинить):**
  - Проверил, видит ли бот свежий статус. `get_conn()` открывает **новое** соединение
    SQLite на каждый poll (`isolation_level=None`, закрывается в `finally`) → коммиты
    API-процесса видны сразу. Гипотеза «бот читает устаревший статус» — **отпала**.
  - Проверил рендер карточки. `_format_labs`/`format_card_header` обращаются к полям
    через `.get()` — на данных Doc 18 (значения вида «44.6\*», 11 нераспознанных) не
    бросают. Гипотеза «падает форматирование» — **ослаблена**.
  - Полез в логи бота — и нашёл, **почему их нет**: логгер модуля назывался
    `logging.getLogger("bot.upload")` — вне дерева `botkin`. А `setup_logging()`
    конфигурирует только логгер `botkin` (`logger.propagate = False`). Итог: весь путь
    доставки писал в ненастроенный логгер → **полная немота**. Дважды слепы: и кода
    логирования не было, и тот, что был, не выводился.

- **Решение (этой итерации — инструментирование, не фикс вслепую):** по методике
  систематической отладки в многокомпонентной системе — сперва добавить наблюдаемость на
  границе, прогнать раз, увидеть, ГДЕ рвётся. Конкретно:
  - имя логгера → `botkin.bot.upload`;
  - `poll_until_done`: маркеры `[POLL_START]/[POLL_STAGE]/[POLL_DONE]/[POLL_TIMEOUT]`;
  - `run_progress_flow` обёрнут в `try/except` с `log.exception` (`[FLOW_ERROR]` — ловит
    D1) + маркеры `[FLOW_FINAL]/[FLOW_CLAIM]/[FLOW_CARD]/[FLOW_LOST_RACE]` (D2);
  - `_edit`: `[EDIT_FAIL]` отделён от шумного «message is not modified».

  Маркеры спроектированы так, чтобы один прогон **развёл три гипотезы**: `[FLOW_LOST_RACE]`
  → D2, `[POLL_TIMEOUT]` → D3, `[FLOW_ERROR]` → D1.

- **Урок:** в системе из двух процессов на общей SQLite «`Doc processed`» в логе одного
  процесса не значит «доставлено». И самое коварное — **слепое пятно наблюдаемости**:
  неправильное имя логгера спрятало весь слой. Прежде чем чинить, убедись, что вообще
  ВИДИШЬ компонент. Темы для статьи: **«цена одной буквы в имени логгера»**; **«fan-in
  доставки: poll бота против push pipeline — кто claim'нул, тот и показал, а проигравший
  обязан не молчать (ветка без `else` = немое зависание)»**.

### Разрешение по логам: подтверждён D3 (+ деградация extract на бэкенде)

Один прогон с маркерами развёл гипотезы однозначно:

```
[POLL_STAGE] Doc 20 | стадия='normalizing' | 12.2s
[POLL_TIMEOUT] Doc 20 | таймаут 120.0s | опросов=60 | последняя стадия='normalizing'
[FLOW_FINAL] Doc 20 | final=None
```

Ни `[FLOW_ERROR]` (D1 исключён), ни `[FLOW_LOST_RACE]` (D2 исключён) — чистый **D3**:
бот сдаётся по таймауту 120 с, документ всё ещё в `normalizing`. Корень — на бэкенде:

```
[FAILED_EXTRACT] ...#стр2 | Elapsed: 207.48s | Error: Invalid JSON: EOF while parsing a list
```

Постраничный добор стр.2 шёл **207 с** и вернул оборванный JSON (модель генерила дубли до
упора `num_predict`, список не закрылся) → `ExtractionError` → статус `failed`. Бот к этому
моменту уже две минуты как отвалился. Урок: **таймаут UI должен превышать реальный потолок
обработки, а сама обработка — иметь свой потолок (timeout на VLM-вызов + защита от
генерации-мусора), иначе UI и бэкенд расходятся в разные стороны.**

### Сложность: TelegramBadRequest «can't parse entities» — `<` из нормы рушит /show

- **Симптом:** при `/show` и листании (`browse`) бот падает, результат не показывается:

  ```
  TelegramBadRequest: Bad Request: can't parse entities:
    Unsupported start tag "1.0)" at byte offset 2171
    File "show.py", line 32, in cmd_show
  ```

- **Корень:** `parse_mode=HTML` + референс **«< 1.0»** (базофилы). `_format_labs` экранирует
  имя/значение/единицу через `html.escape`, но **не `ref`** — `_format_ref` вставляет
  литералы `<`/`>` оператора нормы и свободный `ref_text`. Telegram читает `<1.0` как
  открывающий тег → отказ парсинга. Баг скрыт ровно на тех анализах, где норма
  односторонняя — а это частый случай (базофилы, СРБ, онкомаркеры).

- **Решение (TDD):** `_format_ref` оставлен текстовым helper'ом (его контракт — чистый
  текст, легко тестировать), экранирование сделано **на границе HTML** в `_format_labs`:

  ```python
  ref = _format_ref(r)
  ref = f" ({html.escape(ref)})" if ref else ""
  ```

  `html.escape("норма <1.0")` → `норма &lt;1.0` — Telegram показывает «< 1.0». Заодно
  закрылся и свободный `ref_text` от модели (defense-in-depth). Тест `test_show_labs.py`
  до фикса закреплял баг (`assert "<5.0" in out`) — исправлен на `&lt;5.0` + добавлен
  `test_ref_operator_html_escaped` (нет сырого `<1.0`, есть `&lt;1.0`). Остальные пути
  (`doc_title`, `clinic`, doctor-reports) уже экранированы — проверено.

- **Урок:** при ручной сборке HTML-сообщений экранировать надо **каждую** вставку
  переменных, а не только «очевидные». Один неэкранированный путь = краш на реальных
  данных. Тема для статьи: **«parse_mode=HTML и пользовательские данные: где `html.escape`,
  а где забыли — и почему тест, закрепляющий сырой `<`, маскировал баг»**.

### repro бага «< 1.0» (отдельно от доставки)

1. Любой сохранённый анализ с односторонней нормой (оператор `<`/`>` — напр. базофилы «< 1.0»).
2. Вызвать `/show` или листать карточки (`browse`) → `TelegramBadRequest: can't parse entities`.
3. Фикс закрыт коммитом ниже; проверка — `pytest tests/test_show_labs.py`.

Итог итерации 3: **D3 подтверждён фактом** (таймаут UI < время обработки; extract стр.2
деградирует до 207 с и невалидного JSON). Попутно найден и **исправлен** независимый баг
HTML-экранирования нормы (`<` рушил `/show`). Тесты **183 passed**, ruff чисто.
Коммиты: `64b25bb` (наблюдаемость), фикс HTML — следующим. Осталось по D3: поднять/увязать

## Итерация 4: лечим D3 послойно — extract не должен ронять документ, UI не должен сдаваться раньше бэкенда

Логи дали точный диагноз, и оказалось, что «зависание» — это сцепка четырёх дефектов в
двух процессах. Чинили каждый по TDD (RED → GREEN), от корня к UX.

### Сложность: одна деградировавшая страница убивала весь документ

- **Симптом:** общий вызов дал 6 строк (harvester), стр.1 — 1 строку, но стр.2 ушла в
  генерацию дублей на 207 с и вернула оборванный JSON → `ExtractionError`. Это исключение
  всплыло из цикла добора в `run_analysis` → `orchestrator` → статус `failed`. **Всё
  потеряно**, хотя 7 строк уже были извлечены.

- **Решение (фикс 1а, толерантность добора):** цикл постраничного добора оборачиваем в
  `try/except ExtractionError` — сбой страницы логируется (`[MULTIPAGE_PAGE_FAILED]`) и
  пропускается, уже собранные строки сохраняются. Тот же приём защищает и общий вызов:
  при его падении `rows=[], n_tables=0` → добор постранично ещё может спасти данные.

- **Урок:** в пайплайне «общий проход + добор частей» сбой ОДНОЙ части — ожидаемое
  событие, а не катастрофа. Изоляция сбоя на уровне части = частичный результат вместо
  полного провала.

### Сложность: модель генерит дубли до потолка и обрывает JSON

- **Симптом:** в сыром ответе MCV/MCH/MCHC/RDW повторяются по 2–3 раза; список раздувается
  до `num_predict` (8192), генерация не успевает закрыться → `EOF while parsing a list`.

- **Решение — три слоя защиты:**
  - **Фикс 3 (дедуп):** `_dedup_rows` схлопывает одинаковые `(имя, value_num, value_text)`
    на выходе `rows_from_raw` и `harvest_lab_rows` — повторы не доходят до БД и метрик.
  - **Фикс 2 (timeout VLM):** `get_raw_client` имел дефолт `timeout=600 с` — оттого вызов
    и висел 207 с. Ввели `VLM_REQUEST_TIMEOUT` (env, дефолт 120 с): деградировавший вызов
    прерывается, страница пропускается (фикс 1а), документ сохраняет остальное.
  - **Фикс 1б (salvage обрезанного JSON):** когда instructor падает на невалидном JSON,
    сырой текст последнего ответа достаётся из `InstructorRetryException.last_completion`
    и кладётся в `ExtractionError.raw_text`. `_salvage_json_objects` сканирует текст по
    балансу фигурных скобок (с учётом строк/escape) и вытаскивает все **полные**
    объекты-строки до точки обрыва → harvester собирает из них показатели
    (`[EXTRACT_SALVAGED]`). Полный массив невалиден, но первые N объектов — валидны.

- **Урок:** с локальной 8B-VLM «невалидный ответ» — норма, и относиться к нему надо как
  к потоку, который может оборваться в любой момент: парсить инкрементально, спасать
  префикс. Темы для статьи: **«три уровня обороны от генерации-мусора: дедуп → таймаут →
  salvage префикса»**; **«как достать сырой ответ из исключения instructor и зачем»**.

### Сложность: UI сдавался раньше бэкенда (корень D3)

- **Симптом:** `poll timeout` бота — хардкод 120 с, а обработка с постраничным добором
  легко переваливает за это. Бот возвращал `None` → «Обработка затянулась», пока бэкенд
  ещё работал (или падал) — два процесса жили по разным часам.

- **Решение (фикс 4):** `BOT_PROGRESS_TIMEOUT` (env), **увязан с потолком бэкенда** —
  дефолт `30 + 3 × VLM_REQUEST_TIMEOUT` (classify + общий + добор). Снизишь таймаут
  VLM — синхронно сожмётся и ожидание UI. `run_progress_flow` передаёт его в
  `poll_until_done`.

- **Урок:** таймауты связанных процессов нельзя задавать независимыми константами — у
  ведомого (UI) потолок должен **выводиться** из потолка ведущего (бэкенд), иначе они
  неизбежно разойдутся. Тема: **«согласованные таймауты: одна константа-источник вместо
  двух магических чисел»**.

### repro D3 после фиксов (ожидаемое поведение)

3. Бот ждёт до `BOT_PROGRESS_TIMEOUT` (≈390 с при дефолте) и показывает карточку.

Открыто для следующего живого прогона: подтвердить на реальной Ollama, что стр.2 теперь
либо извлекается, либо корректно деградирует без потери документа.

### Разрешение по живому прогону (Doc 21): доставка работает, вскрылось качество

Прогон подтвердил фиксы доставки фактом: `[POLL_START] timeout=390s` →
`[POLL_DONE] terminal='extracted' | 112.8s` → `[FLOW_CLAIM] claimed=True` →
`[FLOW_CARD] карточка показана`. Бот дождался (раньше сдавался на 120 с), карточка
отрисовалась, HTML-норма «<1.0» корректна. Salvage/timeout не активировались — стр.2
уложилась в 57.8 с с валидным JSON. **Баг A и D3 закрыты.**

Но карточка обнажила два бага уровнем глубже — недетерминизм модели и матчинг справочника:

- **Баг C — дубли с противоречивыми значениями между общим вызовом и добором.** Итог 38
  строк вместо ~21. Общий вызов harvester'ом собрал ВЕСЬ документ (21 строка: СРБ + ОАК),
  но добор постранично всё равно запустился (критерий «неполно»: `таблиц=1 < страниц=2`
  ложно сработал — harvester склеил обе страницы в одну таблицу). Хуже: на втором проходе
  модель выдала ДРУГИЕ числа (Гемоглобин «13.7 г/дл» в общем vs «143 г/л» на стр.2;
  Гематокрит 40.8 vs 42) — `_dedup_rows` по `(имя, value_num)` их не схлопнул, т.к.
  значения разные. Корень: критерий неполноты завязан на число таблиц, а не на покрытие;
  + недетерминизм значений модели между проходами.

- **Баг D — матчинг ФСЛИ подставляет неверный биоматериал/показатель (клинически опасно).**
  rapidfuzz берёт лучшее совпадение по названию, игнорируя биоматериал, а в ФСЛИ сотни
  вариантов одного теста: «Эритроциты» → «…в цереброспinальной жидкости»; «Гемоглобин» →
  «…в моче тест-полоской»; «C-реактивный белок» → «…в плевральной жидкости»; «Тромбоциты»
  → «**CD31+ клетки**». Для медданных это недопустимо: подмена крови на ликвор/мочу. Корень:
  нормализатор не фильтрует кандидатов по биоматериалу документа и дописывает метод/локус,
  которого в исходнике нет.

Темы для статьи: **«дедуп недостаточен, когда модель недетерминирована в ЗНАЧЕНИЯХ, а не
только в ключах — нужен критерий покрытия, а не повторный проход вслепую»**; **«fuzzy-матчинг
по медицинскому справочнику без фильтра по биоматериалу — генератор клинически опасных
подмен»**.

Итог: баги доставки закрыты, качество извлечения/нормализации — новый скоуп (баги C, D).

## Итерация 5: баг D — справочник правит опечатки, но не подмешивает биоматериал

Карточка показывала «Гемоглобин, массовая концентрация **в моче** с помощью тест-полоски»,
хотя в PDF — просто «Гемоглобин». Нормализатор клал в `canonical` поле `FULLNAME` из ФСЛИ
(с биоматериалом/методом), а fuzzy-матч выбирал произвольную specimen-запись из десятков.

### Сложность: fuzzy по ФСЛИ дописывает локус, которого нет в документе

- **Симптом:** «Эритроциты» → «…в цереброспинальной жидкости», «Тромбоциты» → «CD31+клетки»,
  + россыпь ложных ⚠️ (единица бралась из чужой specimen-записи: 1/мкл вместо ×10⁹/л).

- **Решение (по требованию: справочник — для опечаток и единиц, не для подмешивания):**
  - **Дедуп-таблица по `ANALYTE`.** Справочник свёрнут с 20720 specimen/метод-записей до
    **6211 показателей**: одна запись на показатель — чистое имя (`ANALYTE`, инвариант к
    биоматериалу), объединённые синонимы (`SHORTNAME`+`ENGLISHNAME`+`SYNONYMS`) и набор
    допустимых единиц (`UNIT`, расщеплённый по ';'/','). `FULLNAME`/`SPECIMEN` не храним.
  - **`canonical` = `ANALYTE`**, не `FULLNAME`. Подмешивание биоматериала исчезает в корне:
    «Гемоглобин»→«Гемоглобин», «Эритроциты»→«Эритроциты», «Гематкрит»→«Гематокрит» (опечатка
    исправлена), при неуверенном матче (MCV) — имя из документа.
  - **Единицы — из документа.** `unit_mismatch` сверяет распознанную единицу с НАБОРОМ
    допустимых (а не одной из случайной записи) → ложные ⚠️ уходят.
  - **Приоритет канонического имени над чужим синонимом.** «тромбоциты» — синоним записи
    «CD31+клетки», и при сборке ключей он «крал» показатель «Тромбоциты». Двухпроходная
    загрузка (сначала имена, потом синонимы на свободные ключи) → «Тромбоциты»→«Тромбоциты».
  - **Заголовок документа — по группе ФСЛИ** (биоматериал убрали): «Гематологические
    исследования» вместо «Анализ крови».

- **Урок:** медицинский справочник нельзя использовать как «обогатитель» — только как
  корректор. Разворачивать `FULLNAME` с биоматериалом = выдумывать данные, которых нет в
  исходнике. Правильный гранулярность — `ANALYTE` (показатель), а локус/метод/биоматериал
  принадлежат конкретному измерению, а не справочной норме. И: точное каноническое имя
  всегда должно бить чужой синоним. Темы для статьи: **«справочник-корректор vs
  справочник-обогатитель: почему второе для медданных опасно»**; **«дедуп 20k→6k: одна
  сущность-показатель вместо декартова произведения биоматериал×метод»**.

### Остаточные хвосты (точность матча, отложено)

- «Базофилы, %» → «Базофилы; Лейкоциты» — составное `ANALYTE`-имя в самой ФСЛИ (не подмена
  показателя, а кривое каноническое имя справочника).
- Полноценный фильтр кандидатов по контексту/специфике и баг C (дубли с расхождением значений
  между общим вызовом и постраничным добором) — отдельным шагом.

Итог итерации 5: подмешивание биоматериала устранено, опечатки названий правятся, ложные ⚠️
убраны, «Тромбоциты» больше не «CD31+клетки». Реестр пересобран (6211). **192 passed**, ruff чисто.

## Итерация 6: баг C — дубли с противоречивыми значениями между проходами

На Doc 21 карточка содержала **38 строк вместо ~21**: каждый показатель ОАК продублирован
с разными числами (Гемоглобин «13.7 г/дл» и «143 г/л»).

### Сложность: общий вызов + постраничный добор плодят конфликтующие дубли

- **Симптом:** общий вызов harvester'ом собрал весь документ (21 строка), но добор всё
  равно запустился (критерий «неполно» `таблиц=1 < страниц=2` ложно сработал — harvester
  склеивает страницы в одну таблицу). На втором проходе модель выдала ДРУГИЕ числа для тех
  же показателей. Слияние `_merge_dedup` по ключу `(имя, значение)` не схлопывало их —
  значения-то разные → 38 строк.

- **Решение:** слияние проходов **по имени показателя** (нормализованному), а не по
  `(имя, значение)`. Повторный показатель отбрасываем — доверяем первому (общему) проходу;
  добавляем только реально новые показатели (с потерянной страницы). Дубли с противоречием
  исчезают, добор по-прежнему спасает недостающее.

- **Урок:** при дедупликации недетерминированного источника ключ должен опираться на
  СТАБИЛЬНЫЙ инвариант (имя показателя), а не на то, что плавает между прогонами (значение).
  Иначе «защита от дублей» пропускает ровно те дубли, что опаснее всего — с расхождением.

Замечание о скорости: критерий запуска добора (`таблиц < страниц`) всё ещё срабатывает
ложно и тратит лишние VLM-вызовы, но благодаря дедупу-по-имени они безвредны для
корректности (дубли отбрасываются). Оптимизация критерия — в задаче про скорость.

Итог итерации 6: дубли с противоречивыми значениями устранены (38→~21). **194 passed**, ruff чисто.

## Итерация 7: точность матча — квалификаторы имени сбивали fuzzy

После фикса D подмешивание ушло, но часть показателей ОАК матчилась криво: «Базофилы, %» →
«Базофилы; Лейкоциты», «Нейтрофилы (общ.число), %» → ничего.

### Сложность: «, %» и «(...)» уводят fuzzy на мусорную составную запись

- **Симптом (с цифрами):** `DL("базофилы, %", "базофилы") = 3`, но у мусорной составной
  записи «Базофилы; Лейкоциты» нашёлся синоним на `DL = 1` — и он победил точное «Базофилы».
  «Нейтрофилы (общ.число), %» вообще уходило за порог в `unverified`. Корень: модель
  дописывает к названию квалификаторы (`, %`, `, абс.`, `(общ.число)`), раздувая дистанцию.

- **Решение:** перед матчем отсекаем скобочные пояснения и хвосты `, %` / `, абс.` / `, отн.`.
  «Базофилы, %» → «базофилы» → точное совпадение (`dist 0`) бьёт чужой синоним. Защита от
  регрессии: если в остатке лишь аббревиатура (≤3 символов, «MCV»), откатываемся к оригиналу
  — голый «mcv» в ФСЛИ ошибочно числится синонимом составной записи, поэтому честнее
  оставить `unverified` (карточка покажет имя из документа), чем подставить мусор.

- **Урок:** нормализуй ЗАПРОС, а не только справочник. Модель и бланки добавляют шум
  (`, %`, единицы, пояснения), который для fuzzy неотличим от части имени. И: понижение
  «уверенности до нуля» (unverified) — валидный исход; лучше показать сырое имя, чем уверенно
  подставить неправильное. Тема для статьи: **«fuzzy по медсправочнику: чистить вход важнее,
  чем тюнить порог; а аббревиатуры — отдельный класс риска (3 буквы матчат что угодно)»**.

Итог итерации 7: показатели ОАК с квалификаторами матчатся чисто (Базофилы/Нейтрофилы/
Эозинофилы/Лимфоциты/Моноциты «, %»/«, абс.»), аббревиатуры безопасно остаются сырыми.
**198 passed**, ruff чисто.

### UX: нумерованный список показателей в карточке

Маркеры-точки `•` заменены на нумерацию `1. 2. 3. …` — длинный список (20+ строк ОАК)
удобнее читать и ссылаться на позицию. Счётчик идёт по реально показанным строкам
(строки без значения пропускаются). **200 passed**.

### Сложность: составные имена ФСЛИ коверкали матч (Doc 22)

- **Симптом:** «Albumin» → «Альбумин; креатинин» (вместо чистого «Альбумин»). В ФСЛИ
  **287 записей** с `;` — несколько аналитов в одной строке; их синонимы перехватывали
  матч у чистых показателей.
- **Решение:** при сборке таблицы пропускаем ANALYTE с `;`. Чистые отдельные показатели
  («Альбумин», «Креатинин», «Базофилы») их покрывают; реестр 6211→**5924**. «Albumin»
  теперь честно `unverified` (сырое имя из документа), а не подменённое мусорное.
- **Урок:** лучше показать нераспознанное имя как есть, чем «уверенно» подставить составной
  мусор из справочника. `unverified` — не провал, а честность.

> Важно (Doc 22 показал границы): бóльшая часть искажений в этом прогоне — НЕ код, а сама
> модель. qwen3-vl вернула выдуманную англоязычную биохимическую панель (Total Protein,
> Globulins, BUN, Creatinine), которой нет в PDF (там СРБ + ОАК), и деградировала на стр.2
> (160 с, 0.3 tok/s, пустой ответ) → ОАК потерян. `VLM_REQUEST_TIMEOUT=120` не прервал —
> медленный стрим сбрасывает read-timeout на каждый токен. Открытые темы: общий (total)
> таймаут запроса; борьба с галлюцинациями/языком через промпт. Это качество модели, не
> регрессия конвейера — тот же файл на Doc 21 дал корректный русский ОАК.

Итог: составные имена убраны (5924), матч чистых показателей корректен. **201 passed**, ruff чисто.

## Итерация 8: промпт против галлюцинаций + постраничное извлечение (скорость)

Doc 22 показал две системные проблемы: модель выдумывает данные и конвейер читает страницы
дважды.

### Промпт против галлюцинаций

В `ANALYSIS_VLM_SYSTEM` добавлены жёсткие правила: извлекать ТОЛЬКО видимое на изображении
(не добавлять показатели «по памяти»/из типичных панелей); сохранять ЯЗЫК документа (не
переводить «Гемоглобин»→«Hemoglobin»); не добавлять лишние поля (timestamp, статус) и свои
интерпретации. Эффект проверяется на живой Ollama (промпт — не юнит-тестируемая логика).

### Скорость: постраничное извлечение вместо «общий вызов + добор»

- **Было:** общий VLM-вызов по ВСЕМ страницам, затем (почти всегда) добор каждой страницы
  отдельно. Для N-страничного документа контент читался дважды — общим проходом и добором.
  На Doc 22: общий (27 с, обе страницы) + стр.1 (8 с) + стр.2 (160 с). Лишний проход и
  смешивание страниц.
- **Стало:** для N>1 страниц — сразу постранично, каждая страница ровно один раз, без общего
  вызова. Одностраничные — один вызов как прежде. Сбой страницы не валит документ; результаты
  объединяются дедупом по имени. Минус один полный проход по всем страницам.
- **Урок:** «общий вызол + докрутка частей» удобен в теории, но если докрутка срабатывает
  почти всегда — это просто двойная работа. Когда модель за один кадр стабильно видит лишь
  одну таблицу — честнее сразу кормить по одной странице, чем читать всё дважды.

Итог итерации 8: промпт ужесточён против выдумывания/перевода; многостраничные читаются
постранично (нет двойного чтения). **203 passed**, ruff чисто. Эффект на галлюцинации —
за живым прогоном.

## Итерация 9: извлечение из текстового слоя PDF

### Проблема

На живом `sample_020.pdf` (цифровой бланк ИНВИТРО, 2 страницы) VLM-over-image давала три
класса дефектов:

1. **Галлюцинация-нормализация значений.** Гемоглобин в документе `13.7 г/дл, реф 11.7–15.5`
   модель вернула как `137 г/л, реф 120–160`. Сырой ответ VLM в логе уже содержал подменённые
   числа — значит подмена рождается ВНУТРИ VLM-вызова, не в постобработке.
2. **Неполнота.** Из 21 показателя (СРБ + 20 ОАК) извлекалось 14; терялись Базофилы %, весь
   блок «абс.» (5 показателей) и СОЭ — модель обрывала длинную таблицу около 13-й строки.
3. **Обрыв значения.** Последняя строка обрезалась: Эозинофилы → `value_raw "3. "` вместо `3.1`.

Подбор параметров (`temp=0.3`, `repeat_penalty=1.2`, `num_predict=16384`) на одном прогоне
убрал галлюцинацию Гемоглобина, но недетерминированно («обычно верно», не «верно») и не
вылечил неполноту (14/21) и обрыв.

### Диагноз

Цифровой PDF несёт ТОЧНЫЙ текстовый слой: значения дословно, с десятичными, правильными
единицами `г/дл` и правильными референсами. Пайплайн его игнорировал — `get_text()` нигде не
было, `pymupdf` использовался только для рендера в картинки. Мы выбрасывали готовый эталон и
заменяли его галлюцинацией маленькой VLM на пикселях.

### Решение

Для PDF с годным текстовым слоем извлекаем из текста, не из картинки. Источник цифр меняется
с «угадал по пикселям» на «переписал из точного текста»:

- **Реконструкция строк** (`preprocess/pdf_text.py`, детерминированно, без модели): слова
  `get_text("words")` кластеризуются по координате Y с толеранцией 3pt. Нюанс: значение часто
  сидит на 1px ниже имени показателя — наивное округление Y разрывало бы строку.
- **Структурирование** (qwen3-vl text-only, `temp=0`): размечает координатные строки по
  колонкам. Цифры лежат в контексте модели как ТОКЕНЫ — угадывать пиксели не нужно, жадное
  декодирование не залипает на заученной «канонической» норме.
- **Verbatim-страж:** каждое число ответа (значение + границы референса) обязано быть
  подстрокой исходного текста; иначе строка бракуется. Эта проверка невозможна при картинке
  на входе. Нормализует запятую→точку и хвостовой `.0` (`4,64`==`4.64`, `35.0`==`35`).
- **Гейт фолбэка:** слоя нет / 0 строк / >50% выбраковки → текущий VLM-over-image. Один путь
  на документ, без смешивания источников.

Почему модель, а не шаблонный парсер: разные лаборатории имеют разные раскладки колонок,
шаблон не генерализуется. Геометрический детектор `pymupdf.find_tables()` на ИНВИТРО (нет
линий таблицы) выделил лишь 3 строки — тоже непригоден.

### Метрики

| Метрика | VLM-over-image | Текстовый слой |
|---|---|---|
| Полнота | 14/21 (67%) | цель 21/21 (100%) |
| Точность значения | Гемоглобин `137 г/л 120-160` ❌ | `13.7 г/дл 11.7-15.5` ✅ |
| Обрыв строк | Эозинофилы `"3. "` | `3.1` целиком |
| Детерминизм | нет (`temp=0.3`) | да (`temp=0`, текст) |
| Латентность extract | ~30–200 с (деградация до 0.3 tok/s) | <1 с реконструкция + 1 малый text-вызов |
| Стоимость | 2 image-вызова (~1.2 МБ b64) | 1 text-вызов (малый промпт) |

**Доказано офлайн** (без модели): `has_usable_text_layer(sample_020.pdf)=True`; реконструкция
дала 67 физических строк; строка Гемоглобина — ровно `Гемоглобин 13.7 г/дл 11.7 - 15.5`, то
есть точные данные, которые VLM подменяла. Структурирование, verbatim-страж, гейт и фолбэк
покрыты юнит-тестами. End-to-end на живой Ollama (финальный счёт 21/21 + проверка детерминизма

## Итерация 10: ложные ⚠️ unit_mismatch — единицы документа и реестра не сходились к канону

### Проблема

E2E-прогон на живой Ollama (sample_020.pdf, текстовый слой) дал верные значения — Гемоглобин
`13.7 г/дл 11.7–15.5`, как и ожидалось от итерации 9. Но восемь строк ОАК получили ложный
флаг ⚠️ `unit_mismatch`: Эритроциты `×10¹²/л`, Тромбоциты/Лейкоциты и все пять абсолютных
показателей лейкоформулы `×10⁹/л`. Единицы корректные — флаг ложный.

Хендофф из прошлой сессии диагностировал это как «реестр ждёт не те единицы» (Лейкоциты — `%`,
Тромбоциты — `1/поле зр.`, Эритроциты — `1/мкл»). **Диагноз оказался неверным.**

### Диагноз (по методике systematic-debugging — корень до фиксов)

Проинструментировали всю цепочку сверки на границах компонентов. Для каждой строки печатали:
что вернул `normalizer.correct()` (canonical, expected_units, status) и что вернул
`canonical_unit()` для единицы документа. Ключевое наблюдение — одна и та же единица в двух
нотациях вела себя по-разному:

- `10^12/л` (ASCII) → `unit_mismatch=0` ✅
- `×10¹²/л` (Unicode, знак × + надстрочные) → `unit_mismatch=1` ❌

при **идентичном** `expected_units`. Значит реестр ни при чём — `10^9/л`, `10^12/л` в наборе
ожидаемых единиц есть. Ломалась канонизация: документная Unicode-форма `×10⁹/л` и реестровая
ASCII-форма `10^9/л` не сводились к одному канону, поэтому сверка `unit ∈ expected_units`
давала промах. Два дефекта в `canonical_unit`:

1. Ключ алиаса был записан латинской `l` (`"10^9/l"`), а и реестр, и документы используют
   кириллическую `л` — алиас почти никогда не срабатывал на русских данных.
2. Надстрочные Unicode-цифры (`⁰¹²³⁴⁵⁶⁷⁸⁹`) вообще не сворачивались — `10⁹/л` не приводилось
   к `10^9/л`.

Корень был во входе сверки (две несведённые нотации одной единицы), а не в данных реестра —
ровно как в итерации 9 корень был во входе модели (пиксели vs текст), а не в промпте.

### Решение (TDD)

- RED: `canonical_unit("10^9/л") == "×10⁹/л"` (падал — возвращал `10^9/л` as-is).
- GREEN: добавили кириллические ASCII-ключи `10^9/л`, `10^12/л` в `reference/units.py`.
- RED: `canonical_unit("10⁹/л") == "×10⁹/л"` (надстрочные без знака ×).
- GREEN: `_fold_superscripts` в `normalize/units.py` — алгоритмическое сворачивание надстрочных
  цифр в `^N` внутри `_key`, чтобы устойчиво, а не ручными алиасами.

После фикса все восемь строк → `unit_mismatch=0`.

Итог итерации 10: ложные ⚠️ устранены на корневом уровне; канонизация устойчива к Unicode-
и ASCII-нотации степеней. **216 passed**, ruff чисто.

## Итерация 11: мусорный заголовок ОАК — группа ФСЛИ ≠ тип бланка

### Проблема

Документ ОАК (sample_020) получал заголовок «🧪 Химико-микроскопические исследования» вместо
клинического «Общий анализ крови». Заголовок формирует `summary_title` голосованием по группе
ФСЛИ показателей (`most_common`).

### Диагноз (systematic-debugging — корень до фиксов)

Проинструментировали `normalizer.correct()` для 15 показателей ОАК. Группы разошлись:

| group ФСЛИ | показатели |
|---|---|
| Химико-микроскопические исследования | Гемоглобин, Эритроциты, Лейкоциты, Нейтрофилы, Лимфоциты, Моноциты, Эозинофилы, Базофилы |
| Гематологические исследования | Гематокрит, Тромбоциты, MCHC |
| None | MCV, RDW, MCH, СОЭ |

Голосование: химмикро 8 против гематологии 3 → мусорный заголовок.

Проверили гипотезу «многозначность имени» — по точному `name` в реестре **ровно одна** запись
на показатель, и у Гемоглобина/Эритроцитов/Лейкоцитов она помечена «Химико-микроскопическими».
То есть это не коллизия ключей: **реестр ФСЛИ группирует по разделу номенклатуры (методу),
а не по типу бланка** — Гемоглобин определяется и в моче/кале, поэтому лежит в химмикро.

Корень: клиническую группу документа задаёт **состав панели**, а не ФСЛИ-группа отдельного
показателя. Та же природа, что в итерациях 9–10 (проблема во входе, не в обработке): здесь
вход — разнородная номенклатурная группировка, непригодная как «тип исследования».

Замечание: MCHC матчится на canonical «Средняя концентрация гемоглобина в ретикулоците»
(отдельный баг, итерация на будущее) — но это не помешало, т.к. группу проставляем по
raw-имени строки, а не по canonical.

### Решение (TDD)

Детектор панели по составу, а не доверие per-analyte ФСЛИ-группе:

- `is_cbc_panel(names)` — ОАК, если присутствует ≥3 показателя из ядра
  {гемоглобин, эритроциты, лейкоциты, тромбоциты, гематокрит}.
- `is_cbc_analyte(name)` — принадлежность полному набору ОАК (ядро + MCV/MCH/MCHC/RDW/MPV/
  лейкоформула/СОЭ/ретикулоциты), имя чистится `_strip_qualifiers` («MCHC (…)» → «mchc»).
- `summary_title`: панель ОАК приоритетнее голосования по группам → заголовок «Общий анализ крови».
- `orchestrator._persist_lab`: при опознанной панели каждой ОАК-строке проставляется
  `analyte_group = «Гематологические исследования»` (чинит и бывшие `None`, и химмикро-мусор).

Порог 3 защищает от ложного срабатывания: биохимия с единичным «Гемоглобин гликированный»
не опознаётся как ОАК (тест `test_summary_title_not_cbc_for_unrelated_panel`).

После фикса на реальном реестре: заголовок «Общий анализ крови», все 15 строк → гематология.

Итог итерации 11: тип исследования определяется составом панели, а не номенклатурной группой
отдельного показателя. **221 passed** (+5 тестов), ruff чисто.

## Итерация 12: потеря одиночного показателя — единый LLM-вызов по всем страницам

### Проблема

Тот же `sample_020.pdf` (Инвитро, 2 страницы) на выходе давал только панель ОАК (20 строк
со стр.2). **С-реактивный белок (1.8 мг/л, норма <5.0) со стр.1 терялся** — пользователь
заметил «не хватает одного анализа». СРБ — единственный показатель на стр.1, без заголовка
исследования над ним; стр.2 — таблица ОАК (21 строка-результат) с заголовком «Клинический
анализ крови».

### Диагноз (systematic-debugging — трассировка потока данных, корень до фиксов)

Ollama в dev-среде нет (на машине с RTX 3080), живой прогон невозможен — диагноз строили на
детерминированных кусках. Прошли каждый шаг ПОСЛЕ извлечения и доказали, что **ни один из них
не теряет СРБ**:

| Шаг | Теряет СРБ? | Доказательство |
|---|---|---|
| `reconstruct_lines` | нет | строка `'С-реактивный белок 1.8 мг/л <5.0'` присутствует (стр.1) |
| `_verbatim_guard` | нет | прогон: СРБ в `kept`, `rejected` пуст (числа 1.8 и 5.0 есть в source) |
| `parse_reference_range("<5.0")` | нет | → `(None, 5.0, '<', None)` |
| `_dedup_rows`/`_persist_lab`/render | нет | сохраняют **все** строки без фильтрации |

Вывод по исключению: СРБ отсутствует только потому, что его не вернул `_structure_text` —
единственный недетерминированный (LLM) шаг.

Корень — два уровня:

1. **Проксимальный.** Текстовый путь сваливал строки **всех** страниц в **ОДИН** LLM-вызов
   (`reconstruct_lines` → `_structure_text`). Одинокий СРБ на стр.1 тонул на фоне доминирующей
   21-строчной таблицы ОАК. Это ровно та проблема, которую **VLM-путь уже решил** переходом на
   постраничные вызовы (итерация 8, комментарий в `run_analysis`: «общий вызов по всем
   страницам → модель смешивала/теряла содержимое»). Текстовый путь это улучшение не получил.
2. **Архитектурный.** В пайплайне был **анти-галлюцинационный** страж (`_verbatim_guard`:
   каждое число ответа обязано быть в источнике), но **не было анти-пропускного** — что каждая
   строка-результат источника обязана дать строку в ответе. Страж односторонний: пропуск
   никто не ловил.

### Решение (TDD, выбран самый робастный вариант — обе защиты)

**(1) Постранично.** `reconstruct_pages(path) -> list[list[str]]` (строки по страницам);
`reconstruct_lines` стал плоской склейкой. `_extract_from_text_layer` идёт постранично:
отдельный `_structure_text` на страницу + `_merge_dedup`. Зеркалит VLM-путь.

**(2) `completeness_guard(lines, rows)`** — анти-пропускной аналог verbatim:
- `_parse_text_line(line)` детерминированно парсит чистую строку слоя. Гейт строки-результата
  строгий: имя (есть буква) + **чистый числовой токен-значение** + **токен референса**
  (`<x` / `a - b`). Это отсекает шапку/подвал.
- Покрытие считаем **по значению показателя, а не по имени** (имена от LLM и от парсера
  расходятся; значение — стабильный якорь) → не плодим ложные дубли. Недобор при коллизии
  значений безопаснее ложного добора.

Гейт проверен на реальных строках стр.1: из 19 строк (имя пациента, возраст, даты,
телефон `8-800-200-363-0`, «Исполнитель…», обрывок примечания «превышает 6%») страж добрал
**ровно одну** — СРБ. Ключевые отсевы:
- `превышает 6%` → значение склеено с единицей (`6%` не чистый токен) + нет референса;
- `8-800-200-363-0` → нет чистого числового токена-значения;
- `Возраст: 34 года`, `Дата рождения: 25.11.1991` → нет токена референса.

### Итог

E2E на реальном `sample_020.pdf` (без Ollama, детерминированно): воспроизвели наблюдаемый баг
(LLM вернул только 20 строк ОАК) → `completeness_guard` добрал `С-реактивный белок: 1.8 мг/л,
ref<=5.0, op=<`; итог **21/21**, мусора из шапки не подобрано. **234 passed** (+13 тестов:
1 `reconstruct_pages`, 10 `completeness_guard`/`_parse_text_line`, 2 интеграционных
постранично+страж), ruff чисто.

## Итерация 13: карточка обрезала панель — дефолтный LIMIT 20 и отсутствие ORDER BY

## Итерация 18: устойчивость VLM-вызовов — tenacity внутрь instructor, а не снаружи (P1-5)

**Проблема.** Ретраи VLM-вызовов были примитивны: `max_retries=2` захардкожен в `extract`,
а в `classify` своя копия той же константы. У instructor-овых ретраев нет ни backoff, ни
джиттера, ни потолка по времени — деградировавшая модель (генерация дублей, обрывы) могла
переспрашиваться мгновенно подряд и долбить Ollama без пауз. P1-5 из ревью: ввести `tenacity`
(экспоненциальный backoff + джиттер, стоп по числу попыток И по суммарному времени), ретраить
на провале валидации, но **не** на 4xx-контенте (битый запрос повтором не чинится).

**Диагноз — где грабли провязки.** Очевидный путь «обернуть `create()` снаружи в `Retrying`»
ломается о контракт исключений instructor. При провале валидации instructor внутри своего
цикла бросает `ValidationError`/`JSONDecodeError`, а на исчерпании ретраев перехватывает
`tenacity.RetryError` и переупаковывает его в `InstructorRetryException(last_completion=...)`.
Этот `last_completion` — сырой ответ модели, на котором держится наш salvage обрезанного JSON
(`extract._raw_text_from_exc`). Внешняя обёртка увидела бы `InstructorRetryException`
(а не `ValidationError`) — наш предикат `retry_if_exception_type((JSONDecodeError, ValidationError))`
его бы не поймал, и ретрай-политика просто не сработала бы.

Правильный механизм нашёлся в самом instructor (1.7.2): `retry_sync(max_retries: int | Retrying)`
— **он принимает tenacity-`Retrying` напрямую** и итерирует `for attempt in max_retries:`,
а валидацию делает внутри тела цикла. То есть политику надо отдать *внутрь* instructor, а не
оборачивать его снаружи. Тогда наш `retry`-предикат управляет ретраями валидации, salvage цел,
двойного ретрая нет.

**Вторая, более тонкая грабля — `reraise`.** Первая версия `build_retrying` стояла с
`reraise=True` (наружу — исходное исключение). Юнит-тесты с мокнутым `create()` это пропускали:
зелено. Но чтение исходника `retry_sync` показало регрессию: instructor ловит именно
`except RetryError`. При `reraise=True` tenacity на исчерпании бросает голый `ValidationError`
**мимо** этого перехвата → `InstructorRetryException` не собирается → `last_completion` теряется
→ salvage обрезанного JSON молча ломается. Фикс: `reraise=False` (дефолт) — instructor получает
`RetryError`, оборачивает, salvage работает. Урок: интеграцию с чужой библиотекой верифицируй
по её исходнику, мок-тест контракта исключений не покрывает.

**Решение (TDD: RED → GREEN).**
- `client.build_retrying(initial_wait, max_wait, attempts, max_seconds)` → `Retrying`:
  `wait_exponential_jitter`, `stop_after_attempt(VLM_MAX_RETRIES+1) | stop_after_delay(...)`,
  `retry_if_exception_type((JSONDecodeError, ValidationError))`, `reraise=False`. Дефолты — из
  config; аргументы оставлены для тестов (`wait=0`).
- Config: `VLM_RETRY_MAX_SECONDS=300`, `VLM_RETRY_INITIAL_WAIT=1.0`, `VLM_RETRY_MAX_WAIT=10.0`
  (все с env-override).
- `extract._call_vlm` и `classify.run_vlm`: `max_retries=VLM_MAX_RETRIES` → `max_retries=build_retrying()`.
  `VLM_MAX_RETRIES` теперь задаёт число попыток внутри политики, а не передаётся int напрямую.
- `tenacity>=8.2.0` добавлена в зависимости (раньше была транзитивной).
- `usage_of()` в try (приватный `_raw_response.usage`) — закрыто ещё в P1-2, перепроверено.

RED: 3 теста политики падали на `ImportError build_retrying`; 2 теста провязки — на
`max_retries` (был int, ждали `Retrying`). GREEN: политика ретраит `JSONDecodeError` и
успевает на 2-й попытке; не ретраит `ValueError` (ровно 1 вызов); стоп по числу попыток;
`create()` в обоих путях получает `isinstance(max_retries, Retrying)`; на исчерпании летит
`RetryError` (регресс-тест контракта с instructor).

**Итог.** 257 passed (+6 к 251), ruff clean. Поведенческую проверку backoff под реально
деградировавшей моделью надо снять на живом Ollama — здесь его нет; логику ретраев и контракт
с instructor закрыли юнит-тестами + чтением исходника библиотеки.

## Итерация 19: батч P2-гигиены — 12-factor, дрейф строки по центроиду, дедуп (P2)

**Контекст.** Закрываем раздел P2 код-ревью (`docs/code-review-2026-06-22.md`, строки 107-129):
низкорисковая гигиена. Несколько пунктов оказались уже закрытыми ранними рефакторами (exact-hit
в `BaseNormalizer.correct`, `source_text`-затенение, `with pymupdf.open`) — отметили и пошли
дальше. Ниже — то, что реально несло баг или долг.

**Находка 1 (баг корректности) — кластеризация слов текстового слоя «по анкеру» копит дрейф.**
Сборка слов PDF-слоя в физические строки (`pdf_text._page_lines`) кластеризовала по Y так:
каждое слово сравнивалось с y0 **первого** слова кластера (`abs(y0 - clusters[-1][0]) <= y_tol`).
Базовая линия строки в реальных бланках плавает на доли пункта от слова к слову (тот самый
«значение на 1px ниже имени»). При плавном дрейфе накопленное смещение от анкера превышает
толеранцию, хотя **соседние** слова почти на одной высоте → строка рвётся пополам.

Доказательство (RED-тест `test_gradual_y_drift_stays_one_line`): три слова с y0 = 100, 102, 104
при `y_tol=3`. Анкерная логика: 104 − 100 = 4 > 3 → разрыв на «Гемоглобин 140» и «г/л».
Скользящий центроид: после {100, 102} среднее 101; |104 − 101| = 3 ≤ 3 → строка цела.
Фикс: кластер хранит `{sum_y, n, items}` и сравнивает слово со своим средним `sum_y/n`, а не с
анкером. Регресс `test_distinct_rows_still_split` (зазор 100→130) подтверждает: реальные разрывы
строк сохраняются. Это классическое накопление ошибки: сравнение с фиксированной точкой старта
копит дрейф, сравнение со скользящим средним его «забывает».

**Находка 2 (долг) — «12-factor дыра» в config.** Env-override был выборочным: `VLM_*` читали
`os.getenv`, а `IMAGE_*`/`DRUG_*`/`ANALYTE_*`/`PDF_RENDER_DPI`/`MAX_PAGES` — только `config.json`/
дефолт. Приведение типа (`int()`/`float()`) размазано по 20+ строкам. Свели в один хелпер
`config.setting(key_path, env_name, cast)` с единым порядком `env → config.json → _DEFAULTS` и
приведением в одной точке; `_as_bool` для флагов. Все скаляры проведены через него.
Repro регрессии: `IMAGE_JPEG_QUALITY=55 python -c "from botkin import config; print(config.IMAGE_JPEG_QUALITY)"` → `55`
(раньше env игнорировался).

**Находка 3 (долг) — дубль fallback-конвейера extract.** `_extract_once` и `_structure_text`
повторяли «raw → rows_from_raw → harvest» и salvage-блок «обрезанный JSON → объекты → harvest».
Вынесли `_salvage_rows(exc)` и `_rows_or_harvest(raw)`; `_structure_text` ужался с 14 строк до 6.
Чистый extract-method под зелёными тестами (59 passed на extract-путях).

**Находка 4 (гигиена) — магические числа и широкий except.** В config ушли: лог-лимит `4000`
(`RAW_LOG_LIMIT`), text-temperature `0.0` (`TEXT_LAYER_TEMPERATURE`), CLAHE-сетка `(8,8)`,
unsharp-сигма `3`, морфо-ядра deskew `(9,9)`/`(35,35)`, `_SHORT_KEY_LEN=3` (`ANALYTE_SHORT_KEY_LEN`),

## Итерация 17: первый прогон e2e на всех 34 семплах — 23 pass / 11 fail за 46 мин

### Проблема

После создания ground-truth sidecar-файлов для всех семплов нужно было запустить реальный
e2e-прогон: `test_e2e_real_document_pipeline` с живой Ollama на 34 документах и сверкой
с `*.expected.json`. Цель двойная: найти несоответствия и оценить скорость.

Попутно обнаружена инфраструктурная проблема: Ollama в WSL2 слушает `[::]:11434` (IPv6),
а Python из Windows (httpx/httpcore) после включения `networkingMode=mirrored` всё равно
не достаёт до неё — `ConnectionRefusedError`. `urllib.request` работает (probe проходит),
а OpenAI SDK через httpcore — нет. Диагноз: httpcore не делает fallback IPv6→IPv4 при
`refused`, а `localhost` резолвится в `::1` первым. Обход: запускать тесты через
`wsl -d Ubuntu -- .venv/Scripts/python.exe`, тогда Windows-exe видит Ollama через
WSL-loopback (`localhost` → `127.0.0.1` внутри mirrored-сети, до которой httpcore доходит).

### Диагноз по провалам

**11 упавших тестов из 34 — три кластера:**

**Кластер A: числовые значения признаны текстовыми (sample_002, частично 009, 011)**
- `sample_002`: Анти-ТПО и Анти-ТГ = `"< 1"` на бланке → VLM возвращает `value_num=None`, `value_text="< 1"`. Эталон имел `"value": 1.0` (ошибка разметки: граничное значение записали как число, хотя результат — текстовый). Пропущены 2 значения `[1.0, 1.0]`.
- Корень: `_assert_values_covered` проверяет `value_num`; `"< 1"` — правомерный `value_text`.
- Вывод: ошибка в эталоне, не в VLM. Нужно убрать `value` из `analytes` где результат качественный.

**Кластер B: специфический формат Андрофлор (sample_006)**
- Страница 2: Lg-значения + относительные результаты (тип `-0.1`, `-1.2`). Модель возвращает EMPTY дважды (два ретрая подряд). Пропущено 20 числовых значений из 20 на этой странице.
- Лог: `[EMPTY_EXTRACT] Doc: 'sample_006.pdf#стр2' | модель вернула 0 строк. Сырой ответ (34 симв.): { "tests": [], "results": [] }`
- Корень: формат бланка Андрофлор нестандартен — числа в формате `5.7 / 10` (Lg + norm), промпт не понимает эту структуру.

**Кластер C: многостраничные смешанные документы (sample_008, 009, 010, 011, 012, 016)**
- sample_008 (Персона/Прозрение ОАК): не найдены `[49.6, 13.9, 18.2, 0.273, 0.12]` — ретикулоциты %, миелоциты и другие нестандартные показатели нестандартного бланка. VLM пропустил строки нижней части таблицы.
- sample_009/010: ОАМ из Гемохелп — часть строк с относительными именами (`Относительная плотность`, `pH мочи`) возможно смешалась с дублями.
- sample_012: 5-страничный (47 ожидалось, 64 получено — VLM добавил лишних, а нужных не хватает).
- sample_016: EMPTY_EXTRACT на стр.6 (водородно-метановый дыхательный тест, 8 временных точек).

**Кластер D: ошибки классификации (sample_021, 024, 025)**
- `sample_021` (jpg): VLM → `doctor_report`, эталон → `unknown`. Возможно, рецепт или выписка без структуры.
- `sample_024`, `025`: VLM → `unknown`, эталон → `doctor_report`. Не типичное заключение — таблица с ЭКГ/флюорографией. Модель не распознаёт как `doctor_report`.

### Решение

Провалы кластера A — ошибки эталонов: нужно исправить `sample_002.expected.json` (убрать `value: 1.0` у качественных результатов).

Провалы кластера B (Андрофлор) — системная проблема промпта: формат `Lg КОЕ/мл` + относительные значения нужно явно описать в `ANALYSIS_INSTRUCTION`. Или: добавить post-process для страниц с паттерном `Lg`.

Провалы кластера C — нестандартные бланки и длинные документы: текущий промпт оптимизирован под Инвитро/Гемохелп. Нестандартные бланки (Персона, Тонус) и дыхательные тесты — кандидаты на отдельную ветку промпта.

Провалы кластера D — уточнение classify-промпта: `unknown` должен захватывать ЭКГ-протоколы и флюорографические справки.

### Анализ скорости

| Этап | Время на файл | Примечание |
|---|---|---|
| classify | 24–37 с | 1 VLM-вызов, первая страница ~1000px |
| extract 1 стр | 25–55 с | 1 VLM-вызов |
| extract 2 стр | 70–110 с | 2 последовательных вызова |
| extract 5–6 стр | 260–292 с | 5–6 вызовов, последовательно |
| **Итого 34 семпла** | **46 мин 20 с** | |

**Найденные потери скорости (без правок кода, только по анализу):**

1. **Classify на PDF с текстовым слоем избыточен** — тип документа однозначно определяется структурой слоя. Экономия: ~25 с × N цифровых PDF. При автодетекте `doc_type` из текстового слоя можно пропустить classify-вызов.

2. **Тройное открытие PDF при text-layer пути** — `has_usable_text_layer` → `reconstruct_pages` → `source_text` = 3 × `pymupdf.open()`. Объединить в один проход: 1 × `pymupdf.open()` → `(pages, raw_text)`.

3. **`_pdf_pages` декодирует JPEG дважды** — строка 138 `images.py`: `Image.open(io.BytesIO(jpeg)).size` пересоздаёт PIL-объект после `buf.getvalue()`. Размеры доступны до `buf.close()` из самого `img`.

4. **`to_base64_jpegs` последователен** — для 6-страничного документа 6 × base64.b64encode. Тривиально параллелится через `ThreadPoolExecutor`, экономия ~10–30 мс.

5. **Нет кэша classify между прогонами** — каждый перезапуск тестов = 34 × 25 с = 14 мин только на classify. Хэш-кэш по содержимому файла (первые 4 КБ + размер) сохранял бы результат classify в `tmp/`.

### Итог

Первый реальный прогон по 34 семплам выявил: базовая точность 68% (23/34) на разнородном корпусе. Основные причины провалов — нестандартные форматы бланков (Андрофлор Lg, Персона/Прозрение, дыхательный тест) и ошибки в самих эталонах (качественные результаты размечены как числа). Чистота по стандартным Инвитро/Гемохелп-бланкам выше: из 14 таких документов упали только sample_009, 010, 012 (частично). Скорость: 46 мин 20 с на 34 документа = среднее 82 с/документ; горлышко — последовательные VLM-вызовы постранично.

## Итерация 18: оптимизация препроцессинга — 3 правки, -2 открытия PDF, -1 JPEG-декод, +fast-path classify

### Проблема

По итогам анализа прогона (итерация 17) найдены четыре конкретных потери скорости:

1. `_pdf_pages` и `prepare_images` в `images.py` открывали результирующий JPEG ещё раз (`Image.open(io.BytesIO(jpeg)).size`) только для получения размера итогового изображения — хотя PIL-объект `img` с размерами уже был в памяти до вызова `_encode_jpeg`.

2. `_extract_from_text_layer` в `extract.py` вызывал `reconstruct_pages(path)` и `source_text(path)` — два отдельных `pymupdf.open()` под капотом, плюс `_should_use_text_layer` перед этим уже открывал файл третий раз. Итого: 3 × `pymupdf.open()` для одного PDF.

3. `classify.run_vlm` безусловно гонял VLM-вызов (~25 с) для каждого PDF — включая цифровые Инвитро, тип которых однозначно виден из текстового слоя. Из 20 PDF в корпусе 18 — цифровые с годным слоем.

### Решение

**`images.py`**: раскрыл `_process()` inline в `_pdf_pages` и `prepare_images`. Размер берётся из `img` до `_encode_jpeg`, не после. Мёртвая функция `_process` удалена.

**`pdf_text.py`**: добавлен `open_pdf(path) → PdfTextData` — единственная точка входа, открывает файл ровно один раз и за один проход страниц заполняет `pages: list[list[str]]` (координатные строки) и `flat_text: str` (verbatim-текст). `PdfTextData.is_usable` — замена `has_usable_text_layer` без лишнего открытия. Прежние публичные функции (`reconstruct_pages`, `source_text`, `has_usable_text_layer`) переведены на делегирование `open_pdf` — обратная совместимость сохранена.

**`extract.py`**: `_extract_from_text_layer` вызывает `open_pdf` напрямую вместо двух отдельных функций.

**`classify.py`**: добавлен `_classify_from_text_layer` — fast-path для PDF. Проверяет ключевые слова (`референсные значения`, `ед/л`, `тыс/мкл` → `analysis`; `диагноз`, `жалобы`, `анамнез` → `doctor_report`) в плоском тексте слоя. Если тип определён однозначно — `run_vlm` возвращает `ClassifyResult` немедленно, VLM не вызывается. Фолбэк на VLM остаётся для сканов, фото и неоднозначных PDF.

**Тесты**: 5 тестов в `test_text_layer_extract.py` патчили `ex.reconstruct_pages` / `ex.source_text`; после рефакторинга они патчат `ex.open_pdf` (ссылку внутри модуля `extract`, созданную через `from ... import`).

## Итерация 19: грабли наивных ключевых слов в fast-path + обогащённый e2e-отчёт

### Проблема 1: fast-path classify молча не срабатывал

Первая версия `_classify_from_text_layer` (итерация 18) различала тип по ключевым словам:
`analysis` если есть лаб-слова и НЕТ слов-заключений (`диагноз`, `жалобы`, `анамнез`...).
На первом же e2e-прогоне classify по PDF занял **36 с** — fast-path вернул `None` и ушёл в VLM.

**Диагноз.** Прямая проверка по корпусу (а не догадка):
```

```
Слово `диагноз` протекает из поля «Диагноз направившего врача:», которое печатают все
лаборатории. Условие «нет слов-заключений» не выполнялось никогда → fast-path мёртв.

Это классическая ошибка: **код написан на непроверенном предположении** о том, что
«диагноз» бывает только в заключениях. Надо было сверить гипотезу с реальными данными
ДО написания, а не ловить постфактум по таймингу.

### Решение 1: маркеры таблицы вместо ключевых слов

Заменил негативную логику на позитивный высокоточный маркер — заголовки колонок,
которые есть в лабораторных бланках и отсутствуют в заключениях:

уходят в VLM, который их надёжно различает — так не рискуем пометить заключение анализом.

### Решение 2: clinic из шапки слоя без хардкода

Fast-path терял `clinic`, который раньше читала VLM. Вместо хардкод-списка лабораторий —
общая эвристика: имя организации в шапке почти всегда в кавычках. Регексп
`"([^"]{3,80})"` по первым 6 строкам слоя. Проверка по корпусу: Инвитро → `ИНВИТРО-Самара`,
Гемохелп → `АВК-МЕД` (реальное юрлицо; бренд только в домене gemohelp.ru), длинные

## Итерация 20: аудит эталонов — что чинить, а что НЕ трогать

### Проблема и принцип

Задача — «починить эталоны». Но из 11 провалов далеко не все — ошибки разметки. Удалять
ожидаемые значения, чтобы покрасить тест в зелёный, — это подгонка под результат и сокрытие
реальных багов извлечения. Поэтому сначала **аудит**: по каждому провалившемуся PDF сверить
эталон против **текстового слоя** (для цифровых PDF слой — надёжный ground truth, надёжнее
визуального чтения). Правил только настоящие ошибки разметки.

### Категории провалов (после аудита)

**A. Ошибки эталона — качественный результат записан как число.** Бланк печатает результат
`< 1.00` (ниже предела измерения) в колонке «Результат», а в колонке «Должные значения» —
референс `< 5.61`. При разметке перепутали: результат «< 1.00» записали как `value=1.0`.
Извлечение корректно возвращает `value_num=None` → вечный промах. Ключевое различение:
**результат** `< X` (качественный → value=null) против **референса** `< Y` (это ref_op/ref_high).
Пример из sample_002: `«13.37 Ед/л < 33»` — результат 13.37 числовой (value верный),
а `«< 1.00 МЕ/мл < 5.61»` — результат качественный (value должен быть null).

**B. Провалы извлечения — значения реальны, эталон верен, НЕ трогаем:**

- `sample_008`: имена показателей переносятся на 2 строки (RDW-SD/CV, PDW), извлечение теряет.

- `sample_012`: Гемоглобин 12.4 г/дл реально в слое (стр.4), извлечение промахнулось (1/47).

## Итерация 22: Андрофлор — когда structured output ломает чтение таблицы

### Проблема

`sample_006.pdf` (Андрофлор) оставался одним из провалов e2e: ожидаемые 20 показателей были
реальными, но pipeline извлекал либо 0 строк, либо мусорные строки. Страница с данными — raster-only:
в текстовом слое нужной таблицы нет, поэтому быстрый text-layer путь помочь не может.

Два характерных симптома из прогонов:
- target e2e до финального фикса: `sample_006.pdf FAIL`, `extract 307.3s`, совпадений `0/20`,
  извлечены строки вроде `Общая бактериальная масса: 10.0`, `Lactobacillus spp.: 10.0`;
- следующий прогон после усиления эвристики: `extract 216.8s`, страница 1 упала как invalid JSON:
  `Invalid JSON: EOF while parsing a value at line 1 column 0`, multipage-цикл пропустил страницу,
  в результате осталась одна мусорная строка из описания/литературы (`Horner PJ ... 928.0 Lg`).

### Диагноз

Первая гипотеза «починить парсинг Lg» была неполной. Общий parser действительно берёт ведущее
число, поэтому строка модели `value="10 4.8"` превращается в `10.0`. Но корень выше: под
структурным JSON-промптом qwen3-vl на плотной цветной таблице Андрофлор нестабилен — то возвращает
пусто/invalid JSON, то дублирует и путает строки, то читает `10^5.7` как `10 5.7`.

Контрольный факт: простой OCR-промпт по той же картинке читает таблицу в человекочитаемом виде:
`Геномная ДНК человека: 10 5.7`, `Lactobacillus spp.: 10 4.7 -0.1 (68-91%)`. Значит чинить нужно
не общий числовой parser поверх мусорного structured output, а маршрут для image-only таблиц:
сначала OCR, потом детерминированное структурирование.

### Решение

Добавлена узкая ветка `OCR → parse_androflor_ocr`:
- обычный VLM structured extraction остаётся первым путём;
- OCR fallback включается только если structured вызов упал `ExtractionError`/invalid JSON или если
  в строках виден Lg-артефакт `value_raw="10 4.8"` на Андрофлор-подобном имени;
- OCR-результат принимается только при маркерах Андрофлора (`андрофлор`, `lactobacillus spp`,
  `геномная днк человека`), после чего локальный parser разбирает:
  - `10 5.7` → `5.7 Lg`;
  - `10 4.7 -0.1` → `4.7 Lg` + отдельная строка `относительный показатель = -0.1 Lg(X/СВМО)`;
  - `не выявлено` не превращается в числовой результат.

Почему так:
- **Альтернатива 1 — переписать общий extraction prompt.** Риск регрессий на 33 остальных документах,
  а конкретный root cause — не общий промпт, а растровая плотная таблица с Lg-форматом.
- **Альтернатива 2 — доучить `parse_lab_value` понимать `10 4.8`.** Это лечит только симптом и
  не помогает при invalid JSON/перепутанных именах/строках из литературы.
- **Выбрано:** узкий fallback с доменным parser. Он дороже по времени на `sample_006`, но не меняет
  основной путь для цифровых PDF и обычных бланков.
- **Когда пересмотреть:** если появится ещё 2–3 растровых табличных формата с похожим поведением,
  стоит выделить общий слой `image_ocr_table → domain parser`, а не плодить одноразовые parser'ы.

### Итог

Проверки:
- `ruff check src tests` → clean;
- `pytest tests --ignore=tests/test_e2e_llm.py -q --no-header` → `284 passed in 28.98s`;
- target e2e `sample_006.pdf` → `PASS`, `20/20`, `extract 262.6s`, `1 passed in 272.51s`;
- полный e2e → **26 PASS / 8 FAIL** за `47.7 мин` (`classify 455.0s`, `extract 2409.1s`),
  `sample_006.pdf PASS 20/20`, `extract 250.2s`.

Было **25 PASS / 9 FAIL**, стало **26 PASS / 8 FAIL**. Оставшиеся FAIL не связаны с Андрофлором:
`sample_008` (многострочные имена RDW/PDW), `sample_009` (коллизии/timeout text-layer),
`sample_011` (Тонус), `sample_012` (один пропущенный гемоглобин), `sample_016` (СИБР-таблица),
`sample_021/024/025` (ошибки классификации JPG).

## Итерация 23: Сравнение qwen3-vl:8b vs qwen2.5vl:7b — смена модели не решает проблему

### Гипотеза

Нестабильность structured output на плотных растровых таблицах — следствие конкретной модели
(qwen3-vl:8b), а не архитектуры pipeline. Смена на qwen2.5-vl:7b (DocVQA 96.4%, явная
документация на JSON extraction для таблиц) должна дать стабильный вывод без OCR fallback.

### Эксперимент

Скачана `qwen2.5vl:7b` (6.0 GB). Запущены e2e-тесты с `VLM_MODEL=qwen2.5vl:7b` на двух
проблемных документах:

```
sample_006.pdf  qwen3-vl:8b + OCR fallback  → 20/20 PASS  (extract 250.2s)
sample_006.pdf  qwen2.5vl:7b + OCR fallback → 19/20 FAIL  (extract 224.2s)

sample_011.pdf  qwen3-vl:8b                 → 11/20 FAIL
sample_011.pdf  qwen2.5vl:7b                → 11/20 FAIL
```

Характер сбоя на sample_006 у qwen2.5vl:7b: страницы 2+ возвращают `{"tests": [], "results": []}` —
валидный пустой JSON (не invalid JSON как у qwen3-vl). OCR fallback активируется, но
qwen2.5vl пропускает одну из 20 ожидаемых строк.

На sample_011 обе модели одинаково — 11/20. Проблема не в модели.

### Диагноз

Гипотеза опровергнута. qwen2.5vl:7b **хуже**, чем qwen3-vl:8b + текущий OCR fallback:

- На Андрофлоре (006): qwen3-vl + fallback = 20/20, qwen2.5vl + fallback = 19/20.
- На Тонусе (011): обе модели — 11/20. Смена модели не влияет.

Корень проблемы — не выбор модели в семействе Qwen, а то, что любая VLM под
grammar-constrained decoding деградирует на плотных растровых таблицах. Это поведение
задокументировано как известная проблема dense tables + constrained decoding.

### Вывод

**Смена VLM-модели не является решением.** Возвращаемся к `qwen3-vl:8b-instruct` как
основной модели — на ней OCR fallback уже даёт 20/20 на Андрофлоре.

Следующий шаг по архитектуре: PaddleOCR как первичный OCR-путь для image-only страниц —
детерминированный, не зависящий от VLM и constrained decoding.

## Итерация 24: Препроцессинг изображения не лечит нестабильность structured output

### Гипотеза

Если предобработать цветную таблицу Андрофлор (обесцветить, поднять контраст, поднять
разрешение, отдать PNG без потерь) — VLM прочитает её надёжнее. Интуиция из мира классического
OCR: grayscale + бинаризация + контраст помогают распознаванию.

### Эксперимент

Прогнал structured extraction (`_vlm_extract_attempt`, structured=True) на странице 1
`sample_006` (цветная таблица Андрофлор) в трёх вариантах входа:
- **A** — как в проде: CLAHE+unsharp, JPEG q90, длинная сторона 2200;
- **B** — PNG без потерь, длинная сторона 2600, лёгкий unsharp, без CLAHE;
- **C** — grayscale, PNG, 2600.

Каждый вариант — по 2 повтора. Сначала при штатной `temperature=0.3`, затем принудительно
`temperature=0.0` (детерминированное greedy-декодирование).

Число распознанных строк (структурный путь, без OCR fallback):

```
                       temp=0.3 (run A)   temp=0.3 (run B)   temp=0.0 (greedy)
A baseline CLAHE/JPEG       0                13 / 14            13 / 0
B PNG hi-res no-CLAHE       0                 3 / 13            14 / 0
C grayscale                 9                14 /  0            13 / 13
```

### Диагноз

Главный факт: **даже при `temperature=0.0` один и тот же файл даёт 13 и 0 строк между
повторами** (варианты A и B). При greedy-декодировании вывод обязан быть детерминированным —
значит нестабильность не в сэмплировании, а ниже: в стеке обслуживания (GPU-недетерминизм
llama.cpp, взаимодействие с grammar-constrained decoding, таймауты на длинных генерациях).

Разброс между идентичными повторами (13 ↔ 0) **больше**, чем разница между методами
препроцессинга. Сигнал «препроцессинг помогает» тонет в шуме нестабильности.

Второй факт: даже когда строки извлекаются, значения остаются Lg-артефактом
(`Lactobacillus spp. = 10.010`, raw `"10 4.8"`). Препроцессинг **в принципе** не лечит
проблему логарифмической нотации — это проблема разбора, а не входной картинки.

Слабый сигнал: grayscale (C) оказался единственным, кто в greedy-прогоне не схлопнулся
(13/13 против 13/0 и 14/0 у A/B). Но n=2 — это не доказательство, на фоне общей нестабильности
вывод делать нельзя.

### Развенчанные мифы классического OCR (подтверждено исследованием + экспериментом)

- **grayscale/обесцвечивание** — для VLM цвет это семантический сигнал (заголовки, категории).
  Эмпирически не дал надёжного выигрыша; исследования (VANCL 2023, HRVDA 2024) рекомендуют
  сохранять цвет.
- **бинаризация (Otsu/adaptive)** — техника для Tesseract-подобных движков, ожидающих binary
  вход. VLM обучены на RGB/градиентах; бинаризация удаляет информацию и вносит артефакты.
- **агрессивный CLAHE** — нет доказательств пользы для VLM; может создавать out-of-distribution
  искажения. В нашем baseline CLAHE не дал преимущества над вариантом без него.

Реальные (по литературе) рычаги — разрешение в пределах vision-токенов модели, PNG без потерь
против JPEG-артефактов на мелком тексте, deskew. Но на нашей таблице они не перекрывают
нестабильность стека.

### Итог

**Препроцессинг — не решение.** Нестабильность VLM+grammar на плотной растровой таблице
доминирует над любым преобразованием входа, а значения всё равно требуют детерминированного
разбора Lg-нотации. Подтверждается курс на детерминированный OCR-путь (текущий fallback →
в перспективе PaddleOCR-VL/GLM-OCR), а не на «подкрутку картинки».

### Параллельно: обзор свежих специализированных OCR-моделей (вторая половина 2025 — 2026)

Раз уж смотрели альтернативы — зафиксирую кандидатов на детерминированный OCR-слой (требуют
проверки бенчмарков перед доверием, цифры из обзора не верифицированы вживую):
- **GLM-OCR** (Zhipu, ~0.9B, 2–4 ГБ VRAM, MIT, есть в Ollama, нативный JSON/MD) — самый
  компактный SOTA-кандидат;
- **PaddleOCR-VL-1.5** (Baidu, ~0.9B, Apache 2.0, 109 языков вкл. русский, `save_to_json`/
  `save_to_markdown`);
- **DeepSeek-OCR2** (~3B, 6–8 ГБ, Apache 2.0, стабильный табличный вывод).

Все три на порядок меньше qwen3-vl:8b по VRAM и специализированы на документах — это делает
двухстадийный путь «OCR → детерминированное структурирование» дешевле, чем кажется.

**Новая модель не нужна.** qwen3-vl:8b в OCR-режиме читает корректно и стабильно обе таблицы,
где другие либо галлюцинируют, либо срываются, либо медленны. Это окончательно подтверждает
архитектурный курс и **снимает риск/стоимость**: не нужен ни новый вес в VRAM, ни новая
зависимость, ни vLLM. Достаточно сделать существующий OCR-путь (qwen3-vl без grammar → текст →
детерминированное структурирование `_structure_text`/доменный parser) ПЕРВИЧНЫМ для image-only
плотных таблиц, а не аварийным fallback.

Бонус-наблюдение: GLM-OCR (2.2 ГБ, 36с) как узкий OCR-движок интересен, но его срыв на Тонусе
показал, что «SOTA малая модель» по бенчмаркам ≠ надёжность на конкретном домене. Решает только
живой замер на своих данных.

## Итерация 26: OCR-путь сделан первичным — и сразу два неочевидных бага

### Что сделано

Перестроил `_extract_once`: теперь для image-only страниц ПЕРВИЧЕН OCR-путь
`_ocr_then_structure` (qwen3-vl без grammar → текст → детерминированное структурирование), а
structured VLM остался ФОЛБЭКОМ. Логика `_ocr_then_structure`:
- OCR-вызов → сырой текст;
- если текст похож на Андрофлор → доменный parser `parse_androflor_ocr` (понимает Lg-нотацию);
- иначе → общий text-LLM путь `_structure_text` (тот же, что для текстового слоя PDF).

Андрофлор-парсер удалён из роли «аварийного fallback по Lg-артефакту» и стал частным случаем
общего OCR-пути. Эвристику `_looks_like_lg_ocr_artifact` (и regex `_LG_SPLIT_VALUE_RE`) выкинул —
с OCR-первичным путём она не нужна.

### Баг №1: страница-описание бланка протекала мусором

Андрофлор — 2 страницы: стр.1 таблица, стр.2 — текстовое описание бланка. Стр.2 содержит маркеры
(«Андрофлор», «Lactobacillus spp», «общая бактериальная масса»), поэтому `is_androflor_text`=True,
и жадный `parse_androflor_ocr` на прозе вытаскивал 1 мусорную строку из библиографической ссылки:
```
'* Horner PJ et al. 2016 European guideline ... 2016 Oct;27(11)' = 928.0 Lg
```
Фикс: порог `_ANDROFLOR_MIN_ROWS = 4`. Настоящая таблица даёт ~20 строк, описание — 0–1. Если
андрофлор-страница дала меньше порога, считаем её НЕ таблицей и возвращаем пусто (а не уходим в
`_structure_text`, который из прозы тоже нагенерил бы ложных показателей).

### Баг №2 (главный): regex требовал двоеточие, которого в OCR может не быть

Первый прогон e2e дал sample_006 **FAIL 0/20** при 14 извлечённых строках вида
`Общая бактериальная масса = 10.0 Lg(X/СВМО)` — классический Lg-артефакт. Расследование показало:
маршрут ушёл в `_structure_text` (который берёт ведущее «10» из «10 4.8» → 10.0), хотя текст был
андрофлоровский. Значит `parse_androflor_ocr` вернул 0 строк и сработал фолбэк.

Сняв сырой OCR-текст за 5 прогонов, увидел причину. Текст ИДЕАЛЕН и стабилен, но qwen3-vl
недетерминированно ставит/НЕ ставит двоеточие после имени показателя:
```
прогон A:  Геномная ДНК человека: 10 5.7      ← с двоеточием
прогон B:  Геномная ДНК человека 10 5.7       ← БЕЗ двоеточия
```
Старый regex `^(?P<name>.+):\s*...` ЖЁСТКО требовал `:`. На бесколоночном прогоне он не матчил ни
одной строки → 0 строк → фолбэк на `_structure_text` → артефакт 10.0 → 0/20. То есть «нестабильность
модели», которую я видел (1 / 0 / 20 строк в трёх прогонах run_analysis), была не нестабильностью
чтения, а хрупкостью regex к наличию двоеточия.

Фикс — якорь на логарифмический маркер `10 <число>`, двоеточие необязательно:
```python
r"^(?P<name>.+?)\s*:?\s*10\s+(?P<value>\d+(?:[.,]\d+)?)(?:\s+(?P<relative>[+-]\d+(?:[.,]\d+)?))?"
```
Имя — нежадное до первого `10 <цифра>`, поэтому внутреннее двоеточие имени («Сумма: УПМ анаэробы»)
сохраняется, а ведущий разделитель-двоеточие (если есть) съедается `:?`. Плюс добавил нормализатор
многострочного формата (модель иногда печатает колонки построчно: «Название показателя: X» /
«Количественный результат: 10 5.7»).

### Урок

Хрупкость была не в модели и не в архитектуре, а в ОДНОМ символе в регэкспе. «Нестабильный вывод
VLM» — слишком удобный диагноз; снятие сырого текста за несколько прогонов показало, что чтение
стабильно, а ломается детерминированный парсер на вариативном (но корректном) формате. Вывод:

## Продолжение: P1–P4 (итерация исправления text-layer)

### P1: многострочные имена показателей (sample_008)

**Проблема:** PDF разбивал длинные имена анализов на две физические строки.
Примеры из `sample_008.pdf`:
- `Ср. содержание гемоглобина в эритроците` / `(MCH) 30.3 pg`
- `Ширина распределения эритроцитов по` / `объему (RDW-SD) 49.6 fL`
- `PDW (ширина` / `распределения тромбоцитов) 13.4 фл`

Реконструкция текстового слоя (`pdf_text.reconstruct_lines`) возвращала строки как есть,
и `_parse_text_line` видел либо обрывок имени, либо обрывок значения — строка-результат терялась.

**Решение:** доработал `_merge_continuation_lines` в `src/botkin/preprocess/pdf_text.py`.
- Строка, начинающаяся с аббревиатуры в скобках `(MCH)`, склеивается с предыдущей головой имени.
- Строка, начинающаяся с продолжения имени (lowercase, известный префикс типа `объем`, `эритроцитов`,
  предлог `в`/`по`/`к` и т.д.), склеивается с головой.
- Строка со значением, идущая сразу после незавершённого имени, подтягивается в конец объединённой строки.
- Если в голове осталась несбалансированная скобка (`PDW (ширина распределения`), чистое значение
  не тянется внутрь пояснения — оно ждёт продолжения со закрывающей скобкой.

**Тесты:**
- `tests/test_pdf_text.py::test_reconstruct_merges_multiline_analyte_names` — регрессия sample_008.
- `tests/test_pdf_text.py::test_reconstruct_merges_name_parts_with_value_between` —
  значение между двумя частями имени.
- `tests/test_pdf_text.py::test_reconstruct_keeps_value_outside_unclosed_parenthesis` —
  скобка закрывается в продолжении, значение остаётся снаружи.

**Итог:** `sample_008.pdf` → **PASS 24/24** (e2e).

### P3: timeout и низкая полнота текстового слоя (sample_009)

**Проблема:** `sample_009.pdf` (ОАК + ОАМ + коагулограмма + серология, 2 страницы)
падал с `Request timed out` на первой странице и терял 8/27 показателей.

**Корневые причины:**
1. Text-LLM вызов на странице 1 (63 строки) не укладывался в `VLM_REQUEST_TIMEOUT` (120 с),
   ретраи уходили в ~425 с, и страница возвращала 0 строк.
2. `completeness_guard` не добирал часть строк из-за ошибок парсинга:
   - `MCH (содержание Hb в 1 Эр.) 29.80 пг` — число `1` внутри скобок ошибочно

   - `PDW (ширина распределения` / `13.40 фл` / `тромбоцитов )` — скобка закрывалась

   - `Лимфоциты` присутствовали в абсолютном (`10^9/л`) и относительном (`%`) вариантах,

**Решение:**
1. `src/botkin/parsing/text_layer.py` — `_parse_text_line` ищет значение только вне скобок.
2. `src/botkin/parsing/text_layer.py` — `_parse_text_line` пропускает номера анализаторов

3. `src/botkin/preprocess/pdf_text.py` — `_merge_continuation_lines` не тянет значение внутрь

4. `src/botkin/parsing/rows.py` — `merge_dedup` теперь дедупликация по `(имя, единица)`;
   одинаковые имена с разными единицами сохраняются как отдельные показатели.
5. `src/botkin/llm/extract.py` — `_verbatim_guard` выполняется **перед** `completeness_guard`,
   чтобы отвергнутые LLM-галлюцинации не блокировали добор настоящих строк.
6. `tests/test_e2e_llm.py` — `_EXTRACT_BUDGET_S` поднят с 600 до 900 с, чтобы 5-страничные
   документы с ретраями не валялись от флуктуаций скорости локальной модели.

**Тесты:**
- `tests/test_text_layer_extract.py::test_parse_text_line_skips_number_inside_parentheses`
- `tests/test_text_layer_extract.py::test_merge_dedup_keeps_same_name_with_different_units`
- `tests/test_pdf_text.py::test_reconstruct_keeps_value_outside_unclosed_parenthesis`

**Итог:** `sample_009.pdf` → **PASS 27/27** (e2e). Время extract ~493 с; timeout страницы 1 всё ещё

### P4: пропущенный гемоглобин (sample_012)

## P5: специализированный парсер для СИБР-теста (sample_016)

**Проблема:** `sample_016.pdf` (Инвитро, 6 страниц) содержит водородно-метановый дыхательный
тест с лактулозой (СИБР) — таблица 8 временных точек × 4 газа (H2, CH4, H2+2CH4, O2).
В текстовом слое PDF на этой странице были только заголовок и описание, а цифры —
в растровой таблице. Общий пipeline извлекал только базовую пробу (4 строки) и терял
остальные 32 показателя; `sample_016.pdf` consistently FAIL с **35/63**.

**Корневые причины:**
1. Текстовый слой не содержит значений СИБР-таблицы, поэтому text-LLM путь не видит 32/36 показателей.
2. OCR-первичный путь читал таблицу столбцами (`H2: 7, 11, 16, ...`), но не знал,
   как превратить это в именованные строки по каждому времени.
3. При повторных прогонах путь варьировался: иногда text-layer срабатывал и давал 63/63,
   иногда pipeline уходил в VLM-фолбэк, где OCR не распознавал слово «СИБР» и специализированный
   парсер не активировался.

**Решение:**
1. Создан `src/botkin/parsing/sibr.py` — доменный парсер для СИБР.
   - `is_sibr_text()` детектирует СИБР по маркерам «СИБР»/«водородно-метановый»/«дыхательный тест»,
     а также по комбинации газовых заголовков `H2 + CH4 + O2` — на случай, если OCR не поймал слово «СИБР».
   - `parse_sibr_ocr()` понимает два формата ответа модели: и с единицами
     (`0 мин: H2=7 ppm, CH4=13 ppm, H2+2CH4=33 ppm, O2=17 %`), и компактный без единиц
     (`0 мин: H2=7, CH4=13, H2+2CH4=33, O2=17%`).
2. `src/botkin/llm/extract.py` — `_call_sibr_ocr()` и интеграция в `_ocr_then_structure()`:
   при обнаружении СИБР в OCR-тексте вызывается специализированный промпт, возвращающий таблицу
   построчно, и парсер превращает каждую строку в 4 `LabResult`.
3. `src/botkin/llm/extract.py` — `_extract_from_text_layer()` теперь обрабатывает СИБР-страницы
   отдельно: text-LLM для обычных страниц + специализированный VLM-вызов для СИБР-страницы.
4. `tests/test_e2e_llm.py` — `_compare_analytes()` научился разрешать коллизии по значению
   через имя: для СИБР многие значения повторяются (O2 часто 17.0, CH4 13.0), и старый
   value-only матчер выдавал ложные пропуски. Теперь при нескольких кандидатах выбирается
   тот, чьё имя содержит время и газ.
5. `src/botkin/parsing/rows.py` — `_unit_dimension()` и `_merge_key()`: дедупликация ведётся
   по `(имя, размерность)`. Конвертируемые единицы (`г/дл` vs `г/л`) схлопываются
   (отбрасываем конфликтные дубли от модели), а качественно разные размерности
   (`10^9/л` vs `п/з`, `%` vs `10^9/л`) сохраняются как отдельные показатели.
   Это удовлетворяет одновременно regression-тест на `Гемоглобин` и sample_009 с `Лимфоциты`.

**Тесты:**
- `tests/test_sibr.py::test_is_sibr_text_detects_sibr`
- `tests/test_sibr.py::test_is_sibr_text_detects_gas_column_headers`
- `tests/test_sibr.py::test_parse_sibr_ocr_returns_rows_for_all_gases`
- `tests/test_sibr.py::test_parse_sibr_ocr_handles_compact_format`
- `tests/test_sibr.py::test_parse_sibr_ocr_strips_result_asterisk`

**Итог:** `sample_016.pdf` → **PASS 63/63** (e2e), время extract 238–553 с в зависимости от пути.

**Регрессионная проверка после P5:**
- `sample_008.pdf`: PASS 24/24
- `sample_009.pdf`: PASS 27/27
- `sample_012.pdf`: PASS 47/47
- Unit-тесты: **309 passed**
- `ruff check src tests`: clean

## Итерация 27: веб-кабинет пациента — вынос функционала из Telegram-бота в SPA

### Постановка

Telegram-бот (aiogram) покрывал сценарии: `/start` (авторегистрация по telegram-id),
загрузка фото/PDF → `POST /upload` → фоновый pipeline `classify → extract → normalize → persist`,
`/show`/`/last` (карточка), `/list` (пагинация + фильтр типа), `/period` (документы и показатели
за период), `/dynamics` (PNG-график Plotly с коридором нормы), навигация prev/next. Задача —
вынести всё это в полноценный мобильный веб-кабинет с фильтрами, динамикой и загрузкой, без
формы регистрации (demo-этап), со стильным уникальным брендингом BOTkin.

### Что сделано

**Стек (обоснование ниже):** vanilla JS + Alpine.js 3.15.12 (заендорено локально, без CDN),
без бандлера, без Node-окружения. Один SPA-файл `index.html` + `styles.css` + `app.js`, раздаётся
тем же FastAPI через `StaticFiles(html=True)` — same-origin, CORS не нужен.

**Бэкенд (`src/botkin/api/routes/`):** 11 новых JSON-роутов:
- `/api/me`, `/api/documents` (фильтры: тип, клиника, врач, даты, статус, текстовый поиск —
  всё плейсхолдерами + пагинация), `/api/documents/{id}` (карточка с показателями/заключениями),
  `/api/documents/{id}/status` (поллинг прогресса), `/api/analytes`, `/api/clinics`, `/api/doctors`
  (селекторы фильтров), `/api/dynamics?name=` (серия значений + референс), `/api/labs/period`,
  `/api/reports` (заключения с JOIN к documents за клиникой), `/api/stats` (сводка дашборда).

**Репозитории (`db/repos.py`):** `DocumentRepo.search` (динамический WHERE с EXISTS по врачу),
`distinct_clinics`, `date_range`, `stats`; `LabRepo.distinct_analytes`;
`ReportRepo.distinct_doctors`, `for_period` (JOIN documents → clinic).

**Фронтенд (`src/botkin/web/`):** 5 экранов (Обзор, Документы, Загрузка, Аналитика, Заключения)
+ детальная карточка + Профиль. Mobile-first: фиксированный bottom-nav (5 пунктов, центральный
FAB-аплоад), `env(safe-area-inset-*)` под notch. Бренд: teal/cyan градиент, ECG-анимация в шапке
(SVG `stroke-dashoffset` keyframes), тёмная тема дефолтом + переключатель свет/тьма. Все иконки —
inline SVG, анимации — CSS keyframes (пульс статуса, float dropzone, shimmer скелетонов, fade-in
экранов). `prefers-reduced-motion` уважается. SVG-график динамики рисуется в DOM с цветами из
CSS-переменных текущей темы (перерисовка при смене темы). Поллинг статуса загрузки с прогрессом
по стадиям.

### Баг: LOWER() для кириллицы в SQLite без ICU

Текстовый поиск `q=биохим` возвращал 0, хотя в БД есть документ с title «Биохимические
исследования». Корень: SQLite без ICU (стандартная сборка Python) не опускает регистр для
non-ASCII — `LOWER('Биохимические')` = `'Биохимические'` (без изменений), а запрос `LIKE '%биохим%'`
в нижнем регистре не совпадает. Тот же баг молчаливо влиял на существующий `dynamics` (LIKE по
кириллическому `analyte_name`).

**Evidence** (до фикса, через `botkin.db.connection.get_conn`):
```
SQL: SELECT lower('Биохимические')  →  'Биохимические'   ← не lowercased
search(q='биохим')                  →  total=0           ← должно быть 1
search(q='крови')                   →  total=6           ← работает, потому что в данных уже lowercase 'к'
```
«крови» маскировало баг: в title «Общий анализ крови» слово «крови» уже с маленькой «к»,
поэтому совпадало даже со сломанным LOWER. «биохим» — с большой «Б» в данных — вскрывал баг.

**Фикс:** `conn.create_function("lower", 1, lambda s: s.lower() if isinstance(s, str) else s)`
в `get_conn()` — переопределяет builtin LOWER на Python-вариант. `str.lower()` — суперсет
ASCII-lower, поэтому существующие 316 тестов на латинице не сломались, а кириллица стала
регистронезависимой.

**Evidence** (после фикса, на live-сервере, user 113521070):
```
search(q='биохим')    →  total=1, title='Биохимические исследования'
search(q='инвитро')   →  total=15   (было 0 со старым LOWER — 'Инвитро' с большой 'И')
search(q='крови')     →  total=6
lower('Биохимические') → 'биохимические'
```

## Итерация 28: аудит веб-кабинета — stored XSS через имя показателя и off-by-one в датах

### Проблема

Свежесмерженный веб-кабинет (итерация 27) прошёл happy-path тестами (25 новых), но
серьёзного аудита безопасности и краевых случаев не было. Два параллельных Explore-агента
(архитектура backend + детальный разбор веб-части) выдали список кандидатов в баги.

### Диагноз (подтверждённые баги)

**1. Stored XSS в графике динамики.** Единственное место с `innerHTML` — `renderChart()`
(`app.js`): имя показателя и единица вставлялись в SVG-шаблон без экранирования:

```js
wrap.innerHTML = `<svg ... aria-label="Динамика показателя ${this.dynamics.analyte}">
...
<title>${fmtDateShort(p.taken_at)}: ${fmtNum(p.value_num)} ${this.dynamics.unit}</title>
```

Критично то, откуда берутся эти строки: `analyte`/`unit` **извлекаются OCR/LLM из
загруженного документа**. Вектор: документ с крафтовым названием анализа вида
`"><svg onload=...>` → сохранение в БД → исполнение при открытии графика. Весь остальной
UI использует безопасный `x-text` — уязвим был ровно один императивный шаблон.

**2. Off-by-one в фильтре дат.** `search()` сравнивал `created_at <= ?`, где `created_at` —
TIMESTAMP (`2026-06-10 12:30:00`), а фильтр шлёт голую дату (`2026-06-10`). Лексикографически
`'2026-06-10 12:30:00' > '2026-06-10'` → документы, созданные **в сам день date_to, выпадали**.

**3. Рассинхрон селектора и запроса динамики.** Селектор аналитики отдаёт
`COALESCE(analyte_canonical, analyte_name)`, а `dynamics()` искал по
`LOWER(analyte_name) LIKE '%…%'`. Если канон ≠ сырому имени (канон «Гемоглобин»,
`analyte_name`='HGB') — выбор из списка давал пустоту. Бонус-баг того же LIKE:
«Глюкоза» подмешивала точки «Глюкозы в моче» в одну серию с одной единицей.

**4. Потеря свежих точек.** `ORDER BY taken_at ASC LIMIT 60` при >60 замерах возвращал
60 **самых ранних** — график молча терял актуальные значения.

**5. Race conditions на всех fetch.** Ни одного sequence-guard: при быстрой смене
фильтров/показателей поздно пришедший старый ответ перезатирал свежие данные.

**6. Мёртвая ветка 404.** `api()` возвращает `null` на 404 (не бросает), поэтому
`catch` с `e?.message?.startsWith("404")` в `pickAnalyte` был недостижим — тост
«Нет данных по…» не показывался никогда.

**7. Коллизии `:key`.** `:key="r.analyte_name+r.value_num"` — дубли строк панели с
одинаковым именем+значением схлопывались Alpine; аналогично `:key="rep.diagnosis"` и
ключи по строкам жалоб/рекомендаций.

**8. Дырка стадии `processing`.** Массив стадий в `stageDone` не содержал `processing` →
`indexOf` = −1, чекпоинты прогресса «прыгали». Плюс логическая ошибка в разметке:
стадия «Распознавание» ждала `stageDone(item,'normalizing')` — то есть помечалась
done только при `extracted`.

### Решение (TDD: RED → GREEN)

Backend (5 новых тестов в `test_cabinet_repo.py`, 4 падали на старом коде):
- `created_at < date(?, '+1 day')` вместо `<=` — включает весь день;
- `dynamics()`: сначала точное совпадение по `LOWER(COALESCE(canonical, name))`,
  при пустоте — LIKE-fallback (частичный ввод из бота `/dynamics холестер` жив,
  тест-страж `test_dynamics_partial_input_falls_back_to_substring`);
- `ORDER BY taken_at DESC LIMIT ?` + `reversed()` — свежие точки в хронологическом порядке.

Frontend (новый `tests/test_cabinet_web.py` — app.js гоняется в node с заглушкой
localStorage; 4 из 5 тестов падали на старом коде, проверено прогоном против HEAD-версии):
- `escapeHtml()` + экранирование всех внешних вставок в SVG-шаблоне (тест-страж
  сканирует исходник: интерполяции `dynamics.analyte/unit/taken_at` в шаблонах —
  только под `escapeHtml`);
- `_req`-счётчики на `docs/doc/reports/dynamics`: ответ применяется только если он
  от последнего запроса;
- обработка `data === null` в `pickAnalyte` (тост «Нет данных…» ожил);
- `:key` по индексам; `processing` в порядок стадий + `stageDone(item,'recognizing')`
  в разметке.

### Итог

30 тестов кабинета (25 старых + 5 repo) + 6 node-тестов фронта. Полный прогон:
**345 passed**, ruff clean. Отдельно зафиксирован техдолг demo-этапа: аутентификации

## Итерация 29: температуры LLM, которые никогда не работали

### Проблема

При чистке мёртвого кода (по отчёту агента-архитектора) ruff внезапно пометил
`CLASSIFY_TEMPERATURE` и `VLM_TEMPERATURE` как неиспользуемые импорты — после удаления
мёртвого параметра `get_client(temperature=...)`.

### Диагноз

Параметр `temperature` в `get_client()` **игнорировался в теле функции** — все три вызова
передавали температуру в никуда:

```python
def get_client(temperature: float = 0.1, mode=instructor.Mode.JSON):
    return instructor.from_openai(get_raw_client(), mode=mode)   # temperature не используется
```

Реальная температура уходит в Ollama через `extra_body={"options": {...}}`. Проверка всех
вызовов показала: OCR-вызовы хардкодят `"temperature": 0.0` (осознанный детерминизм),
текстовый путь передаёт `TEXT_LAYER_TEMPERATURE`, а вот **классификация и structured-VLM
не передавали температуру вовсе** — работали на дефолте Ollama. При этом комментарий в
`classify.py` прямо жалуется: «модель при temperature>0 иногда путает тип» — и лечит это
пост-коррекцией по ключевым словам. Т.е. конфиг `vlm.classify_temperature: 0.1`
существовал, но эффекта не имел с самого рождения модуля.

RED-тест (мокнутый клиент, проверка kwargs вызова):

```
E       KeyError: 'temperature'
tests/test_llm_calls.py:431: KeyError
```

### Решение

- `classify`: `build_extra_body(ClassifySchema, options={**default_options(),
  "temperature": CLASSIFY_TEMPERATURE})`;
- `_call_vlm` (structured-извлечение): при `options is None` — дефолт
  `{**default_options(), "temperature": VLM_TEMPERATURE}`;
- OCR-вызовы не тронуты (хардкод 0.0 — намеренный детерминизм);
- 2 теста-стража: `test_classify_sends_configured_temperature`,
  `test_extract_sends_configured_vlm_temperature`.

`VLM_TEMPERATURE=0.0` в конфиге совпадает с прежним фактическим поведением extract-путей —
регрессии нет; классификация станет стабильнее (0.1 вместо дефолта Ollama), что нужно
перепроверить на GPU-прогоне корпуса.

Попутные чистки мёртвого кода: `normalize/numbers.py::parse_decimal` (использовался только
собственным тестом; прод считает через `scalars.parse_lab_value`), обёртки
`reconstruct_lines`/`source_text` и полностью мёртвая `_is_continuation_line` в
`pdf_text.py` (тесты переписаны на `open_pdf`/`reconstruct_pages`), исключения
`ConfigurationError`/`LLMError`/`DatabaseError` (нигде не возбуждались),
`BOT_POLLING_TIMEOUT` (нигде не читался).

### Итог

**346 passed**, ruff clean. Инсайт для доклада: мёртвый параметр опаснее мёртвой функции —
мёртвая функция просто лежит, а мёртвый параметр **создаёт иллюзию управления**: три

## Итерация 31: жизненный цикл документа — дедупликация, исходники, удаление, репарсинг

### Постановка

Кабинет умел только накапливать: повторная загрузка того же бланка плодила дубли
в статистике и динамике, оригинал документа был недоступен (только извлечённые данные),
удалить или заново распарсить документ было нельзя. Плюс два UX-долга: списки грузились
лишь после манипуляций с фильтрами, массовых операций не было.

### Дедупликация: правило достоверности

Пользователь загружает один документ повторно по разным причинам (переслал ещё раз,
пере-скан, «а вдруг теперь лучше распознается»). Храним ОДИН экземпляр с максимально
достоверными данными. Правило (все ветки под тестами `tests/test_dedupe.py`, 6 шт.):

- количество извлечённых записей **не изменилось**, значения другие → пишем **новые**;
- количество **уменьшилось** → новый прогон потерял строки, остаются **старые**;
- количество **выросло** → новый прогон полнее, побеждают **новые**.

Реализация красиво легла на «обновление через удаление»: победитель — целый документ,
проигравший удаляется целиком (строки + document + файл-исходник). Никаких merge'ей
на уровне отдельных показателей — источник истины всегда один прогон.

Дубликат распознаётся двумя способами: `sha256` содержимого файла (новая колонка
`documents.file_sha256`, пишется при upload; идемпотентная миграция ADD COLUMN) —
точный повтор; либо совпадение `(doc_type, title, clinic)` — пере-скан того же бланка.
Проверка тенант-скоупа обязательна: одинаковый документ у РАЗНЫХ пользователей — не дубль
(тест `test_dedupe_scoped_to_user`).

Хук в pipeline — между персистом и финальным статусом: `dedupe_document()` в
`orchestrator._run`. Если новый документ проиграл — пользователю уходит уведомление
«уже был загружен», а фронт-поллинг статуса получает 404 и показывает состояние
«Уже был загружен» (state `duplicate` в очереди загрузки). Известное ограничение:
бот-поллинг при таком исходе дотекает до таймаута (push-уведомление о дубликате
приходит отдельно) — не чинили, т.к. косметика.

### Исходники, удаление, репарсинг

- `GET /api/documents/{id}/source` — отдача оригинала (FileResponse, media-type по
  суффиксу; HEIC/HEIF добавлены руками — `mimetypes` их не знает). Фронт открывает
  через `fetch → blob → createObjectURL`: заголовок идентификации в `window.open`
  не передать.
- `DELETE /api/documents/{id}` — атомарное удаление документа со строками
  (транзакция в `DocumentRepo.delete`) + файл; чужой документ → 404, данные целы.
- `POST /api/documents/delete-batch` — массовое; чужие/несуществующие id тихо
  пропускаются (идемпотентность).
- `POST /api/documents/{id}/reparse` — «обновить»: очистка labs/reports/raw_extraction,
  статус `received`, перезапуск `process_document` тем же `BackgroundTasks`-путём,
  что и upload. Файл утрачен → 409 с человеческим объяснением. Прогресс репарсинга
  виден в той же очереди, что и обычная загрузка (переиспользован `pollStatus`).

### Дебаг-вход и деплой

`WEB_DEBUG_USER_ID` (env): если задан и заголовок `X-Telegram-User-Id` отсутствует —
API работает от имени этого пользователя. Отсутствие заголовка без флага теперь
даёт честный 401 (раньше FastAPI отвечал 422 на отсутствующий обязательный Header).
Живая проверка: `curl http://127.0.0.1:8902/api/me` без заголовка → профиль
debug-пользователя. Инструкция по выкатке кабинета в интернет (Cloudflare Tunnel /
ngrok / VPS+Caddy / Tailscale, systemd, предупреждения безопасности) —
`docs/deploy-local-web.md`.

## Итерация 32: инструмент «ожидания vs реальность» — бенч моделей одним запуском

### Постановка

Для статьи нужен воспроизводимый способ сверять публичные бенчи моделей с их реальным
поведением на русских медицинских документах. Вручную это делалось в итерации 25
(замер 5 моделей), но без автоматической привязки к «ожиданиям» и без готового отчёта.

### Решение

`scripts/bench/bench_expectations.py` — надстройка над существующим
`bench_models.py` (переиспользует `run_model`/`ModelResult`, ничего не дублирует):

- **Ожидания** зашиты таблицей `EXPECTATIONS` с числами ТОЛЬКО из
  `docs/ocr-models-research-2026-07.md` (Часть 2) и URL первоисточников: OmniDocBench
  с указанием версии бенча, заявленная скорость с оговоркой про GPU, диск, статус
  русского. Незнакомая модель получает честную заглушку «н/д», а не выдуманные числа.
- **Реальность** — прогон e2e-корпуса (34 документа с sidecar-эталонами) через
  реальную Ollama; точность/PASS-rate/с/док.
- Отчёт `bench_expectations_report.md`: таблица «ожидание vs реальность» + паспорт
  ожиданий с источниками + детали провалов по документам + железо прогона
  (nvidia-smi) — без него колонка скорости бессмысленна.
- `--pull` подтягивает отсутствующие модели; дефолт: qwen3-vl:8b-instruct (боевая),
  glm-ocr (кандидат №1), qwen2.5vl:7b (прошлая база).

Чистые функции (матчинг ожиданий, вердикты, рендер отчёта) — под тестами без Ollama
(`tests/test_bench_expectations.py`, 3 шт.). Попутная находка: при загрузке модуля
через `importlib.util.spec_from_file_location` + `exec_module` **обязательно
регистрировать модуль в `sys.modules` ДО exec** — иначе dataclass-аннотации внутри
модуля падают на `sys.modules.get(cls.__module__).__dict__` с
`AttributeError: 'NoneType'` (dataclasses.py:749, CPython 3.12).

Для автономного прогона на GPU-машине написан промпт для Devin
(`docs/devin-prompt.md`): setup, задачи (бенч → обновление docs → фактура в журнал
по формату итераций), железные правила Stop-list (не выдумывать числа), Definition
of Done. Смысл: агент без контекста сессии может продолжить накопление фактуры.

### Итог

**367 passed** (`-m "not llm"`), ruff clean. Смоук без Ollama: скрипт корректно
скипает недоступные модели и завершает работу с пояснением. Реальный GPU-прогон —
следующий шаг (руками или через Devin).

умолчанию. Для vision/OCR задач через Ollama весь вывод уходит в `thinking`
field, `content` остаётся пустым
([ollama/ollama#14502](https://github.com/ollama/ollama/issues/14502)):

> «all output goes into the thinking field and content is always empty when
> images are involved. Tried everything: 'thinking': False in options —
> ignored for image inputs, /no_think in prompt — treated as literal text»

125.4 с/док — в 5 раз медленнее qwen3-vl. Extract синтетического бланка:
98.9с (vs ~15с у qwen3-vl) — модель генерирует reasoning tokens вместо

## Итерация 37: e2e-бенч qwen3-vl vs gemma4 — скорость, точность, варианты оптимизации

### Диагноз (текущий пайплайн)

Пути извлечения (`src/botkin/llm/extract.py`):
1. **text_layer** (цифровой PDF) → `TEXT_MODEL` compact → verbatim/completeness_guard
2. **OCR-primary** (скан/фото/растровая страница) → free-text OCR (`OCR_MODEL`) →
   structure_text → optional structured VLM fallback
3. **Доменные ветки**: Андрофлор (parser + voting), СИБР (special OCR + voting)

Факторы стоимости:
- `config.json`: `image.extract_long_side=2200` (выше дефолта 1280) → больше vision-токенов
- `bench_models.py` ставит `TEXT_MODEL=VLM_MODEL` — при gemma text-структурирование

- Ollama `ps` показывает CONTEXT=32768 при запросах с `num_ctx=8192` — модель часто

- Voting (`_ANDROFLOR_VOTING_TRIES=3`, `_SIBR_VOTING_TRIES=3`) умножает вызовы на hard-кейсах
- У gemma: runaway generation (sample_007: out=9207 tok, extract 391s)

```bash

### Варианты оптимизации (ранжировано)

**Скорость (qwen, production-путь):**
1. Разделить `TEXT_MODEL` (лёгкий text-only, напр. `qwen3:8b`) от `VLM_MODEL` — не

6. Доменные парсеры ОАК/ОАМ (как Андрофлор/СИБР) — меньше LLM-шума.
