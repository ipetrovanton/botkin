# RAG из медицинских справочников + синхронизация Garmin/Strava/Apple Health в локальный кабинет

> Дата начала: 2026-07-04
> Стек: Python 3.12, FastAPI, SQLite, Ollama (qwen3-vl:8b-instruct, bge-m3), aiogram, Alpine.js SPA

## Постановка

Две задачи. Первая: из уже загруженных структурных справочников (ГРЛС — 20 948 лекарств,
ФСЛИ — 5 924 лабораторных теста, оба в `src/botkin/reference/*/registry.jsonl`) собрать
RAG-слой, чтобы локальная LLM могла давать рекомендации по лечению, опираясь на проверенные
данные, а не на память модели. Вторая: синхронизировать данные о здоровье из Garmin
Connect / Strava / Apple Health (пульс, давление, сон, активность) в локальную БД с привязкой
к пациенту, дать управление подключением через веб-кабинет и включить эти данные в тот же
RAG-слой для анализа локальной LLM.

Критерий успеха: (1) поиск по справочникам возвращает релевантные записи по свободному
запросу; (2) реальные данные из Garmin Connect (тестовый аккаунт) лежат в SQLite с привязкой
к пользователю и видны в кабинете; (3) LLM-запрос «рекомендации» получает в контекст выдержки
из справочников и свежие health-метрики.

## Контекст и ограничения

- Окружение: Windows 11 + WSL2 (Ubuntu) с Ollama (`OLLAMA_HOST=0.0.0.0`), Python 3.12, uv.
- В проекте уже есть: пайплайн распознавания документов, SQLite-схема (users, documents,
  lab_results, doctor_reports), веб-кабинет SPA, фаззи-нормализация лекарств/анализов по тем
  же справочникам (RapidFuzz).
- В Ollama уже скачан `bge-m3:latest` — кандидат на эмбеддинги.
- Официального API у Garmin Connect для физлиц нет (Health API — только для компаний-партнёров),
  придётся исследовать неофициальные библиотеки.
- Секреты (логин/пароль Garmin) — только в `.env`, не в репо.
- Медицинская специфика: RAG не должен «лечить» сам — только снабжать модель фактурой
  из официальных реестров; ответственность за назначения остаётся за врачом.

## План

1. Исследование RAG-стека: чем эмбеддить (bge-m3 через Ollama) и где хранить вектора
   (sqlite-vec vs numpy brute-force) — с учётом того, что БД проекта и так SQLite.
2. Исследование Garmin Connect: неофициальные API (python-garminconnect, garth), какие
   эндпоинты отдают пульс и давление, что пишут на форумах про экспорт «всего».
3. Исследование Strava API (официальный OAuth) и Apple Health (export.xml / Health Auto Export).
4. Схема хранения: таблицы связанных аккаунтов и универсальная таблица health-метрик
   (time series) с привязкой к user_id.
5. Модуль RAG: индексация справочников + health-сводок, ретривер, интеграция в LLM-промпт.
6. Сервис синхронизации Garmin + API-роуты + экран кабинета.
7. Тесты: unit с моками, живой прогон против Garmin Connect на тестовом аккаунте.

## Ход работы

### Шаг 1: исследование — чем и куда класть вектора

- В Ollama НЕ оказалось `bge-m3`, хотя AGENTS.md его обещал (`ollama list` вернул только
  vision/text-модели). Поставил на скачивание: `wsl -d Ubuntu -- ollama pull bge-m3` (1.2 ГБ).
- `sqlite-vec` 0.1.9 на PyPI имеет колёсико `win_amd64` — нативное расширение SQLite
  заведётся на Windows-хосте без компиляции (проверил через JSON API PyPI).
- Справочники: ГРЛС — 20 948 записей `{name, type: trade|mnn|both, mnn, statuses, reg_numbers}`;
  ФСЛИ — 5 924 записи `{name, synonyms[], units[], group}`. Оба уже лежат в
  `src/botkin/reference/*/registry.jsonl` и используются фаззи-нормализацией.

### Шаг 2: исследование Garmin Connect (субагент, сводка)

- Официальный Garmin Health API для физлиц НЕДОСТУПЕН: программа для новых заявок
  приостановлена, только юрлица с лицензией.
- Рабочий путь — неофициальная библиотека `garminconnect` (cyberjunky/python-garminconnect),
  v0.3.6 от 14.06.2026, Python >=3.12, требует `curl_cffi` (Cloudflare TLS fingerprinting:
  обычный `requests` ловит 403, curl_cffi имитирует Chrome).
- Авторизация: email/пароль → OAuth-токены, хранятся в `~/.garminconnect/garmin_tokens.json`
  (путь переопределяется env `GARMINTOKENS`). Refresh-токен живёт ~30 дней и ротируется,
  при регулярной синхронизации сессия вечная. Повторные логины по паролю опасны:
  rate limit на SSO (429 → блок на 48 ч, привязан к email, не к IP) — логинимся один раз,
  дальше только токены.
- Методы: `get_heart_rates(date)` (внутрисуточный пульс + resting), `get_blood_pressure(date)`
  (Garmin Index BPM и ручные записи), `get_sleep_data`, `get_steps_data`, `get_hrv_data`,
  `get_all_day_stress` (+ body battery), `get_weigh_ins`, `get_activities_by_date`,
  `download_activity(..., ORIGINAL)` — FIT-архив.
- Альтернативы для справки: GarminDB (SQLite, отдельная экосистема), garmin-grafana
  (InfluxDB+Grafana), privacy-экспорт архива аккаунта (24–48 ч, ручной).

### Шаг 3: исследование Strava и Apple Health (субагент, сводка)

- Strava API v3: официальный OAuth2 (scopes `read,activity:read_all`), лимиты 100/15 мин и
  1000/день. Отдаёт ТОЛЬКО активности и их стримы (heartrate, watts, cadence...). Давления,
  пульса покоя, сна, HRV в Strava НЕТ — для медицинских метрик источник слабый.
  Требует регистрации приложения (client_id/secret) — подключение делаем конфигурируемым.
- Apple Health: облачного API НЕ существует (HealthKit — только на устройстве). Два пути:
  (а) ручной экспорт `export.zip` (внутри `export.xml`, бывает >1 ГБ — парсить только
  потоково через `iterparse`), типы `HKQuantityTypeIdentifierHeartRate`,
  `...BloodPressureSystolic/Diastolic`, `...RestingHeartRate`, `SleepAnalysis` и др.;
  (б) приложение Health Auto Export шлёт JSON на свой REST-эндпоинт — де-факто стандарт
  self-hosted синхронизации по отзывам r/selfhosted.

### Шаг 4: проверка гипотез на стенде

- `uv add garminconnect sqlite-vec` → garminconnect 0.3.6 + curl_cffi 0.15.0, sqlite-vec 0.1.9.
- sqlite-vec завёлся на Windows-Python 3.12 с первого раза: `vec_version() = v0.1.9`
  (страх насчёт `enable_load_extension` на Windows не подтвердился).
- bge-m3 через `/api/embed`: 1024-мерные вектора, первый вызов 16.9 с (холодная загрузка
  модели в VRAM), дальше — миллисекунды.
- Живой логин в Garmin Connect: библиотека перебирает стратегии, `mobile+cffi` и
  `mobile+requests` получили `429 — IP rate limited by Garmin`, но widget-фоллбек прошёл.
  Ровно то, о чём предупреждали GitHub-issue #344 — повторных логинов надо избегать.
- Возобновление сессии по сохранённым токенам (без пароля) — работает. Реальные данные:
  `get_heart_rates` отдаёт resting HR и до 720 точек пульса в день;
  `get_blood_pressure` за месяц — пустой список (у аккаунта нет тонометра Garmin Index),
  значит коннектор обязан спокойно жить с пустыми ответами по любой метрике.

### Сложность: PowerShell глотает кириллицу и жуёт JSONL

- **Симптом:** `Get-Content registry.jsonl -TotalCount 3` возвращает пусто, python `print`
  с кириллицей в один слэш-командой — `SyntaxError: unterminated string literal`.
- **Гипотезы:** кодировка консоли cp1251/cp866 vs UTF-8 файлов; экранирование кавычек
  PowerShell → Python.
- **Что пробовал:** `type` — пусто; `[IO.File]::ReadAllText` — пусто; многострочный
  `python -c` с `$env:PYTHONIOENCODING='utf-8'` — работает.
- **Решение:** все ad-hoc проверки — через `uv run python -c` с PYTHONIOENCODING=utf-8
  и без вложенных двойных кавычек; для консоли `[Console]::OutputEncoding=UTF8`.
- **Урок:** на Windows-хосте единственный надёжный способ смотреть UTF-8-данные — сам Python.

### Шаг 5: реализация

- БД: +5 таблиц (`health_accounts`, `health_metrics` с UNIQUE(user, provider, metric,
  taken_at) — синк идемпотентен, `health_activities` по external_id, `rag_chunks`;
  vec0-таблица `rag_vectors` создаётся кодом — schema.sql исполняется в init_db без
  загруженного расширения sqlite-vec и о виртуальных таблицах знать не должен).
- `botkin/rag/`: embeddings (батчи по 64 в `/api/embed`), store (тонкий адаптер над
  sqlite-vec: upsert чанков + KNN с фильтрами source/user), indexer (запись справочника →
  русскоязычный чанк: «Лекарственный препарат "Липримар" (торговое название).
  действующее вещество: Аторвастатин. статус в реестре ГРЛС: активен»), retriever,
  recommend (промпт с тремя слоями контекста: отклонения анализов + лекарства из
  заключений + агрегаты носимых устройств + RAG-выдача).
- `botkin/health/`: garmin (connect/resume/fetch: пульс 720 точек/день, resting HR, сон
  с фазами, шаги, стресс, body battery, HRV, давление, вес, активности), apple
  (export.zip потоково через iterparse + JSON Health Auto Export), strava (OAuth-флоу).
- API: `/api/health/*` (подключение, фоновый синк с прогрессом, серии, активности,
  импорт), `/api/rag/*` (reindex, search, recommend). Экран «Здоровье» в SPA.
- Приватность в RAG: health-чанки несут user_id и отфильтровываются в поиске для чужих;
  справочники (user_id IS NULL) видны всем.

### Сложность: node -e упёрся в лимит командной строки Windows

- **Симптом:** после добавления кода экрана «Здоровье» 7 тестов app.js упали:
  `FileNotFoundError: [WinError 206] Имя файла или его расширение имеют слишком большую длину`.
- **Гипотезы:** сломан node; кириллица в скрипте; длина аргумента.
- **Решение:** тесты передавали ВЕСЬ app.js аргументом `node -e "<скрипт>"`; app.js вырос
  с 27 до 36 КБ и перешагнул лимит CreateProcess (32 767 символов). Теперь скрипт пишется
  во временный файл и запускается `node file.js`.
- **Урок:** на Windows любые «скрипт в аргументе» решения — бомба замедленного действия;
  файл надёжнее всегда.

### Сложность: .gitignore-паттерн _*.py съел __init__.py

- **Симптом:** запись `src/botkin/rag/__init__.py` отклонена: «файл в ignore».
- **Решение:** паттерны отладочных файлов `_*.py`, `_*.log` и т.п. в .gitignore были без
  якоря и матчили `__init__.py` в ЛЮБОЙ директории (старые `__init__.py` жили в индексе
  только потому, что были добавлены раньше). Заякорил на корень: `/_*.py`.
- **Урок:** gitignore-паттерн без `/` действует рекурсивно во всех подкаталогах —
  проверяй `git check-ignore -v`.

### Шаг 6: живой прогон

- Индексация справочников: 26 872 чанка (20 948 ГРЛС + 5 924 ФСЛИ) за 463 с на RTX 3080,
  ~110 МБ векторов в botkin.db.
- Синк Garmin за 30 дней: 21 013 метрик (20 835 точек пульса, 30 resting HR, 29 ночей сна,
  шаги, стресс, HRV, body battery) + 16 активностей за 113 с; 5 недельных RAG-сводок.
- Семантический поиск: «аторвастатин от холестерина» → торговые имена со статином;
  «как я спал на этой неделе» → недельные health-сводки. Мультиязычный bge-m3 держит
  русскую медицинскую терминологию уверенно.
- Ассистент (qwen3:8b): на вопрос про холестерин и пульс честно ответил, что значений
  холестерина в данных НЕТ (не выдумал!), разобрал реальный пульс покоя 58.6–62.1 из
  Garmin, прокомментировал реальные препараты пациента из заключений и закончил
  напоминанием про врача. 397 unit-тестов зелёные, ruff чист.

## Архитектурные решения

### Решение: векторное хранилище — sqlite-vec в основной botkin.db

- **Альтернативы:** (a) numpy brute-force в памяти + BLOB-персистенция — просто, но ручная
  синхронизация кэша и ~110 МБ RAM постоянно; (b) FAISS/Chroma/Qdrant — отдельный сервис
  или тяжёлая зависимость ради 27 тыс. векторов; (c) sqlite-vec — нативное расширение SQLite.
- **Выбрано:** sqlite-vec: проект и так живёт на SQLite, KNN прямо в SQL, есть win_amd64
  wheel, 27k×1024 float32 ≈ 110 МБ на диске, поиск <10 мс.
- **Компромисс:** нативное расширение (enable_load_extension) — риск несовместимости
  среды; закрываем тонким адаптером store.py и smoke-тестом.
- **Когда пересмотреть:** >1 млн векторов или потребность в фильтрации по метаданным
  внутри KNN.

### Решение: эмбеддинги — bge-m3 через Ollama

- **Альтернативы:** (a) nomic-embed-text — слабее на русском; (b) sentence-transformers
  локально в Python — вторая инференс-инфраструктура рядом с Ollama; (c) bge-m3 в Ollama.
- **Выбрано:** bge-m3 (1024-dim, мультиязычный, сильный на русском) — инференс уже
  централизован в Ollama, клиентский код — один HTTP-вызов `/api/embed`.
- **Компромисс:** зависимость от доступности Ollama при индексации и каждом поиске.
- **Когда пересмотреть:** если ретрив по медицинской терминологии окажется слабым —
  посмотреть на специализированные медицинские эмбеддеры.

### Решение: приоритет источников health-данных

- **Альтернативы:** пилить все три коннектора сразу / только Garmin.
- **Выбрано:** Garmin — полный коннектор (есть тестовый аккаунт, покрывает давление и пульс);
  Apple Health — приём `export.zip`/Health Auto Export JSON (реализуемо и тестируемо
  синтетикой); Strava — OAuth-флоу за конфигом (без зарегистрированного приложения
  живьём не проверить, и медицинских метрик там всё равно нет).
- **Компромисс:** Strava end-to-end не проверяется в этой итерации.
- **Когда пересмотреть:** пользователь зарегистрирует Strava-приложение и даст client_id.

### Решение: хранение секретов Garmin

- **Альтернативы:** (a) пароль в БД (даже «зашифрованный» ключом рядом — театр безопасности);
  (b) пароль только в момент подключения, в БД/на диске — лишь OAuth-токены.
- **Выбрано:** (b) — пароль живёт один HTTP-запрос подключения, персистятся только токены
  garmin (каталог `data/health_tokens/<user_id>/garmin/`, вне git). Refresh продлевается
  фоновой синхронизацией.
- **Компромисс:** раз в ~30 дней без синка токен умрёт — потребуется переподключение.
- **Когда пересмотреть:** многопользовательский прод — нужен нормальный секрет-менеджер.

## Итог

- Критерий 1 выполнен: RAG-поиск по 26 872 записям справочников работает, релевантность
  на живых запросах хорошая, индекс лежит в той же SQLite (sqlite-vec).
- Критерий 2 выполнен: реальные данные Garmin Connect (21k точек за месяц) в
  `health_metrics` с привязкой к пользователю; подключение и синк — из веб-кабинета,
  пароль не персистится (только OAuth-токены). Apple Health — импорт export.zip и
  эндпоинт для Health Auto Export (проверено синтетикой). Strava — OAuth готов, но без
  зарегистрированного приложения вживую не проверялся (и медицинских метрик в её API нет).
- Критерий 3 выполнен: `/api/rag/recommend` собирает контекст (анализы + лекарства +
  health-агрегаты + RAG) и локальная LLM отвечает по фактуре, не фантазируя.
- Не доделано: у тестового аккаунта нет тонометра Garmin Index — ветка давления
  проверена только на пустом ответе; интерактивный «чат» с историей — за рамками итерации.
- Чему научились: официального API Garmin для физлиц нет — неофициальный путь жизнеспособен,
  но требует дисциплины с токенами (429 → блок на 48 ч); sqlite-vec на Windows заводится
  без боли; bge-m3 достаточно для русской медицинской терминологии; RAG-чанки лучше
  писать человекочитаемым русским текстом, а не сырым JSON.
