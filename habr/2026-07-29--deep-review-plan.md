# Глубокое ревью проекта botkin и план-промт для легковесной модели

> Дата начала: 2026-07-29 14:47
> Стек: Python 3.12.9, FastAPI, aiogram 3, Ollama (qwen3-vl:8b-instruct), instructor, sqlite-vec, uv

## Постановка

Пользователь попросил провести глубокое ревью всего проекта (код, тесты, скрипты,
конфиги, модели) и написать детальный пошаговый план устранения недостатков,
пригодный как промт для легковесной модели. Требования к результату: академический
код, разделение слоёв, библиотеки вместо самописного, без мёртвых зависимостей,
e2e-тесты с метриками (скорость, tokens/sec, размер контекста, структурный diff),
промты отдельно от кода, предложения по оптимизации моделей/RAG/альтернативным VLM,
проверка актуальной версии Python и зависимостей.

Критерий успеха: `REVIEW_PLAN.md` с фазами и проверяемыми шагами.

## Контекст и ограничения

- Окружение: macOS (ревью), боевое — Windows + WSL2 + Ollama.
- Проект: ~23 700 строк Python (src + tests + scripts), 113 файлов тестов.
- Ограничение: план — только документ, правки кода не выполнялись.

## План

1. Обследовать структуру (src/tests/scripts/конфиги) — размеры модулей, мусор.
2. Проверить зависимости: реальные импорты vs pyproject, актуальные версии в сети.
3. Проверить актуальный Python и совместимость.
4. Ревью промтов и альтернативных локальных VLM (по свежим бенчам).
5. Написать `REVIEW_PLAN.md`.

### Шаг 2: зависимости — grep импортов vs pyproject

```bash
for pkg in ...; do grep -rE "(import|from) $pkg" src scripts tests -l | wc -l; done
```

- 0 импортов: `pyyaml`, `markdown`, `pydantic-settings`.
- Первый grep с якорем `^` дал ложные нули для `dotenv`/`fitz` — импорты бывают
  внутри `try:` с отступом. Перепроверил без якоря.

### Сложность: двойная система конфигурации

- **Симптом:** есть и `config.py` (678 строк, самописный merge env/json/defaults),
  и пакет `settings/` на 7 файлов, который никто вне себя не импортирует.
- **Гипотезы:** незавершённая миграция.
- **Что пробовал:** `grep -rn "from botkin.settings" src` — только внутренние импорты.
- **Решение (находка):** в `settings/loader.py` баг —
  `_project_root = Path(__file__).parent.parent.parent` указывает на `src/`,
  а не на корень: `config.json` оттуда не читается. Плюс `pydantic-settings`
  объявлен в зависимостях, но не используется — ровно та библиотека, что
  заменила бы самописный лоадер.
- **Урок:** полумиграции хуже отсутствия миграции — теперь два источника правды
  и рассинхрон дефолтов (`num_ctx` 8192 в config.json vs 16384 в `_DEFAULTS`).

## Архитектурные решения

### Решение: план как последовательность проверяемых шагов, а не список советов

- **Альтернативы:** свободное эссе-ревью / диф-патчи сразу.
- **Выбрано:** формат «Цель → Файлы → Действия → Приёмка → Проверка» на каждый шаг —
  легковесная модель выполняет шаг изолированно и сама верифицирует результат командой.
- **Компромисс:** объём документа больше; часть шагов исполнитель может счесть очевидными.
- **Когда пересмотреть:** если исполнитель будет путаться в зависимостях между фазами —
  добавить явный граф зависимостей шагов.

### Сложность: план содержал ошибочную рекомендацию — путал живые файлы состояния с дампами

- **Симптом:** при выполнении шага 1.1 плана обнаружено, что `TEST_RESULTS.md` (помечен
  в плане как «одноразовый отчёт» на удаление) явно упомянут в `HANDOFF.md`: «Итог
  последнего полного e2e-прогона см. в `TEST_RESULTS.md`». При выполнении шага 1.2
  аналогично: план предписывал перенести `bench_models_results.json`,
  `bench_expectations_results.json`, `bench_reasoning_results.json`,
  `bench_expectations_report.md` в `benchmarks/` с датой в имени — но эти файлы читаются
  и дописываются скриптами `bench_models.py`/`bench_expectations.py`/`bench_reasoning.py`/
  `bench_compare.py` на каждом прогоне (константа `RESULTS_FILE` внутри каждого).
  Переименование сломало бы сравнение с baseline. `bench_compare.py` был изначально
  ошибочно отнесён к «одноразовым debug-скриптам» и удалён, хотя он — задокументированный
  шаг воркфлоу в `HANDOFF.md`/`TEST_RESULTS.md`.
- **Гипотезы:** план составлялся по эвристике «файл похож на результат бенча/отчёт →
  переносить с таймстампом» без проверки, кто фактически читает/пишет файл в рантайме.
- **Что пробовал:** `grep -rn "bench_compare\|<имя файла>" HANDOFF.md TEST_RESULTS.md docs`
  перед каждым удалением — обнаружил обе ошибки до коммита.
- **Решение:** `bench_compare.py` восстановлен (`git checkout HEAD --`), JSON/MD файлы
  результатов возвращены на исходные пути без переименования, `TEST_RESULTS.md` не тронут.
  Текст `REVIEW_PLAN.md` в шагах 1.1/1.2 дополнен блоками «ВАЖНО (найдено при выполнении)»
  с точным описанием находки — план остаётся источником правды для следующих сессий.
- **Урок:** перед удалением/переносом любого файла, который выглядит как «результат» или
  «отчёт», обязательно грепать не только src/tests, но и *.md документацию, и сам код
  скриптов на предмет `RESULTS_FILE`/hardcoded путей — иначе легковесная модель, слепо
  следующая плану, сломает рабочий пайплайн бенчмарков.

### Сложность: Python 3.14 «не работает» — но проблема была не в Python

- **Симптом:** `uv run --python 3.14 pytest -q` — 5 тестов упали с
  `AttributeError: 'sqlite3.Connection' object has no attribute 'enable_load_extension'`
  в `src/botkin/rag/store.py` (sqlite-vec грузится через loadable extension).
- **Гипотезы:** (1) Python 3.14 сломал API sqlite3; (2) sqlite-vec не собран под 3.14;
  (3) конкретная сборка интерпретатора без поддержки loadable extensions.
- **Что пробовал:** проверил `hasattr(sqlite3.connect(':memory:'), 'enable_load_extension')`
  напрямую на interpreter'е, который резолвнул `uv run --python 3.14` (Homebrew/python.org
  символическая ссылка) — `False`. Установил Python 3.14.6 явно через `uv python install`
  (python-build-standalone) и повторил — `True`, все 557 тестов прошли.
- **Решение:** зафиксировал `.python-version` как generic `3.14` (не платформенный тег вида
  `cpython-3.14.6-macos-aarch64-none`), чтобы uv сам подбирал подходящую сборку под ОС
  (важно — прод на Windows+WSL2, а не macOS).
- **Урок:** системные сборки Python на macOS (Homebrew, python.org) часто линкуются с
  ограниченным Apple `libsqlite3` без loadable extensions — это давняя особенность macOS,
  не связанная с версией Python. Диагностировать через прямую проверку `hasattr` на
  РАЗНЫХ сборках одной версии, прежде чем списывать блокер на саму версию языка.

### Сложность: Фаза 3 плана изначально была основана на неверном диагнозе

- **Симптом:** план предписывал «достроить `settings/` на pydantic-settings, мигрировать
  импортёров, удалить `config.py`» — то есть считал `config.py` худшей реализацией.
- **Что пробовал:** перечитал `config.py` целиком (679 строк) вместо беглого просмотра из
  первого ревью. Оказалось: он уже строит типизированный `Settings(pydantic.BaseModel)` с
  единой функцией приоритета `setting()` (env → config.json → `_DEFAULTS`), а модульные
  константы — просто плоский реэкспорт для обратной совместимости. `grep -rn "from
  botkin.settings" src tests scripts` — импортов пакета `settings/` НЕТ нигде, кроме него
  самого. Также «рассинхрон» `config.json` vs `_DEFAULTS`, который план называл багом,
  оказался осознанной ручной настройкой оператора после бенчмарков (задокументирован в
  `TEST_RESULTS.md`).
- **Решение:** вместо запланированной миграции — удалил мёртвый пакет `settings/` целиком
  (269 строк) и убрал неиспользуемую `pydantic-settings` из зависимостей. `REVIEW_PLAN.md`
  переписан: Фаза 3 сокращена с «мигрировать всё» до «удалить дубликат», с явным объяснением
  почему `BaseSettings` не даст выгоды поверх текущей ручной реализации.
- **Урок:** первое ревью (быстрый просмотр 120 строк `config.py`) дало неверную оценку
  архитектуры. Прежде чем планировать миграцию «системы Х на систему Y» — прочитать файл
  ПОЛНОСТЬЮ и проверить фактическое использование через grep, а не полагаться на первое
  впечатление о размере/структуре файла.
