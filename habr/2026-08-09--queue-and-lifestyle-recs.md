# Очередь VLM с видимой позицией + lifestyle-рекомендации uncensored-моделью

> Дата начала: 2026-08-09 10:07
> Стек: Python 3.14.6, FastAPI, aiogram, Ollama, Alpine.js, pytest 8.4.2

## Постановка

Две дыры из списка техдолга: (1) при нескольких пользователях документы молча ждут
глобальный семафор VLM — нет ни позиции в очереди, ни понимания «почему висит»;
(2) собранные из всех источников данные (анализы, заключения, назначения, Garmin,
профиль) не сводятся в единую рекомендацию — есть только Q&A-ассистент по вопросу.

Критерий успеха: позиция очереди видна в веб-кабинете; endpoint `/api/rag/lifestyle`
отдаёт структурированную рекомендацию (образ жизни / физнагрузки / препараты /
взаимодействия) от мощной uncensored-модели; все unit-тесты зелёные.

## Контекст и ограничения

- Ветка `feat/pipeline-speed-accuracy` предварительно влита в `master` (fast-forward),
  работа в новой ветке `feat/queue-and-lifestyle-recs`.
- Жёсткий дедлайн сессии: 11:00 МСК (бюджет токенов).
- Без GPU: только unit-тесты с моками (`-m "not llm"`), живой прогон lifestyle-модели
  остаётся оператору.

## План

1. Влить ветку скорости в master, создать новую ветку.
2. `pipeline/queue.py`: FIFO-трекер поверх семафора, позиция документа.
3. Статус-endpoint + UI: «В очереди: N-й».
4. `recommend_lifestyle()`: агрегатор всех источников → uncensored-модель, промпт
   с четырьмя обязательными разделами.
5. Обновить цифры в статье (субагент, параллельно).

## Ход работы

### Шаг 1: очередь VLM с видимой позицией

Было: `LLM_SEMAPHORE = asyncio.Semaphore(1)` в `orchestrator.py` — сериализация без
наблюдаемости. Стало: `LlmQueue` (`src/botkin/pipeline/queue.py`) — тот же семафор,
но с учётом порядка ожидания:

```python
def position(self, document_id: int) -> int | None:
    """1-based позиция ожидания; 0 — выполняется; None — не в очереди."""
    if document_id in self._active:
        return 0
    try:
        return self._waiting.index(document_id) + 1
    except ValueError:
        return None
```

Ключевой нюанс — освобождение при отмене: waiter, отменённый пока ждёт семафор,
должен исчезнуть из `_waiting` (внешний `finally`), а активный — из `_active`
(внутренний). Тест `test_cancelled_waiter_leaves_queue` фиксирует именно это.

`GET /api/documents/{id}/status` теперь отдаёт `queue_position` и `queue_waiting`;
фронт показывает «В очереди на распознавание: N-й» вместо застывшего прогресс-бара.

TDD: 4 асинхронных теста (`tests/test_llm_queue.py`) — RED (модуля нет) → GREEN
(4 passed за 0.02s). Позиции FIFO гарантированы: семафор asyncio будит ждущих
в порядке постановки.

### Шаг 2: lifestyle-рекомендации uncensored-моделью

`recommend_lifestyle(user_id)` в `rag/recommend.py`. Переиспользован готовый
агрегатор `_patient_context` (профиль, отклонения анализов, назначенные лекарства,
агрегаты носимых устройств за 14 дней, погода/геомагнитка), дополненный новым
блоком `_reports_context` — диагнозы и рекомендации из последних 5 заключений
врача. Раньше в контекст попадали только `medications_json` из заключений,
сами диагнозы терялись.

Отличие от Q&A-ассистента (`recommend`): вопроса нет — ретрив по двум фиксированным
запросам («рекомендации по образу жизни и физическим нагрузкам», «взаимодействие
лекарственных препаратов») плюс адресный добор карточек ГРЛС по каждому принимаемому
препарату (до 8). Промпт `lifestyle_recommend.md` требует ровно четыре раздела:
Образ жизни / Физические нагрузки / Приём препаратов / Взаимодействия — и явное
«данных недостаточно» вместо фантазий.

Endpoint `POST /api/rag/lifestyle`, кнопка «Рекомендации по образу жизни» на экране
Ассистента. 4 новых теста (`tests/test_lifestyle_recommend.py`): контекст включает
диагноз/рекомендации врача, модель получает lifestyle-промпт (а не обычный RAG),
502 при недоступной Ollama.

## Архитектурные решения

### Решение: модель для lifestyle-рекомендаций

- **Альтернативы:** qwen3:8b (текущая RAG-модель) / gemma4 / huihui_ai/Qwen3.6-abliterated:27b.
- **Выбрано:** `huihui_ai/Qwen3.6-abliterated:27b` по умолчанию (`rag.lifestyle_model`,
  env `RAG_LIFESTYLE_MODEL`) — по бенчу `habr/bench-health-report` она дала лучший
  разбор полной истории болезни без цензурных отказов; qwen3:8b отказывается обсуждать
  дозировки, gemma4 на бенче слабее по полноте.
- **Компромисс:** 27B с оффлоадом в RAM отвечает минуты — поэтому отдельная настройка,
  а не замена основной RAG-модели; таймаут клиента 1800 с уже стоял для этого кейса.
- **Когда пересмотреть:** появление меньшей uncensored-модели с сопоставимым качеством
  на том же бенче (`POST /api/rag/benchmark` + `habr/bench-health-report`).

### Решение: очередь как обёртка семафора, а не брокер задач

- **Альтернативы:** очередь задач (arq/celery + redis) / таблица очереди в SQLite /
  обёртка над существующим `asyncio.Semaphore`.
- **Выбрано:** обёртка (`LlmQueue`) — 50 строк, ноль новых зависимостей, процесс
  один (uvicorn), состояние очереди живёт в памяти процесса, который и обрабатывает.
- **Компромисс:** очередь не переживает перезапуск (как и сами фоновые задачи —
  известный техдолг), позиция не видна из другого процесса.
- **Когда пересмотреть:** горизонтальное масштабирование API или требование
  реанимировать обработку после рестарта — тогда таблица в SQLite со статусом
  `queued` и воркером.
