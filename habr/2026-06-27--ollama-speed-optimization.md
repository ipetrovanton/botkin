# Оптимизация скорости локальной LLM: Ollama + qwen3-vl на RTX 3080 Laptop

> Дата начала: 2026-06-27 15:34
> Стек: Python 3.12, Ollama 0.30.11, qwen3-vl:8b-instruct (Q4_K_M), instructor; RTX 3080 Laptop 16 GB

## Постановка

`botkin` — сервис, который распознаёт медицинские документы (бланки анализов, заключения врачей) локальной vision-моделью и вытаскивает из них структурированные показатели. Всё крутится на одной мобильной RTX 3080 с 16 ГБ видеопамяти, без облака — данные медицинские, наружу им нельзя.

Проблема, с которой пришли: обработка одного документа занимала от 38 до 450 секунд. Полминуты ещё терпимо, но семь с лишним минут на тяжёлый бланк — это уже неюзабельно. Задача: найти причины медленности, проверить гипотезы замерами, внедрить фиксы — и не растерять при этом точность извлечения. Ограничение жёсткое: только Windows, переезд на Linux/Mac невозможен. Попутно решили мигрировать с Ollama внутри WSL2 на нативную Windows-сборку.

Критерий успеха: заметно быстрее без потери точности на тестовом стенде из 34 реальных документов.

## Контекст и ограничения

- **ОС:** Windows 11 + WSL2 (Ubuntu), Ollama 0.24.0 в WSL2
- **GPU:** NVIDIA GeForce RTX 3080 Laptop GPU, 16 GB VRAM
- **Модель:** `qwen3-vl:8b-instruct` (6.1 GB, Q4_K_M)
- **Пайплайн:** classify → extract → normalize → persist (`botkin` проект)
- **Тестовый стенд:** e2e-тесты на 34 реальных документах (PDF + JPG)
- **Ограничение:** решение должно работать на Windows без перехода на Linux/Mac

## План

1. Замерить скорость на raw API Ollama при разных настройках
2. Проанализировать исторические данные e2e-тестов
3. Сравнить WSL2 vs нативную Windows Ollama
4. Внедрить фиксы в `config.json` (num_predict, num_ctx, temperature)
5. Настроить подключение к нативной Windows Ollama
6. Запустить e2e-тест повторно для валидации

### Шаг 3: Корневые причины

**Причина 1: `num_predict=16384`** — модель получает «разрешение» генерировать 16K токенов. При скорости 21–40 tok/s это 410–780 секунд. Медицинский документ с 20 показателями требует ~500–800 токенов JSON.

**Причина 2: `num_ctx=16384`** — замедляет генерацию на ~15% (42.8 → 37.2 tok/s). Для одностраничного документа с ~2000 prompt-токенов ctx=4096 достаточно.

**Причина 3: `temperature=0.3`** — провоцирует «расползание» ответа: модель генерирует повторы и мусор, не останавливается до `num_predict`.

**Причина 4: Перезагрузка модели** — VLM-вызовы используют `num_ctx=16384`, text-model — `num_ctx=4096`. Смена ctx заставляет Ollama перезагружать модель (5–8s на каждый переход).

**Причина 5: Ollama 0.24.0 устарела** — актуальная 0.30.11 (25 июня 2026), между версиями обновление llama.cpp и улучшения для vision-моделей.

**Причина 6: WSL2 overhead** — нативная Windows Ollama на 10–13% быстрее по tok/s (источник: quickinference.com, бенчмарк на RTX 4080).

### Шаг 6: Fix 1 — temperature 0.3 → 0.0

Изменение: `config.json` → `vlm.temperature: 0.0`.

|---|---|---|---|
| 1 | **1.6** | **FAIL 1/3** | аномалия — модель перезагружалась после смены параметров |
| 2 | **10.8** | PASS 3/3 | |
| 3 | **11.1** | PASS 3/3 | |

**Сравнение с базовой линией:**
- Скорость: 10.8–11.1s vs 10.6s — в пределах погрешности (±0.5s).
- Стабильность: 2/2 PASS vs 1/2 PASS при temp=0.3. **Ключевое улучшение** — детерминированность.
- Аномалия прогона 1 (1.6s, FAIL): смена `temperature` в опциях заставляет Ollama перезагрузить модель. Первый inference после перезагрузки — крайне короткий и некачественный. Последующие прогоны стабильны.

**Вывод:** `temperature=0.0` не ускоряет, но делает результат детерминированным. Для OCR-задачи это критично.

### Сложность: Ollama 0.30.11 — пустые ответы при grammar-constrained generation

- **Симптом:** модель периодически генерирует пустой JSON `{"results": [], "tests": []}` за 1.3–1.5s. Перезагрузка Ollama временно помогает, но проблема возвращается.
- **Гипотезы:**
  1. Ollama 0.30.11 изменила обработку `format` (JSON schema) — XGrammar constraint может сваливаться в пустой, но валидный по схеме объект.
  2. `temperature=0.3` + grammar constraint — модель попадает в локальный минимум.
  3. `keep_alive` держит «плохое» состояние KV-cache между вызовами.
- **Что пробовал:**
  - `temperature=0.0` — модель тоже выдаёт пустые ответы, но реже.
  - Перезапуск Ollama — помогает на 1–2 прогона, потом проблема возвращается.
  - Выгрузка модели (`keep_alive=0`) — не помогает.
- **Решение:** пока не найдено. Нужно проверить, воспроизводится ли на WSL2 Ollama 0.24.0. Если нет — проблема в новой версии Ollama.
- **Урок:** обновление Ollama может сломать grammar-constrained generation для конкретной модели. Нужно тестировать перед обновлением.

**Ключевые наблюдения:**

1. **qwen3-vl:8b-instruct — безоговорочный лидер.** Лучше по всем трём метрикам: точность 98.5%, pass_rate 88%, score 0.0172. В 1.26x лучше minicpm-v по score, в 3.56x лучше gemma4, в 17x лучше qwen3-vl:30b-a3b.

2. **minicpm-v:8b — быстрая, но неточная.** Самая быстрая (26.3s/док, 2x быстрее qwen3-vl), но 16 FAIL из 34. Основные проблемы: ошибки классификации (doctor_report вместо analysis), пустые извлечения (0/20 на sample_006, 0/6 на sample_002). Модель фокусируется на OCR, но плохо справляется со структурированным извлечением JSON.

3. **gemma4:latest — медленная и нестабильная.** Худший pass_rate (41%), 20 FAIL. При этом единственная модель, которая правильно обработала sample_001 (PASS, 3/3). Провалила большинство JPG-документов (10 из 14 FAIL) — модель плохо классифицирует фото бланков.

4. **qwen3-vl:30b-a3b — непрактично для 16 GB VRAM.** Модель 19 GB, 22% уходит в CPU → extract 362–475s на документ (7–8 минут!). Даже будучи MoE (3B активных параметров), CPU-оффлоад съедает всю выгоду. Полный прогон занял бы ~3 часа.

### Сложность: CPU-оффлоад при превышении VRAM

- **Симптом:** `ollama ps` показывает `86%/14% CPU/GPU` для minicpm-v:8b (5.5 GB) при загруженной qwen3-vl:8b-instruct (5.8 GB). Extract sample_001 — 104s вместо ожидаемых 10–20s.
- **Причина:** Ollama не выгружает предыдущую модель автоматически при загрузке новой. Суммарно 5.8 + 4.9 = 10.7 GB помещается в 16 GB VRAM, но фрагментация или reserve не позволяет полностью загрузить вторую модель на GPU.
- **Решение:** перед запуском новой модели — `ollama stop` для всех загруженных. Добавлено в `bench_models.py`: цикл выгрузки всех моделей из `DEFAULT_MODELS` + `sleep(5)` для освобождения VRAM.
- **Урок:** при бенчмарке нескольких моделей на одной GPU — всегда выгружать предыдущую модель. `ollama ps` — обязательная проверка перед прогоном (100% GPU = правильно, любой % CPU = деградация 10–100x).

## Ход работы: точность

### Шаг 10: Оптимизация точности — чиним все 4 FAIL baseline

Скорость мы разогнали, но осталась вторая половина задачи — точность. Из 34 документов baseline четыре падали (FAIL). Разобрали каждый: у всех оказались разные корни — от бага движка до кривого текстового слоя бланка. Ниже — расследование по каждому и что в итоге помогло.

Напомню устройство пайплайна, чтобы дальнейшее читалось без сносок:

- **classify** — VLM смотрит на первую страницу и решает тип документа: `analysis` (анализы), `doctor_report` (заключение врача), `unknown`. Только `analysis` идёт дальше на извлечение показателей.
- **extract** — достаёт из документа список показателей (`LabResult`: имя, значение, единицы, референс). Два пути: разбор текстового слоя PDF лёгкой моделью либо чтение картинки vision-моделью.
- **XGrammar** — механизм в Ollama, который жёстко заставляет модель выдавать JSON строго по схеме (grammar-constrained generation). Обычно помогает, но, как выяснится, иногда ломается.

**Анализ FAIL-документов baseline:**

| Документ | Что за бланк | Значения | Корневая причина |
|---|---|---|---|
| sample_001 | Гемохелп, онкомаркеры (ROMA, Ca 125, HE4) | 1/3 | XGrammar вернул пустой, но валидный по схеме JSON за 1.3s |
| sample_004 | Тропонин (одиночный показатель) | 0/1 | Показатель полностью пропущен, 0 строк |
| sample_011 | Тонус, общий анализ крови, растровый PDF | 19/20 | «СОЭ (по Вестергрену)» не увидена внизу бланка |
| sample_013 | Анализ мочи | 35/36 | «pH мочи» слит в одну строку с «Относительной плотностью» |

**Внедрённые фиксы:**

1. **Adaptive fallback для grammar constraint** (`extract.py`). Симптом был обманчивый: модель отвечала за 1.3 секунды — подозрительно быстро — и отдавала пустой список показателей, формально валидный по схеме. Оказалось, XGrammar на плотной/сложной картинке иногда «схлопывает» вывод в пустой объект. Лечение простое: если structured-вызов вернул 0 строк, повторяем тот же запрос без grammar-ограничения (`structured=False`). Без принудительной грамматики модель пишет свободный JSON, а `instructor` (библиотека-валидатор поверх ответа LLM) всё равно приводит его к нашей схеме. Починило sample_001 (1/3→3/3) и sample_004 (0/1→1/1).

2. **Multi-result парсинг склеенных строк** (`text_layer.py`). В текстовом слое PDF бланк иногда сливает два показателя в одну физическую строку: `Относительная плотность 1017 г/л 1003 - 1035 pH 5.5 5 - 8`. Старый парсер брал только первый показатель, второй (pH) терялся. Новый проходит по строке, отрезая обработанные токены после каждого результата, и достаёт все. Попутно вскрылся коварный баг склейки чисел: функция, которая соединяет разбитые пробелом тысячи (`1 010` → `1010`), радостно склеивала и `5.5 5` в `5.55` — то есть съедала второй показатель ещё до парсинга. Ограничили склейку целыми числами. Починило sample_013 (35/36→36/36).

3. **num_predict=4096 для VLM** (вместо 2048). `num_predict` — потолок числа токенов, которые модель может сгенерировать за один ответ. На sample_006 (Фемофлор, 20 показателей с длинными латинскими названиями) 2048 токенов не хватило — модель обрывалась на 6-й строке. 4096 покрывает все документы стенда с запасом.

4. **Детерминированная починка классификации sample_011** (`config.py`, `classify.py`). Этот случай оказался самым хитрым и прошёл две итерации. Сначала мы думали, что проблема в СОЭ, которую vision-модель не видит внизу растрового бланка. Но когда остальные фиксы стабилизировались, sample_011 начал падать по другой причине: **classify выдавал `doctor_report` вместо `analysis`**, и извлечение вообще не запускалось. 

   Первая попытка — понизить недетерминизм: для классификации мы держим `temperature=0.1` (маленький шум помогает не застревать в ошибочном варианте на пограничных бланках), для извлечения — строгий `0.0`. Но 0.1 всё равно оставлял ~25% провалов: прогон `run_vlm` 4 раза подряд дал `doctor_report` один раз из четырёх, причём с уверенностью 1.0 — модель «уверенно ошибалась».

   Настоящее решение — не полагаться на температуру, а поймать ошибку детерминированным правилом. Модель при этом стабильно извлекала правильный заголовок — `title = "Общий анализ крови"`. А документ с таким названием является анализом по определению. Добавили в корректор классификации список однозначных лабораторных заголовков (`общий анализ`, `биохимический анализ`, `анализ крови/мочи`, ...): если он найден в `title`, тип принудительно ставится `analysis`, что бы ни выдал VLM. После этого — 5 прогонов из 5 дали `analysis`.

**Результат оптимизированного прогона (финальный):**

| Метрика | Baseline | Оптимизированный | Изменение |
|---|---|---|---|
| PASS | 30/34 | **34/34** | +4 |
| FAIL | 4 | **0** | -4 |
| Точность | 320/325 (98.5%) | **325/325 (100%)** | +1.5 п.п. |
| Время/док | 50.6s | **27.1s** | **-46%** |
| Score | 0.01718 | **0.03690** | **+2.1x** |

> Про «100%»: точность считается как доля найденных эталонных значений. В промежуточном прогоне (до фикса классификации) число было 305/305 — но знаменатель меньше 325, потому что sample_011 падал ещё на classify, его 20 значений вообще не доходили до сверки и в статистику не попадали. После фикса классификации документ снова участвует в сверке полностью и даёт 20/20 (включая ту самую СОЭ) — отсюда 325/325.

Итог по точности: **все 4 исходных FAIL закрыты**, при этом обработка ускорилась почти вдвое (побочный эффект уменьшения `num_predict`/`num_ctx` из Шагов 8–9). Score = (точность × pass_rate) / среднее_время вырос в 2.1 раза.

### Сложность: Adaptive fallback — баланс между точностью и скоростью

- **Симптом:** adaptive fallback добавляет дополнительный VLM-вызов (~10–30s) на документах, где structured VLM уже вернул 0. На 2 из 34 документов это замедлило прогон, но суммарно +1.8s/док — приемлемо.
- **Компромисс:** если structured VLM стал возвращать 0 на >20% документов, adaptive fallback превратится в узкое место. Нужен мониторинг частоты fallback.
- **Урок:** grammar constraint (XGrammar) — мощный инструмент для структурированного вывода, но не всесильный. На сложных/плотных изображениях он может сваливаться в пустой, но валидный по схеме объект. Adaptive fallback — надёжный страхующий механизм.

### Сложность: Multi-result парсинг — склейка тысяч vs десятичных

- **Симптом:** функция склейки чисел `_collapse_numeric_spaces` соединяла «5.5» и «5» в «5.55», потому что обе строки подходили под регулярку «просто число» (она допускала десятичную точку). Итог — второй показатель строки (pH 5.5) исчезал ещё до парсинга.
- **Решение:** склейку применяем только к целым числам (регулярка `^-?\d+$`). «1 010» → «1010» (разбитые пробелом тысячи), но «5.5 5» остаётся двумя токенами — двумя значениями.
- **Урок:** «магическое» regex-преобразование, написанное под один случай (тысячи), легко ломает другой (десятичные). Как только замечаете такое преобразование — заводите тест на оба типа входа сразу.

### Сложность: sample_011 — искали не тот корень

- **Симптом:** документ упорно оставался в FAIL, хотя бланк простой — обычный ОАК из лаборатории «Тонус». Изначальный диагноз был «vision-модель не видит СОЭ внизу растрового бланка» (19/20 значений). Мы потратили силы на добор пропущенной строки.
- **Что оказалось на самом деле:** после стабилизации остальных фиксов документ начал падать раньше — на этапе classify, который возвращал `doctor_report`. `extract` даже не запускался (0.0s в логе), и все 20 значений просто не доходили до сверки. То есть корень сместился, а мы по инерции чинили старую гипотезу.
- **Как поймали:** прогнали `run_vlm` на документе 4 раза — получили `doctor_report` 1 раз из 4, причём с `confidence=1.0`. Классический недетерминизм при `temperature>0`, замаскированный под «уверенный» ответ.
- **Решение:** детерминированный корректор по заголовку (см. фикс №4 выше) вместо надежды на удачный прогон.
- **Урок:** когда документ «мигает» между PASS и FAIL, первым делом смотрите, на каком этапе он падает *сейчас*, а не по памяти. Тайминги в логе (`extract 0.0s`) — самый честный индикатор: они сразу показали, что до извлечения дело не дошло.

### Сложность: гибридный fallback оказался мёртвым и сломанным кодом

Эту проблему нашли уже на код-ревью, разбирая, стоит ли выносить структурирование текста на отдельную лёгкую модель `qwen3:8b`.

- **Симптом:** в `_call_text` жила ветка «гибридного fallback»: если лёгкая text-only модель вернула 0 строк, повтори запрос vision-моделью. Выглядела разумно. Но при прямом прогоне она падала с `NameError: VLM_NUM_CTX is not defined` — код ссылался на константы, которые в модуль не импортированы.
- **Почему тесты молчали:** ветка включалась только при `use_vlm=True`, а это условие — `model != TEXT_MODEL`. В боевом конфиге `TEXT_MODEL` совпадал с `VLM_MODEL` (мы ранее откатили `qwen3:8b`), поэтому `use_vlm` всегда был `False`, и до сломанной строки исполнение не доходило. Классический мёртвый код: и не выполняется, и содержит баг, который ждёт своего часа.
- **Мини-эксперимент:** прежде чем удалять, проверили гипотезу «`qwen3:8b` регрессит на sample_001» из прошлой сессии. Изолированное структурирование этого бланка через `qwen3:8b` давало 3/3 — регрессия «в пробирке» не воспроизвелась. Но позже на честном сравнении end-to-end картина перевернулась (см. следующую «Сложность»): `qwen3:8b` выдаёт непустой, но неверный результат в половине прогонов, а `qwen3-vl` с ретраем — стабильнее.
- **Решение:** убрали мёртвую ветку и параметр `model` из `_call_text` целиком — заодно исчезли 5 строк тернарных `X if use_vlm else Y`. `TEXT_MODEL` оставили равным VLM.
- **Урок:** мёртвый код опасен вдвойне — он не только шумит, но и накапливает необнаруживаемые баги. Если ветка не покрыта ни одним боевым сценарием, её надо либо покрыть, либо удалить, а не оставлять «на будущее».

### Сложность: нестабильность прохождения тестов — adaptive fallback был только на картинках

Самая коварная проблема: `sample_001` то PASS, то FAIL между прогонами без единой правки кода. Пример «плохого» прогона: `extract 1.6s`, найдено 1/3 значений, а вместо онкомаркеров — мусор `Антиген аденогенных раков Са: 125.0`.

- **Симптом:** `extract 1.6s` подозрительно быстр для реального LLM-вызова. Прогнали `run_analysis` на бланке 6 раз подряд и залогировали каждый вызов структурирования:

  ```
  Rows: 3 | 18.7s   ← OK
  Rows: 0 | 29.2s   ← пустой ответ
  Rows: 3 | 24.7s   ← OK
  Rows: 3 | 25.4s   ← OK
  Rows: 0 | 9.7s    ← пустой
  Rows: 0 | 2.8s    ← пустой (те самые ~1.6s)
  ИТОГ: 3/6 прогонов дали 3/3
  ```

- **Корень:** тот же баг пустого ответа XGrammar, что мы уже лечили на картиночном пути, — но `_structure_text` (разбор **текстового слоя** PDF) ретрая не имел. Adaptive fallback добавили только в `_vlm_extract_with_retry` (картинки), а симметричный текстовый путь про него «не знал». Когда LLM возвращала 0 строк, документ спасал только детерминированный `completeness_guard` — и на кривом тексте бланка (имя «Ca 125» с числом внутри) он лепил мусорную строку `125.0` вместо реальных ROMA/Ca125.
- **Что пробовали:**
  - *Симметричный ретрай без grammar* в `_structure_text` — как на картинках. Стабильность выросла 3/6 → **5/6**. Остался редкий (1/6) двойной пустой ответ: и structured, и unstructured вернули 0.
  - *Сменить `TEXT_MODEL` на `qwen3:8b`* (text-only, в изоляции казался стабильнее). На честном end-to-end оказалось **хуже — 3/6**: модель не отдаёт пустой ответ (ретрай не срабатывает), но структурирует неверно. Отвергли.
  - *Ограниченный цикл повторов* (`_TEXT_EMPTY_RETRIES=2`): пустой ответ дешёвый (0.8–3s), поэтому пара лишних попыток почти бесплатна. Результат — **6/6 стабильно**.
- **Решение:** adaptive fallback в `_structure_text` с бюджетом в 2 unstructured-повтора. Плюс регрессионные тесты, фиксирующие и поведение ретрая, и его ограничение.
- **Урок:** дублирующиеся по смыслу пути (структурирование картинки и структурирование текста) должны получать одинаковые страховки. Асимметрия «на одном пути ретрай есть, на другом нет» — источник плавающих багов, которые не ловятся одним прогоном. И: «стабильно в изоляции» ≠ «стабильно end-to-end» — мерить надо на полном пайплайне.

### Сложность: число внутри имени аналита читалось как значение

- **Симптом:** на строке `Антиген аденогенных раков Са 125 8.13 Ед/мл < 35 ...` парсер брал «125» (часть имени онкомаркера **Ca 125**) за значение и плодил фантом `Антиген аденогенных раков Са = 125.0`. Реальное значение 8.13 при этом уезжало в «единицу». На e2e фантом не ронял тест (сверка по значению), но в проде попал бы в БД как ложный показатель.
- **Ключ к решению — соседний контекст токена.** Надо было отличить три похожих паттерна «число число …»:
  - `Са 125 8.13 Ед/мл` — за числом идёт ещё число, а потом **единица** → первое число из имени;
  - `pH 5.5 5 - 8` — за числом число, а потом **тире** → «5 - 8» это референс, 5.5 — значение;
  - `1 010 150` — за числом снова **число** → разбитые пробелом тысячи, не трогаем.
- **Решение:** `_is_name_embedded_number` — число считается частью имени, только если за ним идёт ещё одно число, а следом токен, который НЕ тире и НЕ число (то есть единица/оператор). Точечно, без ML и без словаря онкомаркеров.
- **Урок:** прежде чем усложнять (словарь имён, ML-разметка), поищите различающий признак в 1–2 соседних токенах — часто его хватает. И обязательно тест на каждый из «похожих, но разных» паттернов: одна регулярка легко ловит лишнее.

## Архитектурные решения

### Решение: Переход с WSL2 на нативную Windows Ollama

- **Альтернативы:** Оставить WSL2 / нативная Windows / обе параллельно
- **Выбрано:** Нативная Windows — прямой CUDA-доступ, +10–13% tok/s, актуальная версия 0.30.11, убирает сетевые workaround'ы с WSL-IP
- **Компромисс:** модели нужно скачать заново (~6 GB), WSL2-окружение теряет Ollama
- **Когда пересмотреть:** если понадобятся Linux-specific инструменты Ollama (Docker Compose, Open WebUI)

### Решение: Оставить qwen3-vl:8b-instruct как основную VLM-модель

- **Альтернативы:** minicpm-v:8b (быстрее 2x, но точность 67.8%) / gemma4:latest (точность 79.5%, но 41% pass_rate и 67.8s/док) / qwen3-vl:30b-a3b (MoE 30B, но 19 GB > 16 GB VRAM → CPU-оффлоад)
- **Выбрано:** qwen3-vl:8b-instruct — лидер по всем метрикам: точность 98.5%, pass_rate 88%, score 0.0172 (в 1.26x лучше ближайшего конкурента). 6.1 GB полностью помещается в 16 GB VRAM (100% GPU).
- **Компромисс:** не самая быстрая (50.6s/док vs 26.3s у minicpm-v), но точность компенсирует — меньше ручной проверки и постобработки.
- **Когда пересмотреть:** если появится VLM-модель ≤9 GB с точностью >95% и скоростью <30s/док; или если GPU апгрейд до ≥24 GB VRAM (тогда qwen3-vl:30b-a3b станет реальным кандидатом)

### Решение: Уменьшение num_predict с 16384 до 4096

- **Альтернативы:** 8192 (перестраховка) / 4096 (комфортный запас) / 2048 (впритык)
- **Выбрано:** 4096. Сначала опустили до 2048 (документ с 20 показателями требует ~500–800 токенов JSON), но на Фемофлоре (20 показателей с длинными латинскими названиями, Шаг 10) 2048 не хватило — модель обрывалась на 6-й строке. 4096 покрывает весь стенд с запасом и всё ещё кратно меньше исходных 16384.
- **Компромисс:** на редких документах с >50 показателями на одной странице теоретически может обрезать вывод.
- **Когда пересмотреть:** если появятся документы с >50 показателями на одной странице.

### Решение: Уменьшение num_ctx с 16384 до 8192

- **Альтернативы:** 4096 (минимум) / 8192 (баланс) / 16384 (текущее, медленно)
- **Выбрано:** 8192 — +15% к скорости генерации, -3s к load time, достаточно для большинства документов
- **Компромисс:** для очень длинных многостраничных документов может не хватить
- **Когда пересмотреть:** если контекст превышает 8192 токенов (промпт + изображение)

### Решение: прогрев (warmup) моделей на старте сервиса

- **Проблема:** холодный старт — загрузка 6 ГБ весов в VRAM ~100–120s (замер: cold 110s vs warm 10–20s). Штраф платил первый документ после запуска сервиса.
- **Альтернативы:** только серверный `keep_alive=-1` (не убирает ПЕРВУЮ загрузку) / прогрев блокирующий на старте (старт дольше на ~100s) / прогрев фоном.
- **Выбрано:** фоновый `warmup()` — нативный вызов Ollama `/api/generate` с пустым prompt (только load, без генерации), `num_ctx` и `keep_alive` как в бою (иначе Ollama перезагрузит модель при первом реальном запросе). Хук — `asyncio.to_thread` в старте бота и API, не блокирует. Best-effort: Ollama недоступна → лог, сервис жив.
- **Компромисс:** пока модель грузится (первые ~100s после старта), самый ранний запрос всё ещё может попасть в загрузку — но это окно куда меньше, чем без прогрева.
- **Когда пересмотреть:** если VLM и TEXT-модели разъедутся и обе не влезут в VRAM одновременно — прогревать по очереди либо только основную.

### Решение: TEXT_MODEL = та же VLM, а не отдельная text-only

- **Альтернативы:** отдельная лёгкая `qwen3:8b` (5.2 GB, быстрее на тексте) / та же `qwen3-vl:8b-instruct` для всего.
- **Выбрано:** та же VLM + adaptive-ретрай на текстовом пути. Честное сравнение стабильности на sample_001 (6 прогонов): `qwen3-vl` + ретрай — **6/6**, `qwen3:8b` — **3/6** (отдаёт непустой, но неверный результат, ретрай не срабатывает). То есть text-only не просто «не лучше», а хуже по корректности.
- **Компромисс:** теряем потенциальную скорость text-only модели, но выигрываем в стабильности — для медданных это важнее.
- **Когда пересмотреть:** если появится text-only модель, стабильно структурирующая шумные бланки (проверять только полным e2e, не изоляцией). Гибрид «text-only с фолбэком на VLM» не рассматриваем: он был мёртвым и сломанным (см. одноимённую «Сложность»).

## Итог

1. **Переход с WSL2 на нативную Windows Ollama 0.30.11** — +10–13% к скорости, убраны сетевые workaround'ы.
2. **Оптимизация config.json:** `num_predict` 16384→4096, `num_ctx` 16384→8192, `temperature` 0.3→0.0 (extract) / 0.1 (classify), `repeat_penalty` 1.2→1.1 — суммарно +15–20% к скорости генерации, детерминированный результат для OCR, небольшой шум для классификации.
3. **Сравнительный бенчмарк 4 моделей** подтвердил: `qwen3-vl:8b-instruct` — оптимальный выбор для 16 GB VRAM. Точность 98.5%, pass_rate 88%, 50.6s/док. Ближайший конкурент minicpm-v:8b быстрее в 2x, но точность 67.8% — неприемлемо для медицинских данных.
4. **qwen3-vl:30b-a3b (MoE 30B)** — непрактична для 16 GB VRAM: 19 GB → 22% CPU-оффлоад → 284s/док (5.6x медленнее baseline). Требует ≥24 GB VRAM.
5. **Альтернативы Ollama:** vLLM — для multi-user production (920 tok/s vs 155 tok/s у Ollama при 50 пользователях), но для single-user OCR разница минимальна (71 vs 62 tok/s). llama.cpp с флагами `-b`/`-ub` — заявлено 4–5x ускорение vs Ollama, но требует ручной настройки. Для текущего single-user сценария Ollama остаётся оптимальной по балансу простота/скорость.
6. **Оптимизация точности (Шаг 10):** 4 точечных фикса — adaptive fallback для сломанного grammar constraint, multi-result парсинг склеенных строк, `num_predict=4096` для длинных бланков и детерминированный корректор классификации по заголовку. Результат: **34/34 PASS (было 30), точность 325/325 = 100% (было 98.5%), скорость 27.1s/док (было 50.6s, -46%), score 0.0369 (+2.1x)**. Все 4 исходных FAIL закрыты, ни одной регрессии.
7. **Код-ревью после оптимизации** вскрыло мёртвый и сломанный гибридный fallback (`NameError` в недостижимой ветке). Убрали его, объединили дублирующиеся парсеры строк (`_parse_text_line` / `_parse_text_line_all` → общий `_parse_first_result`), декомпозировали разросшийся `_extract_once`. Урок: оптимизацию всегда стоит закрывать ревью — часть «фиксов» оказывается техдолгом.
8. **Стабилизация плавающих тестов:** нашли асимметрию — adaptive fallback против пустого ответа XGrammar стоял только на картиночном пути, а текстовый (`_structure_text`) флапал 3/6 прогонов. Добавили симметричный ретрай без grammar (бюджет `_TEXT_EMPTY_RETRIES=2`) → **6/6 стабильно**. Урок: одинаковые по смыслу пути должны иметь одинаковые страховки; «стабильно в изоляции» ≠ «стабильно end-to-end».
9. **Прогрев (warmup) моделей на старте:** фоновая загрузка весов в VRAM при запуске бота/API — первый документ не платит холодный старт ~100–120s. Нативный `/api/generate` с пустым prompt, best-effort, не блокирует старт.
