### Сложность: GLM-4.6V-Flash-PRISM не отвечает на inference

- **Симптом:** `curl http://localhost:11434/api/generate` с моделью `hf.co/Ex0bit/Elbaz-GLM-4.6V-Flash-PRISM:latest` — нет ответа за 30+ секунд. Pytest зависает на инициализации.
- **Гипотезы:** 1) Модель через `hf.co/` имеет несовместимый format; 2) Проблема с vision-encoder; 3) Модель загружена в GPU но не отвечает на chat-запросы.
- **Что пробовал:** `ollama ps` показывает модель загруженной (6.8 ГБ, 100% GPU). Прямой `curl` — таймаут. `qwen3.5-9b-abliterated-vision` отвечает за 5.8с — значит проблема в конкретной модели.
- **Решение:** (в процессе) — пропустить GLM-PRISM, перейти к другим моделям.
- **Урок:** Сторонние модели через `hf.co/` могут иметь проблемы совместимости с Ollama API.

### Шаг 15: Архитектура medical RAG + Garmin

Исследована архитектура для медицинской аналитики с данными Garmin:

```
OCR (VLM) → RAG (bge-m3 + PubMed + MedlinePlus) → Medical Reasoning (LLM)
                                                         ↑
                                              Garmin MCP (пульс, сон, стресс)
                                                         ↓
                                              Web Search (searxng → исследования)
                                                         ↓
                                              Strategy Synthesis → TLP (🟢🟡🔴)
```

Ключевые находки:
- **PubMed MCP** — статья про MCP server для biomedical research с Ollama (https://horstherb.medium.com/navigating-the-medical-research-landscape-with-mcp-and-agents-a-local-implementation-with-ollama-b33a0d19bc20)
- **Garmin MCP** — `roman-raducu/garmin-mcp` (прямой доступ к Garmin Connect, интеграция с Ollama)
- **Open Wearables MCP** — unified доступ к Garmin, Apple Health, Whoop (https://openwearables.io/docs/mcp-server)
- **RxLM-Med-Agent** — production-grade clinical AI agent на Qwen-VL с RAG по 53 учебникам и TLP safety (https://github.com/tokisaka23/RxLM-Med-Agent)
- **Lab-AI** — RAG для персонализированных референсных диапазонов с учётом возраста/пола (https://doi.org/10.1109/ichi64645.2025.00025)

### Шаг 12: Reasoning-бенчмарк uncensored моделей (2026-07-12)

**Задача:** сравнить 5+ uncensored локальных LLM на medical reasoning — анализ анализов, диф.диагноз, стратегия лечения, проверка врача, интеграция Garmin.

**Тесты (`tests/test_e2e_reasoning.py`, 8 тестов):**
1. `test_model_responds` — базовая проверка ответа
2. `test_no_refusal_medical_topic` — отсутствие цензуры на медицинскую тему
3. `test_identifies_abnormalities` — анализ лабораторных отклонений
4. `test_critical_values_detection` — распознавание критических значений (калий 7.2, креатинин 340)
5. `test_diff_diagnosis_with_labs` — дифференциальный диагноз с учётом анализов + Garmin
6. `test_treatment_recommendations` — стратегия лечения (препараты, дозы, контроль, Garmin)
7. `test_verify_doctor_prescription` — аудит назначений врача
8. `test_garmin_anomaly_correlation` — корреляция данных Garmin с анализами

**Тестовые данные:** JSON с 8 показателями (Hb 92↓, ферритин 8↓, железо 7.2↓, TSH 6.8↑, T4 9.1↓, витамин D 18↓, глюкоза 5.4, лейкоциты 6.2) + Garmin-данные (пульс покоя 78, сон 5.2ч, deep 12%, HRV 28ms, stress 55).

**Результаты:**

| Модель | PASS | FAIL | Время | Язык | Особенности |
| --- | ---: | ---: | ---: | --- | --- |
| gemma4:latest (12B) | 8/8 | 0 | 3856s | RU | Все тесты, без цензуры, структурированные ответы |
| JOSIEFIED-Qwen3:8b-health | 7/8 | 1 | 1180s | RU/EN | Мед. профиль, провал — англ. ответ на патофизиологию |
| MedExpert (8B) | 7/8 | 1 | 1974s | RU | Быстрейшая (8.7s/запрос), провал — Garmin без пульса |

**Ключевые находки:**

1. **Abliteration → украинизация:** Qwen3.5-9b-abliterated систематически отвечает на украинском вместо русского. Причина: abliteration удаляет refusal direction, который в Qwen тесно связан с языковым переключением — модель теряет русскую "личность" и уходит в украинский. Это известный побочный эффект surgery на weights.

2. **Thinking mode = 5 мин/запрос:** Qwen3.6-27b с thinking mode тратит 170-300s на один reasoning-запрос. Для production нужен streaming + user-facing progress bar. Без thinking — в 10 раз быстрее, но менее точно.

3. **Gemma4 — неожиданный лидер:** Не abliterated, но прошла все 8 тестов. Google не накладывает жёсткую медицинскую цензуру на Gemma. Ответы на чистом русском, структурированные, с правильными диагнозами.

4. **MedExpert — мед. fine-tune работает:** Корректно ставит диагнозы, назначает лечение, но не интегрирует данные носимых устройств (Garmin) — модель не обучена на wearable-данных.

5. **JOSIEFIED-Health:** Medical fine-tune поверх abliterated Qwen3:8b. Хорошо работает на медицинских задачах, но иногда переключается на английский (наследие base model).

6. **Garmin-интеграция — слабое место всех моделей:** Только Gemma4 и Qwen3.6-27b корректно связывают пульс покоя 78 + HRV 28ms с гипотиреозом и анемией. Остальные модели анализируют Garmin-данные поверхностно.

**Архитектура reasoning-тестов:**

```text
tests/test_e2e_reasoning.py
├── TestReasoningBase      # базовые проверки (ответ, нет цензуры)
├── TestLabAnalysis        # анализ анализов, критические значения
├── TestDifferentialDiagnosis  # диф.диагноз с анализами + Garmin
├── TestTreatmentStrategy  # стратегия лечения
├── TestDoctorVerification # аудит назначений врача
└── TestGarminIntegration  # корреляция Garmin ↔ анализы
```

**Сложность:** abliterated модели непредсказуемо переключают язык (RU/UA/EN), нужно мультиязычные ассерты. Thinking-модели требуют таймаут 300s+ на запрос. Скачивание 35B MoE моделей (~21-23 ГБ) через Ollama нестабильно — connection reset каждые 30-60 минут, нужен auto-retry.

### Шаг 13: Language lock и достоверный прогресс инференса (2026-07-12)

Первые прогоны показали, что расширение ассертов на украинские и английские термины только скрывает проблему: модель может пройти тест, но отдать пользователю ответ не на том языке. Поэтому добавлена отдельная фиксация языка в `tests/test_e2e_reasoning.py`:

- префикс system-сообщения: «отвечай строго на русском языке»;
- повтор инструкции в конце каждого user-промпта;
- разрешены только медицинские латинские аббревиатуры `TSH`, `HRV`, `T4`;
- `_language_profile()` считает украинские буквы `і/ї/є/ґ` и долю латиницы, чтобы измерять эффект, а не оценивать его субъективно.

На `lukey03/qwen3.5-9b-abliterated-vision` результат улучшился с 4/8 до 6/8. В новом прогоне шесть непустых ответов были классифицированы как RU, но один ответ снова ушёл в UA — языковая фиксация значительно снижает риск, но не является гарантией для abliterated weights. Это зафиксировано как отдельная наблюдаемая метрика.

#### Почему клиентский таймаут был удалён

Для 27B/35B reasoning-моделей лимит 180 секунд создавал ложную ошибку: модель продолжала считать, а интерфейс показывал «ошибка». Теперь клиент не выносит вердикт по времени. Состояние `failed` устанавливает только серверный pipeline. Если сеть временно недоступна, фронт показывает «Связь с сервером прервалась — перепроверяю…» и продолжает polling.

#### Модель прогресса

В `src/botkin/pipeline/progress_model.py` реализована оценка по EMA длительности стадий:

- каждая стадия (`recognizing`, `normalizing`) получает вес в общем прогрессе;
- длительность предыдущих запусков записывается в `stage_durations`;
- текущий процент считается как `вес завершённых стадий + вес текущей × elapsed / EMA`;
- внутри стадии значение ограничено 95%, а 100% выдаётся только при `extracted`;
- API возвращает `percent`, `eta_seconds`, `stage_elapsed_s`, `alive`;
- фронт показывает процент, ориентировочное время и пульс-индикатор «модель работает».

Это не процент сгенерированных токенов: Ollama в текущем API не даёт надёжного прогресса reasoning. Поэтому UI честно называет значение оценкой, основанной на исторической длительности, а heartbeat подтверждает, что сервер продолжает обслуживать документ.

#### Проверка

- `tests/test_progress_model.py`: 13 unit-тестов — PASS;
- кабинет/API/repository smoke-набор: 46 тестов — PASS;
- `node --check src/botkin/web/app.js`: PASS;
- две 35B модели полностью скачаны и готовы к последовательным прогонам (одновременная загрузка на Mac с 36 ГБ unified memory не используется).

### Шаг 14: GLM-кандидаты и детерминированный слой фактов (2026-07-12)

#### Исправление reasoning-тестов и настроек

Провал `satgeze/qwen36-35b-uncensored-1m` оказался составным:

- `test_model_responds` принимал только символ `4`, хотя корректный ответ модели был «Четыре»;
- при `think=medium` и `num_predict=4096` часть ответов завершалась с пустым `message.content`, потому что бюджет уходил в отдельное поле `message.thinking`;
- для reasoning теперь используется `REASONING_NUM_PREDICT=8192`, значение `REASONING_THINK` нормализуется в `false/true/low/medium/high`;
- если финальный `content` пуст, тест повторяет тот же запрос с `think=false`, не выдавая reasoning-трейс за пользовательский ответ.

Проверка короткого запроса после исправления: PASS, `think=false`, `content=7`, 12,22 секунды на 35B. Полный бенч с новым fallback будет выполнен отдельно: отключение thinking для всех медицинских запросов не выбрано, потому что это меняет сам предмет проверки reasoning.

#### Какие GLM подходят для Mac M3 Max 36 ГБ

По состоянию на проверку 2026-07-12 выбраны два локальных кандидата:

| Модель | Формат | Размер/класс | Почему подходит | Настройка |
| --- | --- | --- | --- | --- |
| `huihui_ai/glm-4.7-flash-abliterated` | Ollama | GLM-4.7-Flash, 30B-A3B MoE | Свежая uncensored-версия, прямой `ollama pull`, reasoning | `think=medium`, `num_predict=8192` |
| `alibilge/Huihui-GLM-4.6V-Flash-abliterated:q4_k_m` | Ollama | 9B VLM, Q4 | Vision, около 5 ГБ, помещается с большим запасом | `think=false`, `num_predict=4096` |

GLM-4.6-Derestricted на 36 ГБ не выбран: найденные GGUF-варианты GLM-4.6 — 357B, даже минимальные кванты измеряются десятками/сотнями гигабайт. GLM-4.7-Flash-Derestricted интересен, но в найденном виде требует самостоятельной загрузки GGUF/совместимого сервера; сначала проверяем прямые Ollama-пакеты.

Проверенные источники:

- [Ollama API Chat](https://docs.ollama.com/api/chat), проверено 2026-07-12: “`think` (boolean or string) — Whether to return separate thinking output.” Перевод: `think` управляет отдельным выводом рассуждений.
- [Huihui GLM-4.7-Flash abliterated](https://ollama.com/huihui_ai/glm-4.7-flash-abliterated), проверено 2026-07-12: “This is an uncensored version of zai-org/GLM-4.7-Flash created with abliteration.” Перевод: это uncensored-версия GLM-4.7-Flash, полученная abliteration.

#### Анализ без LLM

Полностью заменить LLM можно для части задач, и это желательно:

1. OCR/PDF text layer извлекает исходные строки.
2. `parsing.scalars` детерминированно разбирает числа, единицы и референсные диапазоны.
3. `normalize` приводит название показателя и единицы к канонической форме.
4. Новый `clinical.facts` вычисляет только проверяемые факты: ниже/выше/в пределах референса.
5. LLM получает готовую фактуру и занимается только объяснением, группировкой и формулировкой вопросов врачу.

Преимущества: одинаковый результат при каждом запуске, отсутствие галлюцинаций в арифметике, быстрый ответ, возможность аудита и тестирования. Ограничение: правила не заменяют клиническое мышление — по одному отклонению нельзя безопасно выводить диагноз или схему лечения.

Практическое разделение ответственности:

| Задача | Детерминированный инструмент | LLM |
| --- | --- | --- |
| Число, единица, референс | Да | Нет |
| Флаг ниже/выше нормы | Да | Нет |
| Тренд показателя во времени | Да, статистика/SQL | Объяснение тренда |
| Расчётные шкалы и индексы | Да, версия алгоритма | Комментарий |
| Дифференциальный диагноз | Проверки противопоказаний и полноты | Гипотезы с обязательной верификацией |
| Лечение и дозировки | Справочник, ограничения, врачебное подтверждение | Только обсуждение, не назначение |

Новый слой намеренно не содержит медицинских порогов, которых нет в бланке: он сравнивает только с референсом конкретной лаборатории. Это снижает риск подменить лабораторный диапазон универсальной «нормой».

#### Ключевые выводы

1. **think=high на GLM-4.7 непрактичен**: reasoning не останавливается, исчерпывает весь бюджет токенов. Нужно `think=medium` или явный лимит thinking-токенов.
2. **35B MoE — оптимальный размер для M3 Max 36GB**: Qwen3.6-35b и satgeze-35b загружаются в 22-23 ГБ VRAM, оставляя память для context window 65536.
3. **27B dense медленнее 35B MoE**: Qwen3.6-27b (920s) в 4.8 раза медленнее Qwen3.6-35b (192s) при схожем качестве — MoE-архитектура эффективнее на Apple Silicon.
4. **Reasoning-модели превосходят non-reasoning по медицинской глубине**: 15-16 маркеров у thinking-моделей против 10 у gemma4, при сопоставимом объёме content.
5. **Ни одна модель не использовала интернет**: все ответы основаны на промпте и встроенных знаниях. RAG-контекст (ГРЛС, PubMed) был встроен в промт, но модели не запрашивали внешние ресурсы самостоятельно.
6. **Abliterated = без цензуры**: все 6 моделей (4 abliterated, 1 uncensored, 1 gemma4) дали полные медицинские рекомендации без refusal-маркеров.

### Находка при подготовке статьи: детерминированный слой молча пропускал отклонения

При сверке чисел из отчётов моделей с содержимым `data/botkin.db` (user_id=1) вскрылся баг, который в бенчмарке был не виден.

- **Симптом:** в собранном промте мочевая кислота 581,09 при референсе `220 - 450 umol/L` помечена статусом «в норме». Проверка показала: из 7 показателей, у которых `ref_low`/`ref_high` в БД = NULL, а диапазон лежит только в `ref_text`, **5 реально вне нормы** (мочевая кислота, Creatinine 1.781 при 0.8–1.2, BUN 10.04 при 1.8–5.0, Total Protein 99 при 60–80, Globulins 51 при 0–20) — и все 5 код помечал «в норме».
- **Корневая причина:** `classify_value()` в `src/botkin/clinical/facts.py` сравнивает значение только с числовыми `ref_low`/`ref_high`. Если оба NULL, возвращается `"unknown"`, а в скрипте бенчмарка (`_build_user_prompt`) аналогичная ветка падала в «в норме». Числовой диапазон, уехавший при извлечении в текстовое поле `ref_text`, никто не парсил.
- **Ошибка расследования (моя):** сначала классифицировал упомянутый моделями «повышенный креатинин» как галлюцинацию, потому что искал по кириллице `креатинин`. В БД он лежит латиницей — `Creatinine`. Урок: при сверке фактов из мультиязычных данных искать по всем вариантам написания.
- **Кто поймал:** топ-3 reasoning-модели (Qwen3.6-35b, satgeze-35b, Qwen3.6-27b) прочитали текстовый референс и сами скорректировали флаг. Qwen3.6-27b явно указала: «Креатинин… однако помечен „в норме“… Значение превышает диапазон и сигнализирует о гиперурикемии» (`output_huihui_ai_Qwen3.6-abliterated_27b.md`). gemma4, GLM и JOSIEFIED флагу поверили и отклонения пропустили.
- **Фикс:** добавил `parse_reference_range(ref_text)` в `facts.py` (диапазон `A - B`, односторонние `< B` / `> A`, en-dash, десятичная запятая; конвертацию единиц намеренно не делает). `build_lab_facts` парсит текст, если числовых границ нет; отображаемый референс остаётся оригинальным. Ту же функцию переиспользовал в `scripts/bench/bench_health_report.py`, убрав дублирующую логику.
- **Тесты:** `tests/test_clinical_facts.py` — регрессия на все 5 реальных значений + разбор форматов `ref_text`. Итого 29 passed.
- **Вывод для статьи:** самая опасная ошибка эксперимента — не выдумка нейросети, а тихий баг детерминированного слоя, который считался непогрешимым. Правда нашлась на пересечении «код + модель», где они разошлись.
